# Merge-field / placeholder tokens for TipTap + Lexical (2026-08-13)

**Question**: Best practice (2024-26) for a mail-merge token system shared by a TipTap(ProseMirror) legal-doc editor and a Lexical email composer, surviving DOCX<->HTML round-trip. Five parts: token representation, serialization contract, DOCX split-run interop, picker UX, cross-editor consistency.

**Findings**:

1. **Token = atomic inline node, NOT raw `{{text}}` in the editor.** Consensus (CKEditor5 Merge Fields, TipTap Mention) is an atomic non-editable inline element ("pill/chip"). Raw-text `{{client_name}}` in contenteditable fails: caret can land mid-token (`{{cli|ent}}`), backspace/typing corrupts the key, spellcheck underlines it, copy/paste splits it, and find/replace can partially match. TipTap Mention is the exact model: an inline atom node (`inline:true`, `group:'inline'`, `atom:true`, usually `selectable`, `draggable:false`) whose identity lives in `node.attrs` (`id`, `label`) not in editable text. Mention is directly reusable for a first cut (swap `suggestion.char`), but for merge fields a **thin custom Node ("mergeField") is the right call** — you want your own attribute schema (`data-token` key), your own closed-set validation, and independence from the `@` mention semantics. Custom node is cheap; it IS a ProseMirror node with `addAttributes/renderHTML/parseHTML/renderText`.

2. **Serialization contract: `{{token}}` is the wire/storage form; pill is the view.** Canonical pattern:
   - Editor DOM: `renderHTML` emits `<span data-token="client_name" class="merge-field" contenteditable="false">Client Name</span>`; `parseHTML` matches `span[data-token]` and rehydrates the atom on load.
   - Attributes via `addAttributes()` with per-attr `parseHTML: el => el.getAttribute('data-token')` and `renderHTML: attrs => ({ 'data-token': attrs.token })`.
   - `renderText()` returns `{{${attrs.token}}}` so plaintext/export/copy yields canonical syntax.
   - For a pure `{{token}}` STORAGE string (not editor HTML), serialize by walking the doc and mapping each mergeField node to `{{token}}`; on load, run a paste/parse rule (ProseMirror `nodeInputRule` / a scan pass) that converts `{{token}}` substrings back into nodes. Keep ONE registry-validated syntax; the editor never persists the pretty label, only the key.

3. **DOCX interop — consolidate split runs FIRST.** Word fragments text across `<w:r>`/`<w:t>` arbitrarily (rsid/spellcheck/formatting boundaries), so `{{client_name}}` is frequently split across runs. This is the SAME runs-vs-logical-text problem as [[stable-position-anchoring-ooxml-editor-2026-07-22]]. Standard fix = docxtemplater's approach: a **flat-structure lexer** that flattens the paragraph's runs into one logical string, finds delimiter pairs on the joined text, then re-emits (docxtemplater "deep-dive-into-internals": XML-lex -> delimiter-parse -> placeholder -> module postparse). OpenXML equivalent = a run-merge/normalize pass (MarkLogic `ooxml:runs-merge`; caution: naive run-merge can drop non-text children like `<w:tab>`). **Decision: normalize tokens into single clean runs server-side BEFORE DOCX->HTML conversion**, then map each intact `{{token}}` to a mergeField atom during conversion. At export, atoms map back to `{{token}}` runs (or straight to values if merging). Do NOT try to detect split tokens in the browser after lossy HTML conversion — the run structure is already gone. Two viable end-states: (a) template stays tokenized (atoms round-trip as `{{token}}` runs), or (b) merge-at-export (atoms replaced by data values in the final OOXML). Keep merge itself server-side/OpenXML for fidelity; the editor only manages token identity/placement.

4. **Picker UX: closed-set dropdown + typed trigger, categorized.** Mature reference = CKEditor5 Merge Fields: toolbar dropdown button + menubar Insert item + typing the prefix (`{{`) opens a filtered list of the DEFINED set, grouped into categories, with preview/sample values. Document-automation tools (Gavel/Documate "Insert Variable", Woodpecker reuse-same-data-point) all present a curated field list, never free typing. Recommendation for Spaarke: (i) toolbar/menu "Insert field" dropdown grouped by category as the discoverable primary; (ii) a `/`-slash or `{{`-trigger inline picker (TipTap `@tiptap/suggestion`) for power users, filtering the SAME registry; (iii) validate on insert against the registry so unknown keys can't be created (prevents typos); (iv) render unknown/legacy tokens as a distinct "warning" pill rather than silently.

5. **Cross-editor consistency: shared token registry + thin per-editor node; `{{token}}` is the interop contract.** Architecture: a framework-agnostic `TokenRegistry` (id, label, category, sampleValue, maybe formatter) + serialize/parse helpers that both editors import. Then a **thin TipTap Node (ProseMirror atom)** and a **thin Lexical node**. Lexical nuance: two implementation choices — (a) `DecoratorNode` (React component, wrapped `contentEditable:false`, truly atomic, must implement `getType/clone/importJSON/exportJSON` + `importDOM/exportDOM` to round-trip the `data-token` span) — best fidelity match to a ProseMirror atom; or (b) subclass `TextNode` + `setMode('token')` (Lexical playground MentionNode pattern) — token-mode deletes as a single unit and is lighter, but it IS text (spellcheck/format edge cases, less "pill-like"). For parity with a ProseMirror atom, prefer **DecoratorNode**. Pitfalls making PM atom == Lexical node behave the same: (1) selection/deletion semantics differ (PM atom is one step; Lexical token-mode vs decorator differ) — pick decorator for both-atomic; (2) copy/paste + serialization must both round-trip through the SAME `<span data-token>` DOM and the SAME `{{token}}` text so content moves between editors losslessly; (3) unknown-token handling and closed-set validation must live in the shared registry, not duplicated per editor; (4) label vs key — both editors must store only the key and resolve label from registry at render, or labels drift.

**Recommendation**: Custom `mergeField` atom inline node (both editors) over reusing Mention; `{{token}}` as the single canonical storage/interop syntax; `data-token` span as the single DOM contract; shared `TokenRegistry` + serialize/parse in a framework-agnostic package; consolidate split runs server-side (OpenXML run-normalize) BEFORE DOCX->HTML; merge values server-side at export. Lexical side = DecoratorNode for atom parity.

**What to avoid**: raw `{{}}` text left editable in contenteditable; storing the human label instead of the key; detecting split tokens browser-side post-conversion; free-text field entry (typos); two divergent token syntaxes; duplicating registry/validation logic per editor; naive OOXML run-merge that eats `<w:tab>`/non-text run children.
