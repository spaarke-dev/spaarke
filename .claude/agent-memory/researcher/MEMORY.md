## 2026-09-08: Word desktop document.url viability for SPE
**Question**: Is Office.context.document.url a viable identity source for SharePoint Embedded-backed Word desktop files?
**Findings**: The Office.js API docs say the property returns the current document URL or null, but they do not explicitly establish desktop behavior for SharePoint Embedded-backed files. The Graph shares API is documented for encoding a URL into a sharing token and resolving it to a DriveItem, but this is still a logical chain that requires a real URL value from the host. The most honest verdict is AMBER unless a live Word desktop + SPE file check confirms the URL is actually exposed and resolvable.

## 2026-09-08: Word add-in save collision path
**Question**: Does the Word add-in save path inherit the shipped OBO fail-on-collision behavior, and what happens on a same-name save?
**Findings**: The add-in posts JSON/base64 to `POST /api/office/save`, and `OfficeService` synchronously calls `OfficeStorageUploader`, which calls the no-policy `SpeFileStore.UploadSmallAsync` overload. That overload explicitly defaults to `ConflictBehavior.Replace`, and `UploadSessionManager` sends `@microsoft.graph.conflictBehavior=replace` on Graph simple PUT, so a same-name Office save replaces the existing SPE item before Dataverse/content-dedup reconciliation; the add-in has no large-upload/session route. OBO instead defaults to `ConflictBehavior.Fail`, translates Graph 409 to `SpaarkeStorageException`, and `@spaarke/sdap-client` exposes `UploadNameConflictError`; the Office client does not depend on that package and maps non-OK save responses to generic errors. Office content dedup is gate-after-write and uses the immutable suppress path, not editable link/graduate, so it cannot prevent the filename overwrite and may delete the newly overwritten item on a hash hit.
