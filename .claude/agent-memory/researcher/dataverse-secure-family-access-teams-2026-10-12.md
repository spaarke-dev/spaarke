# Secure families via access teams — 2026-10-12

**Question**: Is "all secure rows owned by ONE memberless owner team in a Secure BU + ONE user-created access team per family + GrantAccess each row to that team" sound at thousands of families / 100Ks of rows?

## Findings (all Learn unless noted)
- **User-created access team (teamtype=Access, SystemManaged=false) CAN be shared on many rows across many tables** (use-access-teams-owner-teams-collaborate-share-information, about-team-templates). Members via **AddMembersTeam/RemoveMembersTeam** (or teammembership_association); **AddUserToRecordTeam is templates-only** (one auto team per record, can't be shared elsewhere).
- **Template limits (user's "2" is wrong)**: MaxAutoCreatedAccessTeamsPerEntity default **4**; MaxEntitiesEnabledForAutoCreatedAccessTeams default **100** (dev doc; stale deployment SDK page says 5); set via OrganizationSettingsEditor. Neither limit applies to user-created teams.
- **NO documented max** on shares per team, teams per env, teams per user, POA rows per record/principal. Only soft signals: manage-principalobjectaccess-storage (share to teams not users; team-as-owner when same list recurs; remove access-team members when done), wp-security-cds ("use sharing only for exceptions... less efficient"), fast-track-security training ("users members of thousands of teams in thousands of BUs can be a challenge"; "excessive sharing leads to a large POA table"; updating user/team/BU rows can flush the security cache). Community (Resco POA analyzer): degradation reported >20M POA rows. itaintboring: team share = 1 POA row vs N for N users, BUT SystemUserPrincipals (team membership rows) growth can negate the gain.
- **POA doc is ambiguous for access teams**: says POA rows are created "whenever a user is added to the access team" (system-managed + manual). Community SQL analysis says team share = 1 POA row per (record, team). Spike: count POA rows before/after AddMembersTeam.
- **Cascade/POA**: Share/Reparent cascade writes inherited POA rows (inheritedaccessrightsmask); parent owner/owning-team inherited via parental rel; Assign cascade Cascade All re-owns children AND moves their BU (when AlwaysMoveRecordToOwnerBusinessUnit=true default). Cleanup messages: CreateAsyncJobToRevokeInheritedAccess, ResetInheritedAccess (troubleshoot/.../cleanup-inherited-access). Direct POA delete unsupported. No new 2023+ "inherited access model" found beyond these.
- **Access checks**: privilege check THEN access check; shared access via team counts "provided user passed the privilege check" (how-record-access-determined). Dataverse search/Copilot "respects security roles and permissions" (relevance-search-benefits); Copilot Studio Dataverse knowledge needs Authenticate-with-Microsoft. **Docs silent on security-change propagation latency to search index** (only: config/data changes up to 15 min). Group-team (Entra) membership syncs just-in-time at sign-in/impersonation, cached ≤8h; SyncGroupMembersToTeam exists. Access-team membership change latency to the security cache: UNDOCUMENTED.
- **Hierarchy security LEAK**: manager hierarchy gives managers access to records "directly shared to ... the team that a user [direct report] is a member of" (hierarchy-security, how-record-access-determined). Exclude secure tables from hierarchy table list.
- **BU-literal risk**: how-record-access-determined lists "record belongs to same BU as the team of which user is a member" under role access at BU depth. Keep per-family access teams in a BU that owns NO secure rows (not the Secure Record BU). Literal reading, unverified.
- **Create-by-members hole (inference)**: access-team members "can't create records by using the access rights of the access team"; a member with Basic Create who creates a child row via UI becomes OWNER (ownership gives access at any depth, survives access-team removal). Remove Create/Assign/Share from user roles on secure tables; BFF creates rows with ownerid=owner team.
- **ShareToPreviousOwnerOnAssign** (org setting, default No): if Yes, assign to owner team creates full-rights POA for previous owner. Appointment/activity special case shares with previous owner if still participant even when setting is No.
- **Bulk**: ReassignObjectsOwner = ALL records of FromPrincipal (user/team/org) (+ optional objectType) → useless for ONE family on a shared owner team. Per-row Assign = update ownerid (security-sharing-assigning); UpdateMultiple works on custom standard tables (100-1000/request, all-or-nothing rollback, no alt keys via Web API); ExecuteMultiple/$batch ≤1000 but start small; service protection per user per server: 6,000 req/5 min, 20 min exec/5 min, 52 concurrent, 429+Retry-After; same limits for app users; DOP header; Power Platform request entitlement counts each Target. Elastic tables: no sharing, no access teams, no Assign/Share cascades (create-edit-elastic-tables) → NOT viable. No DeleteMultiple on standard tables.
- **Entra group teams**: can own records, can be assigned rows (aad-group-team); membership dynamic, no Dataverse-side membership mgmt; nesting for group TEAMS undocumented (only env security-group nesting documented in control-user-access). Poor fit for revocation-latency-sensitive families.
- **Modernized BUs (matrix) GA**: owning BU settable, owner needs only a Read-granting role; AlwaysMoveRecordToOwnerBusinessUnit=false keeps BU on owner change; when false, child-owner privilege is NOT validated on cascade (doc examples).
- **NEW (2026-09/10): "Filtered record ownership" PUBLIC PREVIEW** (maker/data-platform/filtered-view-record-ownership, ms.date 2026-09-24; MC1486027 preview 2026-10-02; wp-security-cds updated 2026-10-05): RecordFilter(FetchXML)+EntityRecordFilter granted per privilege in a role; works on existing user/org-owned tables too; union semantics; NO deny; one filter per predicate value → per-family filter/role doesn't scale to thousands; Dataverse Search link-entity limitation. Supersedes the 2026-08-20 "blog-only watch item" status. Still no restrictive primitive.
- **Better-aligned alternative worth spiking**: owner team PER FAMILY (Microsoft guidance: "use the team as the record owner if you frequently share records with the same list of users"). Team role at Basic with "Team privileges only" inheritance → members use privilege only for team-owned rows; zero POA, no per-row GrantAccess, new rows by BFF get ownerid=family team. Costs: thousands of owner teams each needing role assignment; Assign cascade; team BU rule.
- Audit: share changes, N:N associate/disassociate, security role changes audited; team table in common-entities set (manage-dataverse-auditing).
