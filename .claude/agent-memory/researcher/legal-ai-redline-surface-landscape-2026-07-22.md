# Legal-AI redline document-surface landscape (2026-07-22)

**Question**: Independent arch assessment for an AI legal-drafting tool that must (a) generate tracked-change redlines + comments into .docx with high fidelity and (b) insert AI-generated text at a user-highlighted location. Three parts: (1) how leading legal-AI products implement their doc surface + redlining, (2) Office.js as a drafting surface — concrete capabilities + limits, (3) server-side OOXML library comparison for precise w:ins/w:del insertion.

**Findings**:

1. **The market has bifurcated into two surfaces, and the winners are Word-add-in-native for redlining.** Spellbook, Robin AI, Ivo, Legora, Gavel Exec, Copilot-in-Word, Claude-for-Word all ship a **Word add-in (Office.js, doc stays in Word's engine)** as the redline surface — the pitch is explicitly "no copy-paste into a browser, native Track Changes preserves the review workflow, edits appear under the lawyer's authorship." Several ALSO run a **standalone web app** for review/benchmarking/batch (Gavel Exec for Web, Legora tabular review, Harvey web app) but the *redline-into-Word* action happens in the add-in. Harvey uniquely documents a dual output: Word add-in → OfficeJS → native track changes, AND web app → server "docx service" → direct OOXML export. The pure standalone OOXML-native browser editors (SuperDoc, OnlyOffice-style) are the OSS building blocks, not the legal-AI incumbents.

2. **How each produces redlines** (cited): Spellbook = native Word Track Changes, suggestions authored under the lawyer's name. Robin AI = all suggestions appear as tracked changes (or comments/highlights per company standard), edits alongside user without overwriting manual changes, AI is aware of existing tracked changes. Ivo = NOT inline redlines — checklist/issue-list + suggested edits against playbook rules (important contrast). Legora = in-Word redlining + real-time commenting driven by rule-based playbooks (Azure OpenAI GPT-4o/o1). Gavel Exec = structured redlines + comments in Word Online, "apply cleanly over existing redlines no matter which track-changes mode you're in." Copilot-in-Word (2026, Frontier early-access first) = word-level native track changes + contextual comments; enabling Track Changes before invoking Copilot yields a per-change accept/reject diff.

3. **Office.js CAN produce tracked changes but only INDIRECTLY, and this is the load-bearing limit.** There is NO API to emit a `w:ins`/`w:del` with chosen author/date directly. The mechanism every add-in uses: set `document.changeTrackingMode = "TrackAll"` (WordApi 1.4), then perform ordinary edits (`range.insertText(..., "Replace")`, `body.insertParagraph`, delete) — **Word's engine records those API edits as native revisions** (confirmed by community issues + snippets). `Word.TrackedChange`/`TrackedChangeCollection` (WordApi 1.6) and `document.revisions` are **read/accept/reject ONLY** — you enumerate/accept/reject, you cannot construct one. Authorship of API-made tracked changes follows the signed-in Word user, not an arbitrary author string. Known bugs: `TrackedChange.text` returns empty string for Deleted type (office-js #5188); retrieving markup/revision *display* mode is limited (#6246); `changeTrackingMode` load flaky on Word Windows in some builds (#2797); Range-from-tracked-change behaves differently native vs online (#5334).

4. **Office.js positioning/anchoring toolkit (for "insert at highlighted location"):** `document.getSelection()` returns the live Range = the exact highlight; `range.insertText/insertHtml/insertOoxml(..., location)` inserts there. Stable anchors = **ContentControls** (`contentControls` collection, tag/title, survive edits — the recommended durable anchor) and **Bookmarks** (`getBookmarks`/`insertBookmark`). **Search API** (`body.search(text, options)` with wildcards) returns Ranges for text-locate. **Comments API** (WordApi 1.4: `range.insertComment`, `body.getComments`, `CommentCollection`) is first-class. **Fidelity is native/perfect because the document never leaves Word's rendering+layout engine** — no OOXML→HTML→OOXML round-trip, so styles/numbering/headers/footers/embedded objects are untouched; the add-in only mutates the Range it names. That's the core architectural advantage over a browser editor. Limits: `insertOoxml` accepts an OOXML fragment but you don't control revision wrapping; no fine-grained control over how Word coalesces adjacent revisions; complex multi-paragraph structured redlines are harder to place precisely than with server OOXML.

5. **Server-side OOXML library ranking for precise w:ins/w:del + comments (best-practice tier):** **(A) Open XML SDK (.NET)** — MIT, first-class `InsertedRun`/`DeletedRun` + `CommentRangeStart/End` etc., the Spaarke stack choice; low-level so pair with OpenXmlPowerTools/Clippit for diff→redline. **(A) Aspose.Words (.NET/Java/Python)** — commercial, highest-level: real revision engine (`StartTrackRevisions`, `Document.Compare` auto-generates redlines, per-revision access) — most feature-complete but paid. **(B) docx4j (Java)** — `RunIns`/`RunDel` are JAXB subclasses of `CTTrackChange`; full control but you hand-build the object model; no high-level revision helper. **(C) python-docx — does NOT support tracked changes** (no w:ins/w:del); must drop to raw lxml OR use add-on libs: **JSv4/Python-Redlines** (compares 2 docx → third redline via a bundled .NET OpenXmlPowerTools binary), **balalofernandez/docx-revisions** (adds w:ins/w:del to python-docx), or **Aspose.Words for Python**. Consensus best-practice for *programmatic redlining into an existing docx while preserving everything else*: Open XML SDK or Aspose on the .NET side; docx4j on JVM; python-docx only with a redline add-on.

**The strategic conclusion for the assessment**: two viable architectures. (i) **Word-add-in path** (Office.js, TrackAll + Range edits) = native perfect fidelity, redlines "just work," but you inherit Office.js's indirect/coarse revision control and can't set arbitrary authorship — this is what every legal-AI incumbent ships for the redline action. (ii) **Server OOXML path** (Open XML SDK) = precise programmatic w:ins/w:del with chosen author/date, works headless/at scale and for the web-editor surface, but YOU own fidelity and Word's undocumented acceptance quirks. Harvey and Gavel run BOTH (add-in for in-Word, server docx-service for web). Matches Spaarke's existing split (SPE/Word path vs web TipTap path).
