# Dataverse cascade-share / parent→child access (config-only + design landscape) — 2026-08-18

**Question**: Can CONFIG-ONLY Dataverse features make the "members" of a parent (sprk_matter/event/invoice/…) — owner, owning team, and sprk_assigned*/regarding lookup principals — access the parent's child sprk_todo records, incl. todos created AFTER the parent was shared? Plus the design landscape for a code-based "unified access-control cascade".

## The load-bearing distinction (answers the whole question)
Dataverse grants access ONLY from: ownership, security-role privilege depth, team membership, share (POA), hierarchy. **Being referenced by a lookup column (sprk_assignedto, sprk_regardingmatter, …) grants ZERO access.** Cascade/parental features only PROPAGATE access that already exists on the parent (ownership + POA shares); they cannot MANUFACTURE access for a lookup-referenced principal. So:
- **owner + owning-team of parent → child access (incl. future children): SOLVED config-only** via a PARENTAL relationship.
- **sprk_assigned*/regarding lookup principals → child access: NOT solvable config-only** — those principals have no access source on the parent to inherit; a share must be created in CODE.

## Part A — config-only options, verdicts
1. **Cascade Share vs Parental inherited access (the created-after timing crux).** Two DIFFERENT mechanisms:
   - **Share cascade action** = event-driven; fires only at the moment of a GrantAccess/share ON THE PARENT, cascading the POA share to children that EXIST at that instant. A child created later is NOT touched by this past event.
   - **Parental relationship inherited access (Reparent action)** = applied at child CREATE / lookup-set time. Learn (security-sharing-assigning §"Sharing and inheritance"): *"If a record is created and the parent record has certain sharing properties, the new record inherits those properties."* POA-storage doc canonical example: User1 owns Account1, shares to User2, **User2 creates Case1 under Account1 → User1 (parent owner) has access to Case1** via OOB Reparent=Cascade All. So a properly configured **parental** relationship (Reparent/Share = Cascade All/Active/UserOwned) DOES give a child created-after-share the parent's inherited access. The "created-after-share never inherits" folklore is TRUE only for a non-parental relationship relying on the one-time Share event.
   - Behavior presets (create-edit-entity-relationships): **Parental** = the actions in the Parental column set to Cascade All/Active/UserOwned; **Referential** = Cascade None (no access cascade, RemoveLink on delete); **Referential Restrict Delete** = Restrict; **Configurable Cascading (Custom)** = per-action mix. Only ONE parental relationship allowed per table-pair, and a related table can't be the "many" side of two cascade relationships (multi-parent forbidden) — matters for sprk_todo's ~11 regarding lookups: **at most ONE of the 11 can be parental.**
2. **Does cascade cover team-ownership / role access, or only POA shares?** Cascade Share action = POA shares only (incl. shares granted to a team). Parental inherited access covers parent OWNERSHIP too — RetrieveAccessOrigin origins include *"owner of a parent entity"*, *"member of team who is owner of a parent entity"*, *"poa access to object's root entity"*, *"member of team who has poa access to root"*. So owning-TEAM of the parent DOES inherit to children. **Security-ROLE/privilege-depth access to the parent does NOT inherit** (no "role access to parent" origin; role access is evaluated per-table). Confirmed the user's belief partially: team-ownership DOES cascade (via parental inheritance), role access does NOT.
3. **Access Team Templates (child sprk_todo): config-only for the TEMPLATE, but members do NOT auto-populate.** Template defines only the access rights granted + auto-creates a per-record system access team on first share. Members are added manually on the form subgrid or programmatically (AddUserToRecordTeam / AddMembersTeam). It will NOT pull the parent's members automatically → needs code/flow. So NOT a config-only solve for "parent members → child".
4. **Hierarchical security (Manager/Position): NOT relevant.** It's about the USER management/position hierarchy (manager sees subordinates' records), not the record parent-child hierarchy.
5. **Other config-only:** owning-team + business-unit scoping (put todos under a team/BU whose membership = the parent's members) can approximate it, but membership is not driven by the parent's lookups → still not "parent members" without code. No OOB feature reads a lookup column and grants access.

**Part A verdict**: The ONLY config-only win is a **parental 1:N relationship** on ONE chosen parent→sprk_todo path (e.g., sprk_regardingmatter→sprk_todo, Reparent+Share=Cascade All). It gives parent OWNER + OWNING-TEAM access to child todos incl. future ones. It does NOT cover: the other ~10 regarding lookups (multi-parent forbidden), sprk_assigned*/regarding lookup principals, or role-based parent access. Those require code.

## Part B — design landscape for a code-based "unified access-control cascade"
6. **Grant seams (all Web API actions, all callable app-only):** GrantAccess / ModifyAccess / RevokeAccess (manipulate POA share rows); AddUserToRecordTeam / RemoveUserFromRecordTeam (access-team membership) or AddMembersTeam (owner team). When to use which: **owning-team assignment** = cheapest at scale (1 POA-free membership grant covers all team-owned rows; membership changes are dynamic) — best when "members" map to a stable team; **explicit POA share (GrantAccess)** = precise per-(principal,record) but writes a POA row per grant → bloats; **access team** = per-record dynamic member list w/ template-defined rights, still 1 POA row per member per record. For "members of parent → each child" where the member set is derived from lookups, code must resolve the member set then GrantAccess (or add to a record access team) on each child.
7. **Plugin-free triggers (org uses NO plugins):**
   - **Power Automate cloud flow on sprk_todo Create** — easiest; Dataverse connector "When a row is added"; call Unbound action GrantAccess (or Perform-unbound-action). Latency seconds-to-minutes; throughput throttled (connector limits); reliability = flow run history + retry; simplest to build/own.
   - **Dataverse webhook → external service (BFF) on Create** — register a webhook/service-endpoint step (config, not plugin code) → BFF resolves members + calls GrantAccess via Web API. Lower latency, full control, better for high volume/batching, but you own the endpoint + retry/dead-letter. Fits Spaarke's BFF-centric model.
   - **Scheduled/batch reconciliation** — a timer job (Azure Function/BFF) periodically diffs parent membership vs child POA and reconciles. Most resilient to missed events + handles membership CHANGES on the parent (the gap flows/webhooks miss), but access is eventually-consistent (minutes-hours). Best as a SAFETY NET alongside a real-time trigger, and the only clean way to propagate parent-member REMOVALS to already-created children.
8. **Pitfalls:**
   - **POA bloat**: cascade/parental sharing + explicit GrantAccess write a POA row per (principal × record). 11 parent types × many todos × many members → POA explosion; Learn's dedicated mitigation = prefer TEAM ownership over per-user shares, minimize BUs, share to teams not users, lifecycle-manage/remove access-team members. Direct POA delete unsupported — must revoke via security model.
   - **Cascade-share perf**: sharing a parent with many children triggers async cascade jobs (cascadeAsync_Success/FailureAPI); large fan-out is slow + can fail mid-job.
   - **Created-after gap**: real ONLY for non-parental relationships or non-share access sources; a parental relationship closes it for owner/owning-team. Code triggers close it for lookup-principal shares.
   - **Sharing vs ownership**: sharing is additive-only, never restricts (see [[dataverse-record-access-security-2026-07-16]]); to REMOVE a member's child access you must revoke the SOURCE (share/team/owner), not add anything.
   - **Membership-change propagation**: adding/removing a parent lookup principal does NOT auto-propagate to already-created children — no OOB mechanism watches lookup columns. Real-time trigger handles ADD on child-create; parent-side membership edits + REMOVALS need an explicit re-sync (flow on parent update + reconciliation batch). Switching a relationship's cascade to None fires the async "inherited access rights cleanup" job (removes inheritance-only access, keeps direct grants).
