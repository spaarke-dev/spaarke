# The "third answer" for docx round-trip fidelity (2026-08-19)

**Question**: How do real products let a browser rich-text editor edit a .docx without destroying formatting/structure the editor cannot represent, and reliably save it back? Asked for Compose R8 after R4 (surgical byte-patch) and R6 (render-on-save from a thin model) both failed.

## Findings

**1. The decisive precedent is Word for the web itself.** Microsoft — with perfect access to the Word model — does NOT make its browser editor represent everything. Its own service description states that reference tools (bibliography, table of authorities, citations, index), ActiveX/OLE/signature lines, and watermarks "display in the document as expected in View mode. In Edit mode, they appear as **placeholders that you can delete but not edit or update**. They can't be moved or resized." Content controls: viewable, not addable. Captions: viewable, not editable. Restricted-editing/password docs: **refused into read-only** rather than risked. That is the opaque-atom pattern + a capability gate, shipped by the vendor of the format. This is the single strongest architectural sanction available.

**2. [MS-DOCX] paraId explains the R4 failure exactly, and it is a spec-conformance bug not a data bug.** Normative text: paraId is `ST_LongHexNumber`, "unique **within the document part**, **with the exception that it need not be unique across the choices or fallback of an Alternate Content block**". Value MUST be >0 and <0x80000000; Word generates it randomly (not required to). Three consequences that killed R4's anchor: (a) `mc:AlternateContent` legitimately duplicates the SAME paragraph twice (`mc:Choice Requires="wps"` DrawingML + `mc:Fallback` VML) with the SAME paraId — duplicate paraIds are SPEC-LEGAL; (b) "within the document part" means header/footer/footnote/endnote/comment parts each have their OWN paraId space — cross-part collisions are legal and expected, so a globally-keyed map is wrong by construction; (c) interior text boxes: `w:txbxContent` contains full nested `w:p` elements, so a naive `Descendants<Paragraph>()` walk interleaves text-box paragraphs with body paragraphs AND those nested paragraphs usually sit inside the AlternateContent pair, hitting (a) and (b) at once. Separately, Word regenerates paraId values on edit (Open-XML-SDK issue #925), so it is not a durable cross-session identity key at all. **paraId is a hint, never a primary key.**

**3. The named pattern is "grab bag" / opaque-node carry, and it is in production in three independent codebases.** LibreOffice's `InteropGrabBag` (writerfilter) is the documented, deliberate mechanism: unhandled OOXML properties are set aside on import rather than discarded and re-emitted on export; TDF describes it as "a documented part of the import filters rather than an incidental behaviour". EigenPal's DOCX Editor states it most directly: "**Unmodeled XML elements and attributes are kept as generic nodes and re-emitted in place**"; non-XML payloads (embedded fonts, VBA) pass through unchanged. Word for the web does the placeholder version. Documented failure modes: grab bag is **per-feature hand-wired** (nothing is preserved unless a developer wired that property), and cross-part consistency must be maintained as a triple — object properties in document.xml + `[Content_Types].xml` + `.rels` — Word only detects an embedding when all three agree (Igalia).

**4. Nobody achieves a lossless intermediate representation; everyone re-renders.** Apryse's 2026 taxonomy splits the field into native-OOXML editors (Apryse, ONLYOFFICE, LibreOffice) vs JSON/HTML editors (Nutrient DocJSON, Syncfusion SFDT, CKEditor 5, Tiptap, **SuperDoc**) — vendor-authored, so treat placement as directional, but the mechanism split is real. Syncfusion SFDT is a schema JSON re-model (their docs: no server-side SFDT→DOCX in DocumentEditor; track-change IDs are not preserved through SFDT→DOCX). Google Docs converts into its own native model — publicly loses equations, content controls, macros, advanced fields. OnlyOffice uses a real C++ engine (`x2t`) with its own internal format, AGPL/commercial, no published internal-model docs. Docugami/Litera have no public engineering writeups; HotDocs sidesteps the problem entirely by running **inside** Word.

**5. Conclusion for Compose: R6's mechanism was right, its model was too thin.** Render-on-save is what essentially every shipping editor does. Do not return to surgical byte-patching (R4) — anchor reconciliation against live Word output is precisely the thing that has no stable identity to reconcile against. The fix is to widen the canonical model with a first-class **opaque carry** at four granularities: (i) block-level opaque atom = verbatim XML subtree, rendered as a non-editable, non-movable, deletable placeholder (Word-for-the-web semantics); (ii) inline opaque atom (fields, `w:sdt`, `w:drawing`/`w:pict`, footnote/endnote refs); (iii) property grab bag — unmodeled children/attributes of `w:pPr`/`w:rPr`/`w:sectPr`/`w:tblPr` carried verbatim; (iv) part-level passthrough (already done). Plus a **capability gate** that refuses to open into edit mode when the document exceeds the model, falling back to read-only — refusing is a feature, not a failure.

**6. .NET library landscape under permissive-only licensing: nothing new will save you, but Clippit is worth taking.**
- `DocumentFormat.OpenXml` — MIT, dotnet/Open-XML-SDK, very active (pushed 2026-08-18, 4.6k stars). Stay.
- **Clippit** (sergey-tihon) — **MIT, actively maintained** (pushed 2026-08-16, 69 stars, 5 open issues). The living successor to Open-XML-PowerTools; carries `DocumentBuilder` and `WmlComparer`. The only genuinely useful permissive addition.
- `Codeuctivity.OpenXmlPowerTools` — **MIT** (GitHub reports NOASSERTION only because `LICENSE.md` starts with a markdown heading; the text is verbatim MIT, Copyright Microsoft). Active (pushed 2026-08-19).
- `OfficeDev/Open-Xml-PowerTools` — MIT but **ARCHIVED since 2019-02**. Study only, never a dependency.
- Aspose.Words (~$1,175+/dev), Syncfusion DocIO (Essential Studio only), GemBox.Document, Spire.Doc — **all commercial per-developer**, excluded by NFR-03. None of them solve the editor round-trip problem anyway; they are server libraries with their own wide models, i.e. you would still be re-rendering.

**7. Verification practice.** `OpenXmlValidator` (schema + semantic) is necessary but insufficient — the dominant real failure mode is "schema-valid but silently rewritten/repaired by the target app". The shipping practice (EigenPal, and Compose R6 FR-08 already) is a **parity corpus of real documents round-tripped in CI and compared structurally**. Normalization for comparison must strip `w:rsid*`, `w:proofErr`, bookmark ids, remap `numId`/`abstractNumId`, ignore attribute order and namespace-prefix choice, and coalesce adjacent runs with identical `rPr`. Run comparison at two levels: a *lenient* level that ignores identity attrs (paraId/textId) to detect content loss, and a *strict* level that does NOT, to detect identity drift. The only true gate is "Word opens it without the repair dialog" — approximate in CI with headless LibreOffice and/or a Word-Online smoke.

## Open questions
- Does Word ever renumber paraId for paragraphs it did NOT touch? #925 suggests wholesale replacement on some edits; not confirmed as a rule.
- EigenPal's "generic nodes" schema shape (how a ProseMirror-family schema declares a catch-all node without violating strict-schema validation) — not published; needs a code read of a permissive fork.
- Whether adding a Spaarke-owned identity attribute to `w:p` (registered via `mc:Ignorable`) survives Word desktop round-trips — untested, and it is the natural replacement for paraId-as-key.
