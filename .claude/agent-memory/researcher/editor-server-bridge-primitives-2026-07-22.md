# Editor↔server-OOXML bridge primitives — permissive prior art (2026-07-22)

**Question**: For a legal editor where server OOXML is source of truth and TipTap/ProseMirror is a lossy view, what permissively-licensed (MIT/Apache/BSD, NOT AGPL) prior art exists for the bridge — stable-ID anchoring, operation schema, position rebasing, offset→structure mapping, .NET surgical OOXML patch? Six technique families.

**Verified facts (GitHub API + official docs, 2026-07-22)**:

1. **ProseMirror transform primitives — MIT.** `prosemirror-transform` + `prosemirror-changeset` + meta `prosemirror` repo were **archived on GitHub Apr 7 2026 — but this is a mirror move, NOT abandonment**: dev relocated to self-hosted forge code.haverbeke.berlin; NPM packages remain MIT + maintained. Primitives to borrow: `Step`/`ReplaceStep`/`ReplaceAroundStep` (invertible atomic ops), `StepMap` + `Mapping` (position rebasing through concurrent edits via `map(pos, bias)` + `mapResult` with `deleted`/`deletedAcross`), `Transform.invert()` (undo/reject), `prosemirror-changeset` (groups steps into a minimal insert/delete changeset for redline diffing), decorations + `Transaction.setMeta` for non-doc annotations. This is the client bridge layer. Pitfall: ProseMirror positions are absolute token offsets — they DIE across server round-trips; must re-anchor to stable IDs, not persist raw positions.

2. **Stable-block-ID editors — Slate + Lexical both MIT, active.** Slate (ianstormtaylor/slate, MIT, 31k★, active) has the cleanest studiable op schema: 9 operation types as `{type, path, offset/position, properties}` discriminated union (insert_text/remove_text/insert_node/split_node/merge_node/set_node/move_node + set_selection); `Path.transform(path, op)` is the path-rebasing primitive (direct analog of StepMap for a tree). Lexical (facebook/lexical, MIT, 23k★, active) uses stable NodeKeys + reconciler. Notion is closed (no repo) — pattern only. **Borrow Slate's `{type, path, offset}` op shape + Path.transform as the model for our `{op, paraId, offset}` schema.** Pitfall: Slate paths are positional (array indices) — they rebase within a session but are NOT stable identities across reload; our paraId (w14:paraId) is the durable key Slate lacks.

3. **OOXML-as-truth / editor-as-projection — Eigenpal docx-editor. ⚠️ MAJOR CORRECTION (verified 2026-07-22, primary sources).** EigenPal (eigenpal.com, GitHub org `eigenpal` created 2025-11-26) is a **workflow-automation / agent company** (repos: cli, sdk-typescript/python, PageIndex RAG, redb); docx-editor is a **peripheral OSS artifact**. There are TWO distinct things and my initial memo conflated them:
   - **(a) The NEW official repo `eigenpal/docx-editor`** was **CREATED 2026-07-20 (2 days before I first read it — NOT "back again")**, ~6 commits all one day, one human author (jedrazb / npm maintainer `eigenpal-jedr`). Its `packages/core` is literally named **`@docx-editor.dev/core-contract`**, `"private": true`, self-described "**Not the implementation; never published**"; `core/src/index.ts` says "**CONTRACT ONLY. Every function here throws**" — `parseDocx`/`serializeDocx`/`toJSON` are stubs that reject. The 225 OSS `.ts` files are React/Vue UI shells + type contracts + docs; **the OOXML parser/serializer/layout engine is CLOSED-SOURCE.** npm `@docx-editor.dev/core` publishes only `0.0.1-placeholder`, ~306 downloads/mo. This is an **open-facade / closed-engine commercial product** ("Commercial support: docx-editor@eigenpal.com"). **NOT adoptable or vendorable — the hard part is not in the repo.** My "study its core parser/serializer" advice was WRONG for this repo.
   - **(b) The OLD `@eigenpal/docx-editor-core` v1.9.0** — the real, complete Apache-2.0 implementation that existed BEFORE EigenPal pulled it ~June 2026. Survives ONLY in third-party forks: `sorenlouv/docx-editor` (Apache-2.0, created 2026-06-15, frozen 2026-06-29), npm `@sqren/docx-editor` v1.0.3 (~689 dl/mo), `mhurhangee/docx-editor`, `@heyirisai/*`, `@zeke-02/*`. This fork DOES contain the real engine: `packages/core/src/docx/{documentParser,paragraphParser,runParser,numberingParser,commentParser}.ts` + full `serializer/` dir. **This — the frozen, abandoned, forked v1.9.0 — is the only permissively-licensed, studiable, potentially-vendorable Eigenpal artifact.** Byte-preserving/dual-renderer claims (twips layout painter, only-reinterpret-edited-spans, unmodeled parts round-trip; fidelity docs are specific down to naming non-preserved VML `v:rect`/`v:line`) are substantive and documented — those docs live in repo (a), the matching code lives in fork (b).
   - **Bottom line**: "Track B = Eigenpal + Docxodus" as an ADOPT-a-library plan is DEAD. Salvage path = vendor the **frozen Apache-2.0 v1.9.0 fork** (own it yourself, unmaintained) and/or study its parser/serializer as a DESIGN reference — which collapses Track B toward "**Docxodus (server, MIT, active) + build-our-own projection, seeded by the dead v1.9.0 fork**". SuperDoc remains AGPL/commercial (patterns only).

4. **CRDT position anchoring — all MIT.** Yjs (yjs/yjs, MIT — GitHub shows NOASSERTION only because LICENSE has extra copyright header; text is verbatim MIT) `RelativePosition` = position defined relative to a specific character's unique ID that survives concurrent inserts/deletes; `y-prosemirror` (MIT) binds it to PM. Automerge (MIT) `Cursor` = same concept. Peritext (inkandswitch/peritext, MIT, research ref impl, frozen 2022 but studiable) = the canonical essay on stable rich-text anchoring under concurrent edits. **The "relative position that survives edits" concept is directly transferable to paraId+offset even WITHOUT adopting a full CRDT** — a paraId is a coarse RelativePosition anchor; offset-within-paragraph is the fine anchor. Pitfall: raw char-offset within a paragraph still shifts if another edit lands earlier in the same paragraph — need intra-paragraph re-anchoring (run index or a stable inline marker), which is exactly what CRDT relative positions solve and naive offsets don't.

5. **Editor↔server incremental sync — LSP `textDocument/didChange` (spec, MIT-ish/CC-BY).** LSP's `TextDocumentContentChangeEvent` = `{range: {start:{line,char}, end:{line,char}}, text}` ranged incremental edits against a server-canonical text model; client sends ranged deltas, server patches its authoritative copy, version numbers guard ordering. **Transferable framing: our editor sends ranged ops keyed by paraId (the stable "line" analog) + intra-paragraph offset (the "character" analog); server applies to canonical OOXML; a version/etag guards races** (mirrors SPE If-Match etag from openxml-docx-compose-r2 memo). Pitfall: LSP ranges are (line,char) into flat text — OOXML has no flat char stream; must define paraId+run-offset as the coordinate system, and the mapping is non-trivial (runs split styling mid-paragraph).

6. **.NET server-side OOXML surgical patch — MIT.** `dotnet/Open-XML-SDK` (MIT, active) for split-run-at-offset + inject w:ins/w:del. For diff→native-redline: `OpenXmlDev/Open-Xml-PowerTools` (MIT community fork, active — the OfficeDev original is archived 2019) WmlComparer; `Codeuctivity/OpenXmlPowerTools` (MIT, active) is the .NET8 maintained fork. **NEW high-value find: `JSv4/Docxodus` (MIT, active pushed 2026-07-21) = "Office XML Redline Engine Based on OpenXML SDK, forked from OpenXMLTools"** + `JSv4/react-docxodus-viewer` (client-side WASM redline render) + `JSv4/Python-Redlines` (MIT, 119★, wraps the PowerTools comparer binary). Docxodus is the most directly studiable .NET-first redline engine. Canonical technique for "locate para by w14:paraId → split runs at char offset → wrap in w:ins/w:del without corrupting package": walk to the `w:p` whose `w14:paraId` matches; walk runs accumulating text length until offset falls inside run R; `Run.Clone()` split R into R_before/R_after preserving `RunProperties`; wrap inserted content in `InsertedRun` (w:ins) and deleted in `DeletedRun` (w:del) with Author/Date/Id; NEVER edit `document.xml` as a string — mutate the OpenXml DOM and let the SDK reserialize. Pitfall: paragraph-mark deletions (merging paragraphs) require w:del on the paragraph-mark glyph inside `w:pPr/w:rPr` — hardest edge case; and numbering (numbering.xml) is a separate part not inline (per server-docx-authoring-numbering memo).
