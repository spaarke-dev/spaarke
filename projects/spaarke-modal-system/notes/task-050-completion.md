## Deviations / escalations

No escalation trigger fired — all three forms fit `md` without clipping fields or footer; the mid-size unification held for all three as owner-locked. Two deliberate, transparently-documented deviations and one out-of-scope discovery:

1. **`PinnedMemoryEditDialog` does NOT wire `FormModal`'s `busy`/`submitDisabled`.** `Spaarke.UI.Components`'s compiled `dist/` (the type boundary `Spaarke.AI.Widgets`' own `tsconfig.json` resolves `@spaarke/ui-components` against for its `npm run build`) predates the P3 `FormModal` consolidation that added `busy`/`submitDisabled`/`cancelLabel`/`dismiss` (confirmed empirically: I first wrote `PinnedMemoryEditDialog` WITH `busy`, ran `npm run build`, and got `TS2322: Property 'busy' does not exist on type 'FormModalProps'` — direct proof of the staleness, not just a theory; `src/…/FormModal.tsx` mtime is newer than `dist/…/FormModal.d.ts` mtime). Per this wave's explicit build discipline (do NOT rebuild that shared `dist/` from this task — a sibling agent, task 051, is concurrently editing the same package), I removed `busy` rather than force a rebuild. The pre-existing `isSubmitting` re-entrancy guards inside `handleCancel`/`handleSubmit` (both unchanged) still fully prevent a duplicate POST/PUT — only the VISUAL disabled/spinner affordance during the in-flight window is deferred; the Save label still swaps to "Saving…". Rewrote the one test that asserted `.toBeDisabled()` into a functional guard assertion (click while `isSubmitting` → `onSubmit` not called again) instead of weakening coverage. `NewThreadModal` (same-package as `FormModal`, no dist boundary) freely uses `busy` with full visual parity — this asymmetry is intentional and explained inline in `PinnedMemoryEditDialog.tsx`'s render. **Revisit**: once the main session's end-of-wave `dist/` rebuild lands (mirrors the Wave-P2 precedent), `busy` can be added back to `PinnedMemoryEditDialog` for full visual parity — a one-line follow-up, not a design gap.
2. **`QuickStartModal`'s footer has no natural "submit."** It's a 7-card/3-card picker — every card click self-launches and closes (`handleCardClick`/`handleAnalysisCardClick`, unchanged). `FormModal` always renders both a Cancel (secondary) and a primary (Save-slot) button — there's no prop to omit the primary. Wired Cancel→`onClose` (label "Cancel") and the primary→`onClose` as well (relabeled "Close") — both close without picking anything; documented in the file's own JSDoc as a deliberate wiring choice for a footer-shape/content-type mismatch, not a `FormModal` preset gap. Also: the new `md` surface (up to `1040px×720px`/`72vh`) is larger than the old fixed `720×720px` box; the inner `styles.content` (fixed `460px` height, preserved to keep the Create/Analysis tab panels visually consistent with each other) now sits inside a bigger frame, leaving more surrounding whitespace — a cosmetic consequence of unifying to the shared `md`, not a functional one.

Neither is fixed here (out of this task's declared output scope: `NewThreadModal.tsx`/`QuickStartModal.tsx`/`PinnedMemoryEditDialog.tsx` only); flagging here for the main session to route to `notes/defer-issues.md` / a GitHub Issue per the project's deferral process.
