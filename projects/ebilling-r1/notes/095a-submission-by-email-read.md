## 3. The 503 rule (changed from the POML)

The POML said a rights-read fault is 404. uac-r2 replaced it: **any read fault is 503, including a failed rights read.** Built that way: `HoldsReadAsync` asks the caller-scoped snapshot itself (`AuthorizationService.GetCallerRecordAccessAsync`) and, when the snapshot carries no Read and is `Faulted`, throws the route's 503 (`ebilling.submission.record_unavailable`); a thrown rights read, the .eml or attempt query, the submitter-name read and "more than 50 candidates, none readable" are the same 503. `FinanceAuthorizationFilter.CallerHoldsRightsAsync` was not used because it discards `Faulted` (a Faulted snapshot with no Read becomes "false", which would answer the not-submitted 404).

The filter's own refusals (the step-0 flag read, the pre-gate table privilege) were first left on the shared uniform 404 (K1 of the first review log). The adversarial review (F1, section 9) found that the uac-r2 requirement covers them too: the route must never answer the no-match 404 when it could not decide. The route's filter now runs in `FinanceDenial.UniformNotFoundFailClosed`: a refusal that is a system failure (a step-0 flag-read or lookup fault, a thrown check, an OBO, WhoAmI or privilege-read fault) is the same 503 `ebilling.submission.record_unavailable`; a genuine denial (the privilege not held, an external caller, no systemuser row) stays the uniform 404.

### F1 - the route never answers the no-match 404 when it could not decide (uac-r2 binding)

Before: a step-0 flag-read or lookup fault, and a pre-gate table-privilege read fault (OBO, WhoAmI, `RetrieveUserSetOfPrivilegesByNames`), were mapped by `FinanceAuthorizationFilter` to the shared uniform 404 (`FinanceDenial.UniformNotFound`), so the add-in would show "not submitted" for an email that was submitted. After: 503 `ebilling.submission.record_unavailable` for every fault; the 404 stays for a genuine denial (no privilege, an external caller, no systemuser row).

- `CallerRecordAccessProbe.CallerPrivilegeAnswerAsync` (new, `Infrastructure/ExternalAccess/CallerRecordAccessProbe.cs`): the three-state answer `CallerPrivilegeAnswer { Held, NotHeld, Faulted }`. `CallerHoldsPrivilegeAsync` is now `answer == Held`, so every other caller of it is byte-for-byte the old behaviour (a fault is false). Faulted: no token, no OBO or environment URL, a failed exchange, an unresolved caller, a non-success response, an exception. NotHeld: Dataverse answered and the privilege is not listed.
- `FinanceDenial.UniformNotFoundFailClosed` (new, opt-in) in `Api/Filters/FinanceAuthorizationFilter.cs`: the privilege check asks the three-state method; `Deny` renders `InvoiceSubmissionHttp.ReadFault(InvoiceSubmissionService.ReadUnavailable())` for `SystemFailureReasonCode` and the uniform 404 for any other reason. Every other route keeps `UniformNotFound` or `Forbidden` unchanged. The by-email route (`InvoiceSubmissionEndpoints.cs`) is the only user. The filter now references `Api.Finance.InvoiceSubmissionHttp` and `Services.Finance.Submission.InvoiceSubmissionService` (one new dependency of a filter on a route-file helper, for the shared 503 body; no cycle).
- `ExternalPlaneNoOboGuardTests` forbids `CallerPrivilegeAnswerAsync` on the external plane as it does `CallerHoldsPrivilegeAsync`.
- The Record path of the filter (not used by this route; the handler asks the snapshot itself) still reads a Faulted snapshot with no Read as a denial; reported, not changed (other routes).
- Tests (`InvoiceSubmissionByEmailContractTests`, `CallerPrivilegeCheckTests`): probe Faulted gives 503; probe throws gives 503; step-0 `FlagReadFault` and `LookupFault` give 503 with nothing read and the privilege never asked, and the same caller once healthy is a 200 (control); no table Read gives the uniform 404 naming nothing; step-0 `FlagTrue` and `NoSystemUserRow` give the uniform 404.
