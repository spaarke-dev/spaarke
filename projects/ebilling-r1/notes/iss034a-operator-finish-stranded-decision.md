# ISS-034 (#2888), task iss034a: an operator route that finishes a stranded blocked Override or Return as recorded

> **Task:** `tasks/iss034a-operator-finish-stranded-decision.poml` (FULL) · **Decision:** EB-D-244 (owner, option 1) · **Base:** `task/ebilling-iss034a` from 3ff10e65a4 (`origin/work/ebilling-r1`) · **Status:** built and tested; review round 1 fixed on `task/ebilling-iss034a-r1` (see "Review round 1" at the end). Code-review, adr-check and the adversarial pass are for the coordinator.

## The defect

A blocked submission's Override (or blocked Return) can write its Decision Record and then fail before it finishes (release, closes, transition or submission write). Since 095f-2c only the stored decider can finish it by repeating it, and since ISS-031 the other verb is refused `other_decision_pending`. When the decider cannot return, the invoice stays held for good.

### The route's order of checks

1. Route filter, as the caller: Read and Write on the submission (`ebilling.submission.decide`); then the eBilling kill switch.
2. The caller is resolved (`systemuserid`) and the **billing-admin marker** is asked as the caller (`CallerHoldsPrivilegeAsync` for every check of `AdminMarkerChecks()`, all of which must hold; a declared check that is not a table privilege fails closed). No caller, a "no", or any fault: **403 `ebilling.blocked.operator_not_permitted`**. Nothing about the submission has been read.
3. The operator's reason (400 `ebilling.reason_required` / `ebilling.reason_too_long`) and note (400 `ebilling.note_too_long` / `ebilling.note_invalid_characters`), by the decisions' own code.
4. The submission is read (404 `not_found`, 503 `unavailable`).
5. The stranded verb, derived server-side (`StrandedVerbAsync`):
   - submission Overridden: Override; Returned: Return (a finished decision; step 7 answers it as a repeat);
   - Blocked or Procedure-held: the invoice must be the one the submission created (409 `invoice_not_held`), then both writer-created records are looked up through `_findStored` (`OverrideDecisionIdFor` / `ReturnDecisionIdFor`): neither, **409 `ebilling.blocked.nothing_stranded`**; both, **409 `ebilling.blocked.both_decisions_recorded`** (review round 1; needs support); a writer refusal maps as `RecordRefusal` (the real lookup wraps every fault this way: 503 `record_unavailable`), any other fault **503 `unavailable`**; exactly one, that verb;
   - any other state: the refusal a decision gives (`not_internal`, `submission_failed`, `already_accepted`, `still_processing`, `not_blocked`).
6. For an Override, the **eBilling Override privilege** (`EbillingOverridePrivilege.HoldsAsync`, fail closed): **403 `operator_not_permitted`**.
7. From here it is the decision's own code path: `Refusal` (a finished decision answers **200 `alreadyDecided`** with the existing column repair and Signal re-close, and no operator record), the invoice link checks, the invoice lock (`LockKey`, 409 `in_progress`, 503).
8. Under the lock (`DecideLockedAsync`), unchanged: the re-read, `Refusal`, the invoice state, the stored findings, the same verb's lookup, the Signal set, **the FR-51 close rights asked as the operator (403 `not_authorized`)**, the ISS-031 other-verb guard (409 `other_decision_pending`).
9. New, operator only: the stranded record must still exist (409 `nothing_stranded`); the caller must not be its decider (**409 `ebilling.blocked.own_decision_pending`**, review round 1, detail `OwnDecisionDetail`: repeat your own decision; no operator record); the record must name a decider (503). From here `decider` is the **stored decider**.
10. Unchanged: the record's readability (503), the stored reason and note replace the request's, the firm gate (409 `ebilling.override.firm_missing`, 503), the invoice's row version (503), the holds derivation (503).
10b. Review round 1 (F4), every decision: the stamp must fit the findings column (409 `findings_too_large`), checked here, before the set's store, the Decision Record, the operator record and the Signal closes. The check after the closes stays as a backstop.
11. New, operator only: the submission's row version is checked (503), then **the operator record** (`RecordOperatorFinishAsync`): preflight (400 `decision_invalid`), then a lookup of this operator's decision id (one per submission, verb and operator): found, reused (no write); not found, written through `BillingDecisionRecorder.RecordAsync` → `DecisionRecordWriter.WriteBillingDecisionAsync`. A writer refusal maps as `RecordRefusal`; a fault is 503 `record_unavailable`.
12. Unchanged: the Signal closes (the first write of the finish; under the stored record and the stored decider), the Return transition, the stamp (stored reason, stored decider, stored record), the release transaction (stored note or reason in `sprk_decisionnote`), the re-index, the notification.

The response is the decision's: `Outcome` and `RecordId` are the finished decision's (A's record), as the decider's own repeat answers.

### What the finish keeps from the original decision

The stored reason, note, Signal set and decider (`recordedSet.ConfirmedByUserId`): the stamp's `bySystemUserId`, the holds derivation's provisional stamp and every Signal close credit the stored decider, and the column, stamp and transition hold the stored text. The operator's reason and note go only on the operator record.

### The operator record

`finish-stranded-decision`, subject the invoice (`BillingSubjectEntityOf` maps every non-line code to the invoice), `ConfirmedBy` the operator (role "billing admin finishing another person's recorded decision"; the contact is looked up by the recorder, K3), reason the operator's, outcome `FinishRequested` (review round 1: the record is written before the finish's writes, which can still fail or be completed by the decider's own repeat, so it never claims the decision finished), values `finishedDecision` (`override-submission` / `return-to-firm`), `finishedRecord` (the finished record id), `submissionId`, and `note` only when given (no null key). It resolves no Signal (the finished decision's record does). Facts: the decision, the submission, the finished decision, record and decider. Decision id `IdOf("ebilling-operator-finish-{submissionId:D}-{override|return}-{operatorId:N}")`, so one per submission, verb and operator (review round 1, F1).

## Component justification (CLAUDE.md section 11)

- **New route** (`POST .../finish-stranded`). Existing: the override and return routes. Extension: they cannot serve it, because they answer for the caller's own decision (`decision_conflict` for another person's, by the 095f-2c rule the owner kept) and take the verb from the path, while this one derives the verb and needs its own authority and its own record. Cost of doing nothing: a stranded decision whose decider is gone holds its invoice for good (ISS-034).
- **New service method** `FinishStrandedAsync`. It is a flag on the existing `DecideAsync` / `DecideLockedAsync`, not a copy: the same lock, re-read, refusals, firm gate, holds derivation, closes, release, transition and notification.
- **New catalog code** `finish-stranded-decision`. Existing: `override-submission` and `return-to-firm`. Extension: they are the decider's records and must stay the decider's (append-only, and the trail must show who decided and who finished, EB-D-244). Cost of doing nothing: the finish would leave no record of the operator.
- **New view fields** `StrandedDecision`, `CanFinishAsOperator`. Existing: `CanOverride`, `CanReturn`, the stamps. Extension: none tells the client a decision is stranded or who may finish it. Cost of doing nothing: iss034b cannot offer the action without guessing.

## Decisions made where the POML could not be followed literally

- **New codes (superseded in review round 1).** The first build reused `decision_conflict` and `other_decision_pending` for "the caller is the stored decider", "another operator's finish has not completed" and "both records". Review round 1 gave the route stable codes of its own: `ebilling.blocked.own_decision_pending` and `ebilling.blocked.both_decisions_recorded`; the another-operator case no longer exists (F1). The override and return routes keep their codes.
- **A finished decision answers 200 `alreadyDecided`.** The POML says "as today's repeat (already_overridden / already_returned, ...)". Today's repeat of the SAME verb answers 200 `alreadyDecided` (the codes named are the OTHER verb's answers), and only that answer runs the column repair and re-close the POML asks for, so the operator route takes the finished verb and answers as its repeat. For a finished Override the operator must still hold the Override privilege (fail closed: 403 otherwise).
- **"The submission's row version" before the operator record.** The decision path checks the submission's row version only after the Signal closes. For the operator finish it is also checked before the operator record (an extra check, no extra read), so that refusal cannot follow the record.
- **A repeat of an interrupted finish reuses the operator record only for the same operator; another operator writes their own (review round 1, F1).** The record's decision id carries the operator, so the same operator's repeat finds it and completes with any text (as a decider's repeat does), and another operator writes a record of their own and completes the finish.
- **The operator record's lookup and write share one fault answer**: 503 `record_unavailable` ("Nothing was changed. Try again."), not `unavailable`.

## Known limits

- **K1 (removed in review round 1).** An interrupted operator finish no longer belongs to its operator: the operator record is one per submission, verb and operator, so if operator B's record is written and B's finish then faults and B leaves, operator C writes C's own record and finishes (tested: `AnInterruptedFinish_IsCompletedByASecondOperator_WithTheirOwnRecord`), and the decider's own repeat still finishes too, leaving B's record as written (`AfterAnInterruptedOperatorFinish_TheDecidersOwnRepeatFinishes_AndTheOperatorRecordStays`). The trail then holds one record per operator who asked, each with outcome `FinishRequested`; the finished decision's stamp and state say it finished.
- **K2: refusals that can still follow the operator record.** After the operator record, the finish can still stop at the same points the decider's own repeat can: a Signal close that fails (503; the repeat re-closes), the release's version conflict after the bound (409 `concurrent_change`), the lifecycle refusing the transition. In each case the operator record stays and a repeat of the operator route (by the same operator, another operator, or the decider) completes it (tested for the release and the transition). The stamp not fitting the findings column is no longer among them: since review round 1 it is checked before any write.
- **K3: the GET hints cost Decision Record lookups** on every read of a held submission. Since review round 1 the two lookups run together (one wait, not two), and the hint reuses `canOverride`'s Override privilege answer instead of a second probe. The hints are read-only; the POST still decides. A lookup fault drops the hints and the view still loads.
- **K4: a stranded decision whose record names no decider** cannot be finished (503, nothing written; tested since review round 1): a human record always names one (K3 of 074), so this is a corrupted record, not a reachable state.
- **K2-class, unchanged by this task:** close rights apply when the decision closes Signals; the route filter's Read and Write on the submission always apply (095f-2c, ISS-031 notes); the operator finish inherits this.

- **K5 (second verifier pass, finding 1) — fixed by iss034c (EB-D-253): the trail records who asked to finish, not who completed.** Since the operator record is keyed per operator, AC3's "exactly one operator record" holds per operator, not per decision. Each operator who tried leaves one `FinishRequested` record, and nothing names who completed the finish: a later operator, or the decider's own repeat. The submission's state shows that it finished. Shown to the owner for acknowledgement (EB-D-244 reads per operator).
- **K6 (second verifier pass, finding 2): data written before this fix can stay stranded.** Before the pre-write stamp-size check, a decision could write its record and close its Signals, then be refused `findings_too_large`. A submission left in that state is refused 409 on every route, fail closed with nothing written. New decisions cannot reach it, but existing data needs support. The read-only dev scan for 084h-5 found no duplicate keys; it did not look for this state.
- **Test-harness note (second verifier pass, finding 4):** `WithDistinctCreateIds` is switched on in the shared SubmissionOverride World, so it applies to all seven SubmissionOverride suites, not only the new ones; all pass. It sets `Entity.Id` on the created entity, which the real SDK does not. That is harmless, because the writer uses the id the create returns.

## Disabled decider (question from uac-r2)

"Their decider is gone" usually means a disabled `systemuser`. The finish credits the stored decider everywhere; every place it does, from the code (line numbers at the review round 1 tip):

**Finding: no write of the finish depends on the decider being enabled**, so nothing was changed for it. The finish never assigns ownership to the decider and never sends the decider a notification; the only systemuser lookup that names the decider is `sprk_resolvedby`, which Dataverse accepts for a disabled user. Pinned by `AFinish_NamesTheDeciderOnlyAsALookupAndInTheStamp` (both verbs, with Signal closes): the closes credit A; no submission write, release transaction or invoice write carries an `EntityReference` to A; the operator record carries no lookup to A; the notification type has no person member. It passes before and after this round (a characterization, not a fix). A double that refuses the decider cannot be added where it would bite, because no write sends the decider anywhere a refusal could come from. Not verified against a live disabled user.
