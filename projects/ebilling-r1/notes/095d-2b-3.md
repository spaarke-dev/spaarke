**Before and after (the extraction).**
- Before: `internal async Task<Guid?> FindSupersededInvoiceAsync(Guid submissionId, Guid invoiceId, SubmissionSnapshot submission, InvoiceCoreRecord core, CancellationToken ct)`, an instance method over `_entities` and `_logger`.
- After: `internal static async Task<Guid?> FindSupersededInvoiceAsync(IGenericEntityService entities, ILogger logger, Guid submissionId, Guid invoiceId, SubmissionSnapshot submission, InvoiceCoreRecord core, SupersedesRerunNarrowing? rerun, CancellationToken ct)`. The persister calls it with `(_entities, _logger, ..., rerun: null, ct)`; the re-run calls it with `new SupersedesRerunNarrowing(invoice createdon)`.

**When the re-run looks a predecessor up** (all must hold):
- the submission is New (`ResubmissionOfSubmissionId` is null);
- the evaluation's outcome is not `AutoRejected`. The check runs before `HeldInsteadOfRejected`, so a would-be rejection held for review (R5) is not linked, as the persister links no automatic rejection;
- the invoice has no `sprk_supersedesinvoice`;
- the submission has its firm.

**The narrowings (re-run only).**
- (a) Candidates are invoices created before this one: `createdon`, then the id in Dataverse's uniqueidentifier order (`SqlGuid`), the same order the query sorts by. The filter is applied in memory, after the unchanged query and before the walk-back, so a later automatic rejection or a later resubmission never decides the chain.
- (b) After the walk-back and the core check, a predecessor that another invoice names in `sprk_supersedesinvoice` is not linked. That is `SubmissionCommitGate.SupersededByAnotherAsync`. The re-run's invoice has no link yet, so any row found is another invoice. It logs ids only, at Information.

**Escalation triggers: neither fired.**
- (1) The re-run's commit is one `ExecuteTransactionAsync` in which every row, the invoice included, is `IfRowVersionMatches` (`BuildPlan`, `CommitAsync`). The link rides on that invoice update.
- (2) No legitimate flow was found with two live invoices that should both supersede one predecessor.
  - At create time, the persister's walk-back gives a predecessor at most one successor. After B links A, a later C finds B as the most recent earlier invoice (not Returned), unless B is itself Returned, in which case C links B.
  - A Correction (097c) targets an In Review invoice, never a Returned one.
  - The case (b) refuses: a firm-less X is created, then B is created with the firm and links A, then Set firm runs on X. Under the create-time rule exactly one of X and B is A's successor (X, had its firm been known). B already holds the link, and EB-D-206 keeps it with B. That is "which one", not "both".

## 4. Known limits

- **K2: race on the predecessor.** The link is decided from reads made before the commit. The commit conditions on this invoice's version, not on the predecessor's. Suppose another invoice takes the same predecessor between this run's read and its commit. That needs two firm-less submissions of the same firm and number whose Set firm re-runs overlap. Then both can link it. The persister has the same read-then-commit shape. L8 shows that a change that also moves this invoice's version is re-decided.
- **K2: order of Set firm.** With two firm-less submissions of one firm and number, the one whose re-run commits first takes the predecessor, and narrowing (b) refuses the other. The create-time rule would have picked the earlier-created one.
- **K2: missing createdon.** An invoice with no `createdon` (Dataverse always sets it) fails closed. On the re-run's own invoice it is `Failed`/`Unavailable`. On a candidate it is a read fault (`supersedes_read_failed`). Either retries until it dead-letters, with nothing written.
- **Test scope.** Exactly L1-L8 (with their controls) and the two seeds. The three harness lines above are fixtures, not tests.

## 7. Review fix round (after the adversarial review)

Binding decision: EB-D-206 as amended on 2026-11-07 (the amended row is copied unchanged into this branch's `decisions-log.md`).

### 7.1 F1: narrowing (c), the Return must predate this invoice

- **Before:** narrowing (a) dropped later invoices, but "Returned to Firm" was read at re-run time. An invoice X sent while P was still In Review was linked to P once P was later returned.
- **After:** on the re-run only (`rerun != null`), after the walk-back and the core check, P counts only if its Return to Firm was decided strictly before X's `createdon`. No Return record: no link, Warning with the submission and predecessor ids only. A read fault throws, and the re-run answers `Failed` / `supersedes_read_failed`, as for the lookup.
- **Where the Return time comes from.** The Return's own Decision Record (D-75: one per invoice decision, filed under the invoice):
  - Both Return routes record `return-to-firm` under the invoice through `BillingDecisionRecorder`. Return of the invoice is `InvoiceRejectReturnService` (decided-on is the server clock cut to the second, `InvoiceRejectReturnService.cs:466`, taken before the claim and the status move; recorded at `:678`). Return of a blocked submission is `SubmissionOverrideService` (`ReturnActionCode`, `:310`; no decided-on passed, so the writer's clock).
  - The writer stores it in `sprk_decidedon` (`DecisionRecordWriter.cs:2966`, from the request or the writer's clock; never a value a firm supplies).
  - The read is `InvoiceSubmissionPersister.ReturnDecidedOnAsync`, app-only. It reads `sprk_decisionrecord` where `sprk_regardinginvoice` = P and `sprk_actioncode` = `return-to-firm`, the latest by `sprk_decidedon` then `createdon`, top 1. It uses `sprk_decidedon`, else `createdon`. A record with neither throws (a retry).
- **Strictly before.** decided-on is cut to the second, so a Return in the same second as X's create is not known to precede it, and gives no link (L9 `SameSecond`).
- **Known limits of (c).**
  - The invoice route moves the status before it writes the record. If the record write fails, the claimant's repeat completes it (`Incomplete`). A re-run in that window finds no record, so it makes no link, and that is permanent for this invoice. This is the "no record, no link" rule; the Warning names both ids.
  - The read is not narrowed to rows the writer identity created. That narrowing needs `DecisionRecordWriter.WriterUserIdAsync`, which the re-run does not hold. It matches the other Finance reads of Decision Records (`InvoiceApprovalService.ReadRecordedLinesAsync`, `InvoiceReviewReadService.ReadHistoryAsync`). Because the latest record answers, a row a person created can only remove a link. It can add one only where the genuine record is missing.
- **Persister path unchanged.** (c) sits under `rerun is not null`. At create time X is new, so (c) holds by construction, and the persister pays no read. The persister test files are not modified.

### 7.2 K2 mitigation: two re-runs racing for one predecessor

- **Change:** `CommitAsync` takes a third lock when the plan carries a link. Its key is `InvoiceSubmissionRerun.SupersedesLockKey(predecessor)` = `ebilling-supersedes:{id:N}`, through the same `AcquireAsync`/`ReleaseAsync`.
  - It is taken after the invoice's decision lock and line lock, and after the K1 line re-check. It is released first, in `finally`.
  - Inside the lock and before `ExecuteTransactionAsync`, `SupersededSinceReadAsync` runs `SubmissionCommitGate.SupersededByAnotherAsync(..., except: this invoice)`. If another invoice now names the predecessor, the run returns `Changed` at step `supersedes` and nothing is sent. The re-evaluation's narrowing (b) then drops the link. A fault in the re-check is `Failed` / `supersedes_read_failed`. Nothing is reverted after a commit.
- `SupersededByAnotherAsync` gains an optional `except` (a `NotEqual` on the invoice id). With it null, which is what both other callers pass, the query is unchanged.
- **Why the order cannot deadlock** (the remark on `SupersedesLockKey`):
  - Every lock is a try-acquire, so a held key answers Busy at once and the job retries. No holder ever waits for another key.
  - The order is fixed anyway: the invoice's keys first, then the predecessor's.
  - The persister takes no such lock. Its link is in its create transaction, so it neither holds nor waits for this key.
- **Known limit (residual race):** the persister's create-time link is not serialised against this lock. A firm submission created while a re-run holds the key can link the same predecessor. Nothing reads the successor as unique (EB-D-206).

### 7.3 K3: the same-second tie

- **Test:** `L3_ASameSecondCandidate_IsOrderedByTheSqlGuid`. The candidate has X's own `createdon`, and its id is one step before or after X in `SqlGuid` order and the other way in `Guid.CompareTo` order (both asserted as setup). Sorts first: linked. Sorts after: no link.
- **Harness:** the predecessor query's id order uses `new SqlGuid(id)` (Dataverse's uniqueidentifier order), not `Guid.CompareTo`.

### 7.4 K4 (notes only)

- Narrowing (b) counts any successor, including a Cancelled or Rejected one. This matches the create-time chain end: once another invoice names P, P's chain has moved on, whatever that invoice's later fate.
- The `AutoRejected` guard and the `!snapshot.HasNoFirm` condition in `PrepareAsync` are defensive.
  - `!HasNoFirm`: the gate already refuses a submission whose firm differs from the stored Set-firm decision (`FirmMismatch`), so the lookup never sees a firm-less snapshot.
  - `AutoRejected`: R5 holds such an outcome instead of rejecting it. The guard keeps the re-run aligned with the persister, which links no automatic rejection (L6 pins it). It is not a second line against a firm-less link.
