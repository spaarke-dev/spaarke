## 2. §11 answers

**Re-run job handler.**
1. Existing: `InvoiceSubmissionProcessingJobHandler` (049) runs the first evaluation; `InvoiceSubmissionRerun` (2a-2) is the re-evaluation, but nothing invokes it.
2. Extension: the 049 handler's payload, idempotency key and outcome contract are the first evaluation's. Folding a second job type into it would branch on every step, so the handler is a separate one that reuses 049's lock key (`LockKeyPrefix` + `id:N`), so the two never run on one submission at once.
3. Cost of doing nothing: a Set firm leaves `rulesRerun = pending` forever. The invoice stays held and its submission stays withheld from partners, with no path that clears either.

**DI registrations** (`InvoiceSubmissionProcessor` concrete, `InvoiceSubmissionRerun`, the handler).
1. Existing: `IInvoiceSubmissionProcessor` is registered; the concrete type and the re-run are not.
2. Extension: the re-run takes the concrete processor (2a-2's constructor), so the interface registration cannot serve it. They are registered unconditionally, like the 049 handler, so a message queued while eBilling is off is Poisoned `ebilling_disabled` by the handler rather than dead-lettered `NoHandler`.
3. Cost of doing nothing: the handler cannot be resolved, and `ServiceBusJobProcessor` dead-letters every re-run message.

**Set firm enqueue** (an internal seam in the existing service, plus the `rerun` failed step).
1. Existing: `JobSubmissionService.SubmitJobAsync`; Set firm's apply → record steps.
2. Extension: this extends Set firm with a third step through the existing submitter. There is no new endpoint and no new service.
3. Cost of doing nothing: the re-run never starts (see above).

**Refused counter.**
1. Existing: the `FinanceTelemetry` meter "Sprk.Bff.Api.Finance".
2. Extension: one counter added to that meter.
3. Cost of doing nothing: a refused re-run is visible only through a log query or the dead-letter queue, which K2b rules out.

**Partner withhold.**
1. Existing: `ExternalInvoiceVisibility` step (0) withholds a firmless submission (`InvoiceHiddenReason.FirmMissing`).
2. Extension: the same step now also withholds a submission whose stored reason is still `firm_missing` while a firm is set. No new reason, no new reader; the assistant tools' row read gains one column.
3. Cost of doing nothing: after Set firm, a partner would see the submission in its pre-firm state (decided without the firm's rules), which conditions 1 and 2 forbid.

**Check (g).**
1. Existing: check (f) reads the stored member and the Decision Records.
2. Extension: (g) reuses (f)'s loop (only rows (f) found recorded) and its stored-member reader; it adds one column read from the same member.
3. Cost of doing nothing: a re-run that dead-lettered or was refused leaves an invoice held with no operator signal outside the log.

**K3b guard.**
1. Existing: `IlCallScan`-based guards (for example `FindingsJsonAppOnlyReadGuardTests`).
2. Extension: a new guard file on the same scanner. No existing guard covers the re-run result type.
3. Cost of doing nothing: a later change could project `RerunState` (an internal marker state) into an API or partner DTO, with nothing to stop it.

## 3. ADR-052 placement

Queue-driven, per-submission and retryable work, so it uses ADR-004 `IJobHandler` in the BFF. That is the same placement as the 049 processing handler. It lives in `Services/Ai/Jobs/` because it re-runs the AI-coupled submission processor (bff-extensions section D). ADR-052 §7 asks for a reason when a state machine is hand-rolled. The handler holds no state of its own: its "state" is the stored marker and `rulesRerun`, which 2a-2's single commit owns. The handler only maps outcomes to the job contract, so there is no new hand-rolled state machine. There is no timer and no `BackgroundService`.

## 4. Outcome map

| `InvoiceSubmissionRerunStatus` | Job outcome | After |
|---|---|---|
| Completed | Success | Totals recalculated through `IInvoiceTotalsService.RecalculateAsync`; a fault there → Failure (retry), whose redelivery answers AlreadyCompleted and recalculates |
| AlreadyCompleted | Success | Totals recalculated only when `RerunState` is committed |
| Refused | Poisoned (no retry) | Error log with the code and `Permanent=True`; the counter `finance.ebilling.rerun.refused{code}` |
| Busy, Changed, Failed | Failure (retry); Poisoned on the final delivery | Nothing written: the hold and the withhold remain |
| (step 0) invalid payload | Poisoned | — |
| (step 0) eBilling off | Poisoned `ebilling_disabled` | — |
| (step 0) 049 lock held | Failure (retry) | — |
| exception from the re-run | Failure (retry) | — |

`finalDelivery` = `JobContract.IsFinalDelivery`. Only on the last delivery may an unresolved Procedure be committed as `procedures_unresolved` (2a-2's rule).

## 5. Withhold change, for uac-r2 review

The change is in `Infrastructure/ExternalAccess/ExternalInvoiceVisibility.cs`; it is the only change in that folder.

- `DecideSubmissionsAsync` step (0): the withhold condition goes from `HasNoFirm(s)` to `HasNoFirm(s) || IsUndecidedForFirm(s)`, where `IsUndecidedForFirm` = `OutcomeReasonCode == SubmissionReasonCodes.FirmMissing`. The hidden reason reused is `InvoiceHiddenReason.FirmMissing`.
- `ReadSubmissionViewsAsync` (the assistant tools' path) also selects `sprk_outcomereasoncode`.
- **Why the reason code is the key.** `sprk_firmhold` and `sprk_findingsjson` are field-secured, and their reads are confined to app-only guards that this class does not use. The reason column is not secured, and 2a-2's commit replaces it in the same transaction that sets `rulesRerun = completed`. The withhold therefore lifts exactly on commit.
- **It is not lifted on failure.** A failed, dead-lettered or refused re-run writes nothing, so the withhold stays. Tests: `InvoiceSubmissionRerunTests.Job.cs` (pending → lifted; dead-letter; refused) and `ExternalInvoiceVisibilityTests.RerunPending.cs` (routes, an internal systemuser, assistant tools).
- **U1(a).** The partner projection of a committed `procedures_unresolved` hold carries only the neutral review detail ("could not be checked"); no Procedure name, rule id or detail text. The test is in `InvoiceSubmissionRerunTests.Job.cs` and has a must-fire control.

## 6. Deviations and known limits

1. **Refused → Poisoned, without admin-attention text.** The POML says "end Poisoned". K2b is met by the counter plus the dead-lettered message, which carries the code and the submission id. `StoppedNote`'s wording describes a different situation, so no reviewer-facing note was added.
2. **Reason reused.** The withhold uses `InvoiceHiddenReason.FirmMissing` instead of a new reason. To a partner, a firm set but not yet decided with is the same as no firm.
3. **Only the invoice's own submission is enqueued.** Only that submission carries the stored decision.
4. **Totals run after the commit, not before decisions open.** Between the commit and the recalculation there is a window of seconds. The decision and approval paths recalculate anyway. This is a known limit.
5. **U1(a) is shown through the invoice review detail.** On the internal channel the committed reason is Blocked and has no warning; the partner-visible neutral text is the review detail `BillingTermsNotChecked`.
6. **No Pester file** exists for the script. Check (g) is pinned in `tests/integration/data-mutation/FinanceSubmission/InvoiceFirmHoldFieldSecurityAgreementTests.cs`, as check (f) is (source facts, each with a seeded drift).

## 8. Seam for 2b-2

`InvoiceSubmissionRerunJobHandler.AfterCommitAsync` runs after a Completed commit, and after an AlreadyCompleted one whose state is committed. It currently calls only the totals. 2b-2's after-commit Signals (ConditionCleared close and link, superseded episodes, supersedes link) go there, after the totals. The step must be idempotent, because a redelivery re-enters through AlreadyCompleted.
