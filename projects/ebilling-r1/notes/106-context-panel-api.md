# Task 106 - Invoice Review context panel API (notes)

> Run 2026-10-16. Rigor: the POML says STANDARD; the tree overrides UP to FULL (tags `bff` / `api`, modifies `.cs`), so code-review and adr-check ran. Model sonnet @ high. Spec FR-33, NFR-02. Wave W4-1.

## 1. What was built

`GET /api/finance/invoices/{invoiceId}/context` (`Api/Finance/InvoiceContextEndpoints.cs`) over `InvoiceContextService` (`Services/Finance/InvoiceContextService.cs`, concrete, scoped).

- Filter chain: group `RequireAuthorization()` -> `AddFinanceAuthorizationFilter("finance.read", sprk_invoices, route invoiceId)` (Read as the caller, fail closed) -> `RequireEbillingEnabled()`. The flag never replaces authorization.
- Response: `{ invoiceId, coreRecord, budget, priorInvoices, disallowHistory, rateHistory }`. Each section is `{ status, data, code, message }`, `status` = `available` | `unavailable` | `notTracked`.
- 200 unless authorization fails. The only 4xx after authorization is the uniform 404 for an invoice deleted between the check and the read (ProblemDetails, 4xx only).
- Firm (`sprk_vendororg`) and core record (exactly one of `sprk_matter` / `sprk_project` / `sprk_regardingworkassignment`) are read from the invoice. No firm or core id is accepted from the request.

## 3. Query count (NFR-02; independent of line count)

One header read, then in parallel: core record 1, budget 1 (0 for a Work Assignment), prior invoices 1, disallow history 1 (paged), rate history 4 (this invoice's fee lines, then roster + rates + previous lines in parallel; 0 of the last three when no line has a roster-matched timekeeper). Total **9** entity reads for a Matter / Project invoice with roster-matched timekeepers, 5 minimum (unchanged by fix-round-2: the sibling read replaces the old prior-invoices read and is shared by the three sections that use other invoices, and the line reads name the readable invoice ids instead of joining to the invoice). In addition, one rights lookup per sibling invoice (see section 7a), up to 200, 8 at a time; these are not entity reads and repeat lookups are absorbed by `CachedAccessDataSource`. Pinned by `QueryCount_DoesNotDependOnTheInvoicesLineCount` (3 vs 400 lines, same 9). Paged reads (5000 per page) stop after 10 pages and the section says `too-large` rather than summarise a partial read. The whole response has a 5 s deadline (`Deadline`); NFR-02 (3 s p90) is measured live by task 112.

## 4. Deviations and assumptions (each one line)

1. **Disallow history counts decided invoices only** (Approved, Sent to AP, Paid). A Reduced line on an In Review invoice is provisional, and Rejected / Returned / Cancelled invoices are void (FR-36). The POML says "this firm's invoices"; this narrows it. Easy to widen in `StandingInvoiceStatuses`.
2. **History is firm AND core record** (the POML constraint), not the firm's history across all core records.
3. **"Prior" invoices are all other invoices of the firm on the core record**, most recent first, not only those dated before this one (reviews happen out of order).
4. **Two core record lookups set on one invoice -> `ambiguous`**, not a precedence rule (FR-05: exactly one).
5. **Classification rates** are included in the rate history for a timekeeper whose roster classification matches (rate rows with no timekeeper). The POML says "sprk_ratecardrate for the firm's timekeepers"; a firm that rates by classification would otherwise show nothing.
6. **Two files not in the POML list were touched**: `tests/Spaarke.ArchTests/RouteAuthorizationGuardTests.Ledger.cs` (new `GovernedFile` + `ExpectedEndpointFileCount` 126 -> 127; the guard demands it for any new endpoints file).
7. Tests live in the unit project: the contract file is compiled in through the `tests/integration/contract/**` glob.

## 7. Known limits (K-class, not fixed)

- **K2** `budget.asOf` is the core record's `modifiedon`, not the rollup time.
- **K4** `MaxTimekeepers` 1000 and the 10-page cap are fail-loud (`too-large`) limits no real invoice is expected to reach.
- **K4** (reviewer, fix-round-3) On a cold rights cache the sibling checks run 8 at a time, one OBO lookup each, so a core record with about 200 sibling invoices can exceed the 5 s deadline; the three sibling sections then fail closed as `.timeout` (never partial or unfiltered data). Real core records carry far fewer invoices from one firm, repeat lookups are cached, and task 112 measures NFR-02 live.

## 7a. Fix-round-2: other invoices limited to what the CALLER can Read (was K2, now fixed)

The finding: authorizing the route on invoice A said nothing about invoice B on the same core record, yet B's number, dates, totals and status (`priorInvoices`) and its disallow and billed-rate figures were returned from app-only reads. A confirmed defect against the fail-closed rule, not a known limit.

- **Access path reused:** `AuthorizationService.GetCallerRecordAccessAsync` + `OperationAccessPolicy.HasRequiredRights(rights, "finance.read")` - the identical question and policy key the route filter asks about invoice A, answered by Dataverse for the caller (OBO `RetrievePrincipalAccess`, cached by `CachedAccessDataSource`). Precedent for the call from a service: `ComposeService`, `OfficeSearchService`. Not chosen: `SuggestionCandidateAccess` (one OBO GET per candidate through `IDataverseUserClient`, name-oriented, tied to the Communication engine), `ICommunicationAccessFilter` (communication access model), `SignalReadService` (signals). `GetRecordAccessAsync` carries an explicit per-request token (not the shared HttpClient header), so the 8-way parallel lookups are safe.
- **Section 11:** existing = the route's `finance.read` check and `AuthorizationService`; extension = this IS that call, repeated per sibling; cost of doing nothing = a caller reads invoices they cannot open. No new interface, DI registration, package, endpoint or column; the service constructor takes the already-registered `AuthorizationService`; one nested `InvoiceCaller(UserId, AccessToken)` record carries the caller from the endpoint (`CallerResolution.ResolveObjectId`, `TokenHelper.ExtractBearerTokenOrNull`, as the filter does).
- **Shape:** the siblings (all statuses) are read once, most recent first, then each is checked (max 200, 8 at a time); the result is shared by prior invoices, disallow history and previously-billed rates. Disallow and previous-rate line reads now name `sprk_invoice In (readable ids)`, so an unreadable invoice's lines are never requested.
- **Disallow history: RECOMPUTED over readable invoices** (not marked unavailable). The figures are what the caller could add up from the invoices they can open. An empty readable set is an empty (available) section, like zero history.
- **Fail closed:** no caller id or token, a rights lookup that throws, or a lookup that is `Faulted` AND did not grant Read -> the three sections are `unavailable` with `.access-check-failed` and carry no data; no line query runs. A faulted lookup that did grant Read (the degraded read-probe) counts as readable, as the route filter treats it. A plain "no Read" is an answer: that sibling is excluded.
- **Bound:** more than 200 siblings (or an incomplete sibling read): the prior list is built from the 200 most recent and says `hasMore`; disallow history and previous rates are unavailable (`.too-large`) because a total over only some of the readable invoices would be wrong. No real core record has that many invoices from one firm.
- **Independence note:** the three sections now share the sibling read, so if it throws they are all unavailable (each with its own `.unavailable` / `.timeout` code); the core record and budget sections are unaffected.
- **The core record** was the follow-up listed here in fix-round-2; it is fixed in fix-round-3 (section 7b).

## 7b. Fix-round-3: the core record is the caller's to read too, and `invoicesConsidered`

**A1 (F1, confirmed bypass).** The route checks `finance.read` on the INVOICE only. `coreRecord`, `budget` and the core-scoped approved rates came from app-only reads of the matter / project / work assignment, so a user who can read an invoice but not its matter saw the matter's name, number, status, dates, budget, spend, remaining, utilisation, invoice count and matter-scoped rate cards. Elsewhere that data needs Read on the matter (`FinanceEndpoints.cs` matter routes; `OperationAccessPolicy` defines `finance.read` as Read on the parent matter or project).

- **One check, shared:** `CheckCoreRecordReadAsync` asks the same question as the sibling invoices (`CheckReadAsync` -> `AuthorizationService.GetCallerRecordAccessAsync` + `finance.read`) of `sprk_matters` / `sprk_projects` / `sprk_workassignments` (`FinanceAuthorizationFilter` constants). It is a `Lazy` shared by the three sections, started on first use, one lookup per request.
- **Gated:** `coreRecord`, `budget` and the rate history's approved-rate read (which includes cards scoped to the core record). A Work Assignment's budget stays `notTracked` (nothing is read for it, nothing to withhold).
- **Refused** (Dataverse says no Read): the section is `unavailable` with `.access-denied`. **Faulted or threw, or no caller token:** `unavailable` with `.access-check-failed`. In both cases nothing of the record is read: no core row, no rollup row, no rate-card query.
- **Choice to flag:** the whole rate-history section is unavailable on a refusal (as the review asked), although its firm-wide cards and the caller's own invoice lines would be safe to show. Loosening it to "firm-wide cards only" is a one-branch change in `LoadRateHistoryAsync` if the owner prefers a partial section.
- **Reads:** unchanged at 9; the core-record check is one more cached rights lookup (not an entity read).
- **Why this was missed:** fix-round-2 treated it as a follow-up of a different record. It is the same disclosure class and the same fail-closed rule.

**A2 (F2).** `DisallowHistoryContext.InvoicesConsidered` counted only invoices that had a Reduced or Disallowed line (distinct owners of the returned lines), so 12 decided invoices with 2 cuts reported 2. It is now the number of decided, readable invoices examined (`decidedIds.Length`), which is what the UI's "N invoices considered" must mean. Test: `InvoicesConsidered_CountsEveryDecidedReadableInvoice_NotOnlyThoseWithCuts`.

## 7c. Fix-round-4 (from the task 107 review): "more" and "too large" must not count invoices the caller cannot read

`AllExamined` was `complete && rows.Count <= MaxSiblingAccessChecks`, so it counted every sibling invoice including unreadable ones: a caller who could read 3 of 250 invoices on a record was told `hasMore = true` and got `.too-large` for disallow and rate history, which reveals that unreadable invoices exist. Now the sibling walk checks invoices newest first in pages (shared `CallerReadCheck.ScanAsync`) until more than `MaxReadableSiblings` (200) are READABLE or the rows (or the `MaxSiblingAccessChecks` ceiling, now 1000) run out; `hasMore` is `readable > 10` only, and the too-large codes fire only when more than 200 are readable (or at the ceiling, see the 107 notes, section 10, K2 (b)). The loop is the shared helper also used by 107. Tests: `SiblingsTheCallerCannotRead_NeverMakeTheAnswerTooLarge_OrSayMore` (250 siblings, 3 readable), and `MoreReadableSiblingsThanCanBeSummarised_...` (the old too-large test, now over 201 readable).
