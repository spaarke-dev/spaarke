## Behaviour

- **Show:** the stored `proposals[].firmDescription` fills the field; null is an empty field.
- **Save:** `firmDescription` is on the PATCH body only when the admin changed it (compared after the server's trim): a changed text as typed, a cleared or blank field as `""`, an untouched field not at all. It is never null. A Duplicate rule never sends one.
- **Client checks** (early; the server decides), in the server's order: blank is valid; Duplicate; unpaired surrogate or a Control, Format, line or paragraph separator character; more than 200 Unicode scalars (`[...text].length`); `{` `}`; `<` `>`; the rule set's or the rule's name after NFKC, white-space runs folded to one space, case-insensitively. The trim uses the server's white-space set (so U+FEFF is not trimmed, as on the server).
- **Counter:** `n / 200`, turning to the error colour over the limit; no `maxLength`, so nothing is cut (ISS-027).
- **Notice** (by the field): "Firms see this text when this rule rejects their invoice. Do not name the rule set or the rule, and do not put internal notes here. The check for names does not catch letters from other alphabets that look the same, so read the text through before you save."
- **Duplicate:** the field is read-only and a reason replaces the notice and the counter.
- **Server refusal:** a 422 `ruleset.invalid` or `ruleset.publish_invalid` with `errors[].field === "firmDescription"` shows one message per reason code under the field (the server's wording), until the admin edits the text again. The top banner still lists the server's errors, as for every other failure.
- **After save:** unchanged path. `saveEdit` reloads the rule set; on a published working version the server creates a draft and the reload shows it (form re-keyed by version id), with the existing "Saved as a new version" notice.

## Known limits

- Look-alike letters from another alphabet (homoglyphs) remain uncaught by the name check, as on the server; the notice says so. Default-ignorable characters (the combining grapheme joiner, the variation selectors, the Hangul fillers and the rest of Unicode's Default_Ignorable_Code_Point set) are now refused as invisible characters, so they can no longer be used to hide a name inside a text (review round 2).
- The source-scan wiring tests (`firmDescriptionWiring.test.ts`) are whitespace-sensitive: a reformat that moves a token fails a test rather than passing silently. Accepted, with a control in the same file that shows the scan finds the wiring as written and not a reformatted copy.
- Selecting the rule that is already selected (a re-click) also drops a save's refusals: the selection handler clears them on every click, not only on a change of rule. It fails closed: the admin tries the save again and the server answers again.
- The name check upper-cases per character (keeping a letter whose upper case is longer, such as "ß"), which approximates the server's ordinal ignore-case comparison; the server stays authoritative and a text the client lets through can still be refused with a 422 (shown under the field).
- The page has no DOM test environment (node Jest, as the other page tests): the field's typing and the Save click are covered through the pure functions (`firmDescriptionToSend`, `checkFirmDescription`) the component calls, and its rendered output through static markup, not by simulating events.
- A refusal from Accept or Publish shows under the field of the rule it names when that rule is selected; the publish dialog's own banner still lists every error.
- `assignmentPanelFirmPicker.test.ts` fails to start in a worktree without a built `Spaarke.UI.Components` (pre-existing, above).
- **Unicode-version drift between the browser and .NET.** The client folds case with the browser's tables and NFKC; the server with .NET 10's. Measured on 2026-11-17 against .NET 10.0.15 and Node 22.14 (every scalar compared): the client folds 27 scalars the server does not (5 letters: U+019B, U+0264, U+1C8A, U+A7CD, U+A7DB; and the 22 Garay letters U+10D70 to U+10D85), all added in newer Unicode versions than the server's tables, so the client can refuse a text on those letters that the server would accept. In the other direction the server folds 27 scalars the client does not (the Greek letters with ypogegrammeni, such as U+1F80), which the server still catches. No other pair differs on a common script. A 37-code-point NFKC difference was also reported in review; it is the same kind of drift and is not measured here. The server stays authoritative.
- **Lost update between two admins.** Two admins editing one rule at once: the later save overwrites the earlier one's change to the same field. This is how every field of the page behaves (the PATCH has no version token; only Accept and Reject send `rowVersion`) and predates this task.
- **Messages copy the server's wording; only the codes are pinned.** The six messages in `firmDescription.ts` are the server's `FirmDescriptionMessage` text, but `firmDescriptionPin.test.ts` pins the six reason codes, the limit, the member and the error codes, not the wording. A change of wording on the server shows under the field only through an unknown reason code (its own message is used then).
- The "does not pass the checks" warning (F6) compares the stored text with the client's checks, so it can differ from the server for a letter in the drift above; the save still behaves as the server decides.
