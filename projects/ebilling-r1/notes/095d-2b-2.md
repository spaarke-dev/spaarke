## 2. The steps (`RemapSignalsAsync`)

1. **Read** the submission.
   - The state is `done`: AlreadyDone, and nothing more is read or written.
   - The step is Refused (`Permanent=true`, nothing written) if any of these holds:
     - the state is not `committed`;
     - the state names a decision other than `DecisionIdFor(submissionId)`;
     - there is no stored decision, or `rulesRerun` is not completed;
     - the findings are unreadable, or have no plan.
2. **Rule Signals.** Each committed `signalPlan` entry goes through `SignalEpisodeLifecycle` (D-13 key, `SkipWhenSameFingerprint`).
   - A would-be rejection held for review (EB-D-187) is written like any other held finding. No record is written or claimed, and nothing is closed as Acted.
3. **System Signals.** 049's read of `BILL-SYSTEM-SUBMISSION` is followed by the same mapping the intake uses (`StoredFindings.SystemFindings` → `BillingFindingSignalMapper.MapAll`), and each mapping goes through the lifecycle.
   - Q2: a changed reason set gets a Superseded close (record-free) and episode n+1. An unchanged set is refreshed only.
   - An open system Signal on one of **this submission's** lines with no finding left is closed ConditionCleared, record-free. Line ids derive from the submission; a line another linked submission added is untouched.
   - Unusable policy (null): no system re-map and no shared close, so the result fails toward open. A non-"disabled" state is noted in `sprk_adminattention`, as 049 does.
4. **The shared hold Signal** (system policy on the invoice):
   - **Invoice group non-empty:** a lifecycle write (Q2).
   - **Group empty:** the step reads the latest episode, then:
     - *open*, and `InvoiceOpenHolds.ReasonsAsync` over every linked submission is empty (T19):
       1. find the assign-firm record (`BillingDecisionRecorder.FindStoredResolvedSetAsync("assign-firm", invoice, decision)`, read-only; not found is a retry);
       2. record the Signal id in `assignFirmRerun.conditionCleared` with a conditional write, BEFORE the close;
       3. `CloseAsync(ConditionCleared)`;
       4. `LinkConditionClearedRecordAsync(signal, record, expectedPrior: null, resolvedBy: decider)`.
     - *open*, with a reason left: untouched (fail toward open).
     - *resolved*, and it is the recorded Signal: link only (a retry after the close).
     - *resolved* by any other path: untouched and never linked (Q1 must-not-fire).
   - If the close answers ChangedSinceRead, the recorded id is withdrawn, so a retry never links a close this run did not make.
5. **Last,** one conditional write (`UpdateIfRowVersionMatchesAsync`) sets the state to `done` (with `signalsOn`), records the permanent writer refusals in `signalWriteRefusals`, and merges `sprk_adminattention`.
   - Any retryable failure leaves the state `committed`. The refusals and the intent are still written.

**Never a hold write.** The steps write Signals, the submission's findings and the attention text only, never the invoice, a line, the reason code or the firm hold. A Signal fault therefore cannot lift or add the hold or the partner withhold. The test `ASignalFaultOnTheFinalDelivery_LeavesTheHold_AndAReplayFinishes` asserts that the invoice row is unchanged.

**Idempotent.**
- `done` answers AlreadyDone with nothing written.
- Before `done`, every write is a lifecycle write (it refreshes; there is no second row), a conditional close (a closed Signal is not reopened), or a link that answers AlreadyLinked.

## 3. §11 answers (`RemapSignalsAsync`, `RerunSignalSeams`, the result type)

1. **Existing.** These already exist:
   - `InvoiceSubmissionAfterSteps` writes an intake's Signals, and only while the submission is Processing.
   - `InvoiceCorrectionReevaluation` re-maps one corrected field.
   - `SignalWriter` writes one Signal.

   None of them re-maps a committed re-run, or closes the shared Signal when the last reason is gone.
2. **Extension.** The steps are a partial of the re-run, the class that owns the state they move on. They are built from those parts unchanged: the lifecycle, the mapper, `InvoiceOpenHolds.ReasonsAsync`, and the writer's close and link. They add no DI registration, no endpoint and no package.
3. **Cost of doing nothing.** After the commit, the shared Signal still says "held for its firm" though the hold is gone. The re-run's new findings (a Procedure gap, a firm rule's finding) also raise no Signal.

## 6. Deviations, known limits, open questions

- **Q2 "LeftAsIs" wording vs the writer.** `CloseActedByDecisionAsync` returns LeftAsIs only for a Superseded close made before the stored set was read. A Superseded close after the read is re-closed as Acted with the human decision's record, the same treatment as any record-free system close after the read (049 D-122). Either way `CloseSetAsync` counts no failure, so there is no 503 loop. The tests pin both. Ontology may want the ruling text, or the writer, aligned.
- **"The supersedes link."** This is implemented as Q2's superseded episodes: a Superseded close, record-free, then episode n+1 found by its dedupe key. There is **no `sprk_signal` successor link** (R16, ONT:724). The invoice-level automatic supersedes link (task 104, `sprk_invoice.sprk_supersedesinvoice` to a Returned-to-Firm predecessor once the firm is known) was a 2b seam that nothing implements. It needs a design decision (in the commit or after it, and a persister dependency), so it is **not built**. Open question for the lead.
- **Cleared line Signals are closed ConditionCleared,** record-free, as `InvoiceCorrectionReevaluation.CloseClearedAsync` and the re-evaluation job do. The brief's step 4 names only the shared Signal. The line case follows the reference.
- **Known limit (K-class).** The intent is written before the close. Suppose the process dies after the intent write and before the close, AND another system path then closes that same Signal as ConditionCleared. The retry would then link the assign-firm record to that close. A close the run itself sees refused withdraws the intent (S3). The residual window needs a crash plus a concurrent ConditionCleared close of the shared Signal, and the condition is cleared in both cases.
- **Log text.** The handler's final-delivery `Transient` log still says "the invoice stays held". On the Signal path the commit has already released or re-held the invoice, so the text is imprecise there. The Signal steps log their own line before it.
