> Written by `/project-pipeline` Step 3 as the per-task contract for the POML authors. **spec.md is authoritative**; this brief fixes ids, dependencies, waves, tiers and scope boundaries between tasks. `tasks/TASK-INDEX.md` is generated from the same table.

## Conventions for every POML

- **File name**: `projects/ebilling-r1/tasks/{id}-{slug}.poml`. Root: `<task id="{id}" project="ebilling-r1">`. Valid XML (escape `&`, `<`, `>` in text — write "and", "less than"; never put a bare `<element>` name in prose).
- **Field set**: task-create Step 4 skeleton (`.claude/templates/task-execution.template.md`): `<metadata>` with title, phase, gate, status `not-started`, rigor + rigor-reason, model-tier + model-tier-reason, effort, parallel-group, parallel-safe (+ parallel-reason when false), deps, tags, estimated-effort; then prompt, role, goal, context (background, relevant-files, dependencies), constraints, knowledge, steps mode, escalation, justification (new surface only), ui-tests (frontend only), tools, outputs, acceptance-criteria, notes, execution.
- **Size**: target ≤ 12 KB per POML. Point at files and spec sections; do not restate them.
- **Acceptance criteria**: closed set, testable, include negative / authorization cases, plus the test-scope clause: *"Cover the stated contract plus the edge cases named above. Anything beyond that needs a one-line justification in task notes."* No numeric test counts. Ask for a seeding proof only for security / fail-closed / tenant-isolation guards.
- **Every BFF task** (touches `src/server/api/Sprk.Bff.Api/**`): constraint citing `.claude/constraints/bff-extensions.md` and an acceptance criterion "publish-size delta measured against a fresh master build and recorded in task notes; no new HIGH CVE". Only task 043 adds a package (`Azure.AI.ContentUnderstanding` 1.1.0).
- **Shared append points** (excluded from file-overlap analysis; the executor re-reads the file immediately before editing and adds only its own lines): `src/server/api/Sprk.Bff.Api/Infrastructure/DI/FinanceModule.cs` (DI registrations, ADR-010), the Finance endpoint-mapping call site, `appsettings*.json` option sections, `docs/data-model/*.md` (each task edits only its own entity's section). Say so in the POML's notes when the task touches one.
- **Endpoint files**: each API task adds its own `*Endpoints.cs` file under `src/server/api/Sprk.Bff.Api/Api/Finance/` (verify the folder; follow the existing `/api/finance/invoice-review/*` placement) unless the brief says otherwise. Every route: endpoint-filter authorization (ADR-008), ProblemDetails with stable codes (ADR-019), returns the eBilling disabled code when the flag is off (040).
- **Schema tasks (010–028)**: each writes ONE idempotent PowerShell Web API script `scripts/ebilling/Deploy-Ebilling{Area}Schema.ps1` modelled on `scripts/Deploy-ChartDefinitionEntity.ps1` and the `dataverse-create-schema` skill (`.claude/skills/dataverse-create-schema/SKILL.md`), runs it against **dev** (additive changes only; `-WhatIf` first), verifies with a metadata read, and updates the entity's `docs/data-model/` file. **They do NOT edit `src/dataverse/solutions/SpaarkeMaster/**`** — task 029 is the only task that syncs solution source, forms and views (afterwards only serial tasks edit it: 015 and 026 for their entities, 070 for the rule-type option set, and deploy tasks 079 / 112 / 136 / 153 for sitemap / navigation entries of the pages they deploy). FR-05 core-record fields (ADR-024 dual-field: Matter / Project / Work Assignment lookups + the five resolver fields) are added by the task that owns each table (010 line, 012 invoice, 020 submission, 021 approval, 022 external identifier). Destructive changes (delete table / column / option set / data) need explicit owner OK first — escalation trigger.
- **Actions** (042, 047, 075, 131): author the JPS Action with the `jps-action-create` skill (exemplar `.claude/skills/jps-action-create/examples/document-profiler.json`), validate with `jps-validate`, seed the Action row and the Binding (`sprk_playbookconsumer`) with the existing seed scripts (`scripts/seed-data/Deploy-Actions.ps1`, `scripts/dataverse/Seed-PlaybookConsumers.ps1` — verify the current seed-file location by Grep), output schema in the Action row (no C# output schema), closed enums via `$choices`, Null peer behaviour, and an ADR-043 seam test through `IActionRunner`. Reading `.claude/skills/**` is fine; **writing under `.claude/` is main-session-only** — none of these tasks should need to.
- **Frontend tasks**: Fluent v9 only (ADR-021), shared components first (ADR-012), dark-mode check in `<ui-tests>`, `npm install --legacy-peer-deps --no-audit --no-fund` in `src/solutions/*`. Visual reference for 108–111: the owner's prototype `c:\code_files\spaarke-prototype\projects\ebilling.r1` (README, `src/review/`, `src/ui/kit.tsx`) — copy behaviour and layout, never import from the prototype repo.
- **Ontology-owned code** (`Services/Signals/**`, `Services/Finance/FinanceBaseValues.cs`, `PolicyVersionValidator`, `RuleBodyDescriber`, `DecisionActionCatalog`): **PR #1111 merged to master 2026-10-15 at `f292ad119`** (Signal writer, rule grammar + evaluator, Decision Record writer `WriteAsync` / `WriteGateDecisionAsync`, `GET /api/v1/signals/worklist`, uac-r2 walker batching #1892). `work/ebilling-r1` merges origin/master at pipeline commit.
