### C4.5 — NEW: `RunStatus` int-vs-string — reconciler + crash-recovery scans return zero rows

- **Verified — defect confirmed, exactly as the gap analysis stated**:
  - `Models/ProvisioningRun.cs:177–178` — `RunStatus` carries **STJ** `[JsonConverter(typeof(JsonStringEnumConverter))]` only.
  - `Modules/CosmosModule.cs:140,155–157` — the client is built with `.WithSerializerOptions(new CosmosSerializationOptions { PropertyNamingPolicy = CamelCase })`, i.e. the SDK's **default Newtonsoft-based serializer**. Newtonsoft ignores STJ converter attributes → `status` is written as an **integer** (proven defect class: #19/#20 both arose from this exact serializer). The comment at CosmosModule.cs:140 ("every POCO in Models/ carries explicit …") and the scanner's own comment at `Reconciler/CosmosActiveRunScanner.cs:40–44` ("courtesy of the JsonStringEnumConverter attribute") both rest on the same **false premise**.
  - `Reconciler/CosmosActiveRunScanner.cs:46` — `SELECT * FROM c WHERE c.status IN ('Running', 'WaitingOnGate')` compares **strings** → 0 rows forever.
  - **Consumers blinded**: `StateReconcilerService` (DAG advance) AND `Reconciler/CrashRecoveryStartupService.cs:236` (I6 boot scan) — both go through `IActiveRunScanner`.
  - **Same-class exposure**: two more STJ-only enums in the doc graph — `Models/GateState.cs:26` (`GateState`) and `ProvisioningRun.cs:287` (`QuarantineState`). No SQL queries them *today* (grep: the scanner query is the only enum-comparing `QueryDefinition` in production code), but any future gate/quarantine query inherits the trap.
- **Fix shape (recommended)**: **Dual-attribute the enums, mirroring the #20 precedent** — add `[Newtonsoft.Json.JsonConverter(typeof(Newtonsoft.Json.Converters.StringEnumConverter))]` alongside the STJ attribute on all THREE enums (`RunStatus`, `GateState`, `QuarantineState`). Minimal blast radius, consistent with the already-landed `id` fix, keeps the scanner query and the Bicep composite index on `status` untouched. Rejected alternatives: (a) custom STJ `CosmosSerializer` on `CosmosClientOptions` — cleaner long-term (all STJ attributes become authoritative) but re-opens every serialization behavior at once and invalidates the two shipped fixes' rationale; defer as a possible follow-on with its own test pass. (b) Change the scanner to query ints — leaves live docs unreadable by humans, contradicts the doc-comment contract, and still leaves GateState/QuarantineState divergent. Also fix the two misleading comments (CosmosModule.cs:140, CosmosActiveRunScanner.cs:40–44) to state the real mechanism (Newtonsoft `StringEnumConverter`).
- **Live-data migration**: exactly 1 Cosmos doc exists (`runs/65109e91-…`, NotStarted, dead test run). Delete it (or PATCH `status` to the string) as a runbook step — no migration tooling needed.
- **Test coverage needed** (the regression net for the whole #19/#20/C4.5 family): a **serializer-contract unit test** that serializes a fully-populated `ProvisioningRun` through Newtonsoft with `CamelCasePropertyNamesContractResolver` (the observable equivalent of the Cosmos default serializer) and asserts: `"id"` present, `"status":"Running"` as string, `"gateStates"` values as strings, no `"ttl"`. Plus an **integration seam test** (Cosmos emulator or live-dev container): repository writes a `Running` run → `CosmosActiveRunScanner.ScanAsync` returns it. The seam test is the one that would have caught this.
- **Blast radius**: L2-only. Existing unit tests that serialize via STJ fixtures keep passing (STJ attrs unchanged). Zero API surface change.
- **Effort**: **S** — but **load-bearing**: without it a working dispatcher still looks hung (see Ordering).

### C4.6 — NEW: FR-22 Level-1 idempotency inert (SB duplicate detection off)

- **Verified — defect confirmed**:
  - `infrastructure/bicep/modules/service-bus.bicep:39` — `requiresDuplicateDetection: false` for all queues it manages, and its default `queueNames` (`:15`) is `['sdap-jobs','document-indexing']` — **`sprk-provisioning-jobs` appears in no Bicep file** (repo-wide grep: 0 hits in `infrastructure/`).
  - Live queue was created via `az servicebus queue create` defaults → dedup **off**, sessions **off**.
  - `Enqueue/ServiceBusHandlerEnqueuer.cs` header (lines 11–45): deterministic `MessageId = SHA256(HandlerId|RunId|CustomerId|paramHash)` AND **always sets `SessionId = CustomerId`** — both features the live queue cannot honor (dedup ignored; SessionId inert on a non-session queue).
- **Fix shape**: This is an IaC + live-surgery pair (design detail under C5.4):
  1. **Bicep**: declare the queue in the L2 stamp (see C5.4) with `requiresDuplicateDetection: true`, `duplicateDetectionHistoryTimeWindow: 'PT1H'` (must exceed the longest re-enqueue window a reconciler retry can produce for the same MessageId; handlers run ≤30 min → PT1H is the safe floor), and `requiresSession: true` **if and only if DS-2 decides on a session-aware receiver** (the enqueuer already emits SessionId either way; a sessionful queue with a non-session receiver deadlocks, and a session receiver on a non-session queue throws — the two must be decided together).
  2. **Live sequence**: both `requiresDuplicateDetection` and `requiresSession` are **create-time-only** in Azure Service Bus — the existing queue CANNOT be patched. Sequence: (a) discard the 1 stale H0 envelope (belongs to the dead NotStarted run deleted in C4.5 migration); (b) `az servicebus queue delete`; (c) deploy the Bicep-declared queue; (d) verify — namespace-scope RBAC survives deletion, so no re-grant needed.
- **Test coverage needed**: An IaC assertion is impractical in the current test stack; instead add a **runbook verification step** (`az servicebus queue show --query "requiresDuplicateDetection,requiresSession"`) to the L2 deploy script (C5.9) and to H13's eventual live probes. The FR-22 "no duplicate under N reconcilers" load-test half (gap C1.8) is the behavioral net.
- **Blast radius**: The queue delete/recreate is destructive to in-flight messages — safe today (1 stale message), a coordinated drain forever after. BFF's `ServiceBusProvisioningEnqueuer` (H0.5 consent path) targets the same queue name — unaffected by properties, but its messages also gain dedup semantics (correct).
- **Effort**: **S** (+ the session decision belongs to DS-2).

## Ordering / dependencies vs the dispatcher build (DS-2)

**Hard prerequisites — must land before the dispatcher can be meaningfully tested:**

1. **C4.5 status serialization — the single most-blocking item.** The dispatcher's job is to move runs to `Running` and hand completions to `ApplyHandlerOutcomeAsync`; with `status` written as an int, the reconciler (DAG advance) and I6 crash recovery scan zero rows, so even a perfect dispatcher produces an E2E that *silently hangs after H0* — indistinguishable from a broken dispatcher. It fails invisibly, poisoning every dispatcher test above the unit level. (One-line-per-enum fix; do it first.)
2. **C5.5 SB Data Receiver grant** — mechanically absolute for live receive (loud, obvious failure; trivially granted; but must exist before any deployed-dispatcher smoke).
3. **C5.4/C4.6 queue recreate (dedup + session decision)** — if DS-2 chooses a session-aware receiver, the queue MUST be recreated with `requiresSession: true` first (create-time-only); a session receiver against the current queue throws immediately. The session decision itself is DS-2's; the queue surgery is this study's.
4. **C5.1 config keys** — must be in Bicep source before any stamp redeploy (the deploy that ships the dispatcher would otherwise wipe the live aliases and take Cosmos/SB config down with it).

**Parallel with the dispatcher build:** C5.2 (audience), C5.9 (deploy script — needed *by* the dispatcher's first live deploy, buildable now), C6.1–C6.3 + C6.5 (skill/runbook contract fixes; independent of runtime), C4.1–C4.3 regression tests.

**Follow-on / decision-gated:** C5.3 + C5.6 + C5.7 + C5.8 (all gated on the C1.4 registry-client credential decision — UAMI-App-User vs secret; recommend deciding this in DS-2/DS-1 since it also shapes handler auth); C6.6 (gated on C3.3 real Ready-writer).
