# Task 153 (H12c Credential Config Confirmation) — Deviations

> Recorded per CLAUDE.md §6.5 ADR Conflict Resolution Protocol + task-execute Step 9 (deviation documentation).

## D-153-1: No client-secret credential to provision — Path C (pivot to comply)

**POML literal framing** (`<prompt>`): "This task provisions/confirms H12c's credential configuration (the customer-env Dataverse Web API credential it needs, matching the same H4-populated-KV pattern as H7/task 142)."

**What the code actually shows**: `DataverseWebApiModelDeploymentReferenceWriter.AcquireTokenAsync` (H12c's sole Dataverse Web API collaborator) already authenticates via `new DefaultAzureCredential(new DefaultAzureCredentialOptions { TenantId = tenantId })` — the SAME UAMI-as-Dataverse-App-User idiom used by every OTHER post-H10 handler in this DAG (H12a's 4 seeders, H12b's 2 seeders, H11's Graph collaborators, EntraAppReg, IntegrationWiring). There is no `ClientSecret`-shaped field anywhere in `RuntimeReferencesOptions`. H7 needed a confidential-client secret specifically because H7 dispatches BEFORE H10 exists in the DAG (design.md §4.1: H5→H6→H7→H10→H11); H12c dispatches AFTER H12a+H12b, both of which are themselves post-H10 — H12c never runs before the MI-Dataverse-App-User exists. The POML's assumption that H12c needs "the same H4-populated-KV pattern as H7" does not hold.

**Resolution — Path C (pivot to comply)**: no client-secret credential was added. This confirms (does not contradict) the Wave G-5 dispatch directive: "Auth pattern per H12b precedent (task 151 landed): DefaultAzureCredential (L2 UAMI as Dataverse App User post-H10), NOT ClientSecretCredential. Confirms auth-v4 obligation only affects pre-H10 handlers." No escalation needed — this is a straightforward confirmation-of-correctness, not a conflict.

**Alternative considered and rejected**: adding a `RuntimeReferences:ClientSecret` option + KV wiring mirroring H7, per the POML's literal words. Rejected because it would introduce an unused, dead config surface (the writer never reads it) and would misrepresent H12c's actual (correct) auth posture to future readers.

## D-153-2: The genuine config gap was `SharedPlatformOpenAiEndpoint`, not a credential

Grep-verified pre-task-153 that `RuntimeReferencesOptions.SharedPlatformOpenAiEndpoint` (Model1Shared's shared-platform OpenAI endpoint — NOT a secret, a URL) had **zero** Bicep app-setting wiring anywhere in `modules/controlplane-worker-app-service.bicep` or `platform-controlplane.bicep`. Every Model1Shared customer's H12c run would have failed Resumable at runtime (`MissingSharedPlatformEndpointConfiguration`) forever, silently, until an operator noticed and manually set an App Service setting out-of-band.

**Resolution**: wired `RuntimeReferences__SharedPlatformOpenAiEndpoint` as a KV-reference app setting on the Worker site, sourced from the SAME canonical `AzureOpenAI-Endpoint` KV secret the `.Api` site already resolves for `AzureOpenAI:Endpoint` / `DocumentIntelligence:OpenAiEndpoint` (per `scripts/canonical-secret-catalog/manifest.yaml`) — single source of truth for this environment's shared-platform OpenAI endpoint, not a duplicate value that could drift from the BFF's own config. New params: `azureOpenAiEndpointSecretName` (default `'AzureOpenAI-Endpoint'`, stable per-environment name, parity with `bffApiClientSecretName`'s shape) on both `modules/controlplane-worker-app-service.bicep` and `platform-controlplane.bicep`; threaded through the `workerAppService` module invocation; regenerated `platform-controlplane.json` via `az bicep build`. Set explicitly in `parameters/platform-controlplane-dev.bicepparam`.

**Why NOT an NFR-05 boot-time requirement**: unlike `EnvVarValuesOptions.ClientSecret` (every H7 run needs it) or `DataverseEnvironmentRegistryOptions.AdminEnvironmentUrl` (every registry-client call needs it), `SharedPlatformOpenAiEndpoint` is consulted ONLY on H12c's `Model1Shared` branch. A Worker serving exclusively `Model2Dedicated` customers in some environment must not crash-loop at boot for a setting it never uses — that would be the NFR-05 pattern's failure mode in reverse (an unconditionally-required check on a conditionally-required field). `RuntimeReferencesOptions.Validate()` therefore only bounds-checks `DataverseRequestTimeout` (the one field every H12c run needs); the existing per-run handler guard (already correct, already tested) remains the enforcement point for the endpoint itself, correctly classified Resumable per design.md §4C.
