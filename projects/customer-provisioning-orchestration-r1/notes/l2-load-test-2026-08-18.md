## 2. Compression Strategy for the 30-Minute Scenario + Equivalence Argument

**POML acceptance criterion 2**:
> "A 30-min synthetic handler enqueued via POST /api/runs receives 202 immediately; GET /api/runs/{id} eventually reports status=Completed; no HTTP timeout observed on caller."

**Approach chosen**: parametrized wall-clock duration `SyntheticHandlerDuration = 3 seconds` in `LongHandlerScenario.cs`. Production T = 30 minutes.

**Equivalence argument**:

The FR-22 fear this scenario addresses is: *"a synchronous handler call from L2 REST would force the caller's HTTP connection open for the handler's full 30 minutes, blowing the App Service default 230-second HTTP request timeout."*

The invariant proven is DURATION-INDEPENDENT:

1. **POST /api/runs returns 202 immediately (measured: 60 ms) regardless of handler duration.**
   Because the L2 REST endpoint does NOT invoke the handler — it enqueues a Service Bus envelope and returns. The `SyntheticHandlerDuration` value only affects when the background "handler" task mutates the repository row from `Running` → `Completed`. It has zero effect on the initial POST response time.

2. **Each GET /api/runs/{id} poll during the "handler runtime" is a fresh short request (measured: max 33 ms, p95 33 ms).**
   Because the caller opens a NEW HTTP connection for each poll — no HTTP session is held open across the handler duration. The caller's socket completes and closes on every poll. A 30-min production handler would produce a series of the same ~30ms polls over 30 minutes, not one 30-min-long request.

3. **The state transition to `Completed` is observed on the next poll after it lands (measured: 12 `Running` observations followed by 1 `Completed`).**
   Because the caller polls at 250ms intervals and the "handler" completes at wall-clock T=3s, the caller sees ~12 `Running` polls before the transition. In production, a 30-min handler would produce ~7,200 `Running` polls at the same 250ms cadence before the transition — the observation logic is identical.

A wall-clock 3-second synthetic and a wall-clock 30-min production handler prove the SAME architectural invariant. The 27-minute-57-second additional wall-clock at production is 27-minute-57-second of NO ACTIVITY on the caller's HTTP socket by definition — that is the fire-and-forget contract.

**What compression does NOT prove**: that real BFF `IJobHandler` bodies (H2a Bicep, H6 solution import, etc.) actually complete within 30 minutes on live Azure infrastructure. That is the concern of Phase F E2E acceptance (task 089), Sprk.Provisioning.ControlPlane.Tests.ServiceBusSmokeTests + CosmosSmokeTests, and the per-handler unit tests. Scenario 2 here is the ARCHITECTURAL invariant that the L2 REST layer NEVER blocks on handler execution.

**Escalation trigger** (per POML `<escalation>`): if any handler exceeds 30 min in production without completing, that is a handler-side bug, not a load-test-framework concern — the framework survives regardless.

- Latency budget is measured against the endpoint's OWN work over an in-process TestServer. The FR-22 <100 ms budget is a production target on the deployed L2 App Service; network round-trips to real Cosmos + Service Bus are exercised by the sibling `NightlyTests` + `SmokeTests` projects.
