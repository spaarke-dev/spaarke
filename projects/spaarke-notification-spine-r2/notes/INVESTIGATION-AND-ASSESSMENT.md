# spaarke-notification-spine-r2 — Investigation & Assessment

> **Created**: 2026-08-20 by `spaarke-notification-spine-r1` (hydration hand-off).
> **Status**: Pre-spec investigation. This document is the substance the future `design-to-spec` run consumes; it is NOT itself a spec.
> **Predecessor**: [`spaarke-notification-spine-r1`](../../spaarke-notification-spine-r1/README.md) built the spine backend (Layers A–D, ADR-047) and shipped it to master.
> **One-line**: Rebuild the proactive-suggestion **surface** — which was removed after r1 — as **OOB Dataverse notifications** (native bell), generated by a **scheduled job**, deduped on a **7-day** window, whose click opens the record in a **modal**.

---

## 1. Executive summary

The r1 notification spine is **live and correct on the backend**: durable outbox, SignalR delivery, three REST endpoints (negotiate / pending / dismiss), an idempotent Daily-Briefing suggestion producer, and a live `communication-arrived` UI consumer. **But the proactive-suggestion *renderer* built in r1 (tasks 051/052) was subsequently removed** by `spaarkeai-assistant-enhancements-r2` (FR-E1). Net effect today: **`suggestion` outbox rows are produced but nothing displays them.**

Separately, even when the renderer existed, suggestions were only ever *produced* on the **interactive Daily-Briefing render** — a user who never opens the briefing got no suggestions at all.

r2 fixes **both** gaps with a single, deliberately OOB-native design the owner selected on 2026-08-20:

1. **Surface** = the **native Dataverse notification bell** (`appnotification`), not a custom Assistant card. Nothing to render/maintain in SpaarkeAi; works app-wide.
2. **Generation** = a **scheduled background job** (decoupled from interactive briefing render), so suggestions appear whether or not the user opens the briefing.
3. **Click** = opens the regarding record in a **modal** (center dialog), not navigate-away.
4. **Dedup** = a **7-day re-notify window** keyed on `(owner, kind, regardingRecordId)`, using `sprk_notificationoutbox` as the ledger; must **not repeat** and must **not reappear after dismiss**.

2. **Click behavior**: opens the regarding record as a **modal** (center dialog), not navigate-away / new tab.

## 6. Researcher findings — OOB `appnotification` capabilities

> Full memo: [`.claude/agent-memory/researcher/appnotification-modal-click-schema-2026-08-20.md`](../../../.claude/agent-memory/researcher/appnotification-modal-click-schema-2026-08-20.md) (committed).

**Modal-on-click is natively supported:**
- Set `appnotification.Data.Actions[].data` with `type:"url"` **AND `navigationTarget:"dialog"`** → opens the record in a **center dialog** (equivalent to `Xrm.Navigation.navigateTo` `target:2`).
- Constraint: the modal fires from a **labeled action link** (e.g. a "Review matter" button), **not** the raw title/body click.
- The URL must be a **same-origin `?pagetype=entityrecord&etn=<entity>&id=<guid>`** form. 2026 security blocks bare-relative / `javascript:` / `data:` URLs → silent no-op.
- Action `type`: `url` | `sidepane` | `teamsChat`. `navigationTarget`: `dialog` | `inline` (default, full-page) | `newWindow`.

**Background generation is supported:**
- Directly `Create`-ing `appnotification` rows needs only **Create** privilege (no special `SendAppNotification` privilege).
- Delivery = **MDA shell polling** (on app-start, and on page-nav if >1 min stale) — **not** real-time push. Acceptable for a daily nudge.
- `OwnerId` = **systemuser only**.
- `TTLInSeconds` default **14 days**. `ToastType`: `Hidden` = bell-only / `Timed` = toast pop. `Data` JSON ≤ **5000 chars**.

**Dedup limitation → why the outbox is the ledger:**
- `appnotification` is an **Elastic table with NO read/dismiss state — dismiss DELETES the row.**
- It therefore **cannot** self-dedup or answer "was this already dismissed?".
- **`sprk_notificationoutbox` is the ledger**: key `(owner, kind, regardingRecordId)`, honor `sprk_dismissed` + a 7-day window so a dismissed nudge does not reappear and a shown nudge does not repeat.

## 7. Proposed architecture (agreed direction — to be formalized in spec)

```
 SCHEDULED JOB (daily, per user)
   └─ compute high-priority items (reuse DailyBriefing collector logic, server-side, no interactive render)
        └─ per item:  ground (ADR-039) + gate (ADR-041 / SuggestionGateOptions)
             └─ DEDUP against sprk_notificationoutbox:  skip if a row for (owner, kind=suggestion, regardingRecordId)
                 exists within the 7-day window OR is dismissed-within-window
                  └─ else:  (1) write sprk_notificationoutbox row  [the ledger]
                            (2) write appnotification  [the native bell]
                                 Data.Actions[]: label "Review {Name}",
                                 type:"url", navigationTarget:"dialog",
                                 url = same-origin ?pagetype=entityrecord&etn=<type>&id=<id>
```

**Reuse, don't rebuild:**
- Grounding + gating + idempotency: reuse `DailyBriefingSuggestionProducer` logic (extract the per-item decision so both the interactive producer and the scheduled job share it — avoid a fork per CLAUDE.md §11).
- Ledger: `OutboxService` (add/confirm a "within N days OR dismissed" query helper if `GetPendingAsync` isn't sufficient — dismissed rows must suppress re-notify within the window, which `GetPendingAsync` excludes; a dedicated dedup query is likely needed).
- Bell writer: `NotificationService.CreateNotificationAsync` — **tweak `BuildActionData`** to emit `Actions[].data.navigationTarget="dialog"` + the same-origin `?pagetype` URL shape (today it puts actionUrl/regardingId in `data` but not the modal-action schema).

## 8. Component-justification pre-work (CLAUDE.md §11)

| Candidate new surface | Existing overlap | Extend or new? | Concrete cost-of-doing-nothing |
|---|---|---|---|
| Scheduled job | No existing per-user proactive-suggestion scheduler | **New** (thin) | Without it, users who never open the Daily Briefing get zero suggestions (G2) — a named, reproducible miss. |
| Dedup query helper | `OutboxService.GetPendingAsync` (excludes dismissed/expired) | **Extend** `OutboxService` | Without a "dismissed-within-window" query, a dismissed nudge reappears next run — violates owner decision #5. |
| Bell modal-action shape | `NotificationService.BuildActionData` | **Extend** (tweak) | Without the `navigationTarget:"dialog"` + `?pagetype` shape, click either no-ops (blocked URL) or navigates away (violates decision #2). |
| Client models | `@spaarke/notifications` types + `INavigationService.openRecordModal` | **Reuse** (owner decision #3) | N/A — no new client model. |

**Placement (CLAUDE.md §10):** the scheduled job + writer tweak land in `Sprk.Bff.Api`. A `design.md` **Placement Justification** + **Hot-Path Declaration** (BFF=Y) is required at spec time. Verify publish size ≤60 MB and 0 new HIGH CVE per BFF task.

## 9. Open questions for `design-to-spec`

1. **Scheduler mechanism**: reuse an existing BFF background-work path (`ServiceBusJobProcessor` / a hosted `BackgroundService` / a timer trigger)? Which cadence host is already sanctioned? (Avoid inventing a new scheduler.)
2. **User-set scoping**: which users does the job iterate — all licensed systemusers, or a monitored/opted-in subset? (Cost + privacy.)
3. **Dedup query precision**: exact predicate for "within 7 days OR dismissed-within-7-days" against the outbox; confirm whether a new index/column is needed vs `createdon` + `sprk_dismissed`.
4. **Item source parity**: does the job reuse `DailyBriefingCollector.CollectHighPriorityAsync` directly, or a leaner server-side query? (Reuse preferred; watch for interactive-only assumptions.)
5. **Toast vs bell-only**: `ToastType` `Hidden` (bell) vs `Timed` (pop) for a daily nudge — owner preference?
6. **Retire the interactive producer?** Once the scheduled job exists, does `DailyBriefingSuggestionProducer`'s interactive invocation stay (harmless, idempotent) or get removed to avoid double authorship? (Both share the ledger, so no duplication — but decide intent.)
7. **Expiry/TTL alignment**: outbox `sprk_expiresat` vs `appnotification.TTLInSeconds` (default 14d) vs the 7-day re-notify window — reconcile the three horizons.

## 10. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Job double-writes bell rows if dedup query is wrong | Medium (notification spam — the exact bug r1 UAT hit) | Ledger-first: write the outbox row and dedup on it before the bell write; seam-test the "second run suppresses" + "dismissed-within-window suppresses" cases. |
| Blocked action URL → silent no-op on click | Medium (dead notification) | Enforce the same-origin `?pagetype=entityrecord` shape; test the built URL; never emit bare-relative/js/data. |
| Scheduled job iterates too many users / too costly | Medium | Scope to monitored/high-priority users; measure; cap per-run. |
| New scheduler forked instead of reusing sanctioned background path | Medium (CLAUDE.md §10/§11) | Q1 above — pick an existing host; Placement Justification at spec. |
| BFF publish size / CVE regression | Medium | Per-task publish-size report ≤60 MB; `dotnet list package --vulnerable`. |
