## Overview

R1 built the notification spine backend (Layers A–D, [ADR-047](../../.claude/adr/ADR-047-notification-action-spine.md)) and shipped it to master. R1 also built an in-Assistant proactive-**suggestion renderer** (tasks 051/052) — which was **subsequently removed** by `spaarkeai-assistant-enhancements-r2` (FR-E1). R2 rebuilds the proactive-suggestion **surface** the way the owner chose on 2026-08-20: as **OOB Dataverse notifications** (the native bell), generated by a **scheduled job** (not only on interactive Daily-Briefing render), deduped on a **7-day** window using `sprk_notificationoutbox` as the ledger, whose click opens the regarding record in a **modal**.

## Problem Statement

Two gaps, both live today:
1. **No renderer** — the spine produces `suggestion` outbox rows, but the r1 renderer that displayed them was removed (`spaarkeai-assistant-enhancements-r2` FR-E1). Rows are produced-but-invisible.
2. **Interactive-only production** — the `DailyBriefingSuggestionProducer` runs only on `POST /api/ai/daily-briefing/render`; a user who never opens the briefing gets no suggestions at all.

## Solution Summary (agreed direction — to be formalized)

A **scheduled BFF job** computes each user's high-priority items server-side, grounds + gates each (reusing the r1 producer logic), dedups against `sprk_notificationoutbox` on a **7-day** window keyed `(owner, kind, regardingRecordId)` (honoring `sprk_dismissed` so a dismissed nudge never reappears in-window), then writes **both** an outbox ledger row **and** a native `appnotification` whose action opens the record in a **modal** (`navigationTarget:"dialog"` + same-origin `?pagetype=entityrecord` URL). Reuses the outbox + `NotificationService` + existing client models; **no new push channel, no new Assistant card**.

## Graduation Criteria (draft — refine at spec)

- [ ] **Scheduled job** produces grounded+gated suggestions per user, independent of interactive briefing render.
- [ ] **OOB bell**: each admitted item writes an `appnotification` whose labeled action opens the regarding record in a **modal** (verified `navigationTarget:"dialog"` + same-origin `?pagetype` URL).
- [ ] **Dedup**: a second run within 7 days does **not** re-notify the same `(owner, kind, regardingRecordId)`; a **dismissed** nudge does **not** reappear within the window (seam-tested).
- [ ] **Ledger-first**: outbox row written before the bell row; correctness preserved if the bell write fails.
- [ ] **Reuse, no fork**: grounding/gating shared with the r1 producer (CLAUDE.md §11); no second push channel; no re-added SpaarkeAi card.
- [ ] **BFF hygiene**: Placement Justification + Hot-Path Declaration (BFF=Y); publish ≤60 MB; 0 new HIGH CVE.
- [ ] Docs updated (this architecture + user guide) once the surface is live.

## Scope

### In Scope
- Scheduled per-user proactive-suggestion job (decoupled from interactive render).
- `appnotification` writer with the modal-action shape (tweak `NotificationService.BuildActionData`).
- Outbox-as-dedup-ledger, 7-day re-notify window (extend `OutboxService` with a dismissed-within-window query as needed).
- Reuse of r1 grounding/gating (extract the shared per-item decision).

### Out of Scope
- Any second push/delivery channel or a re-added in-Assistant suggestion card (hard MUST NOT — ADR-047).
- Communication notifications (`communication-arrived` is live and unaffected).
- New client-side models (owner decision #3 — reuse shared-lib models).
- ADR-047 promotion Proposed→Accepted (an r1-090 / owner call).

## Key Open Questions (see Investigation §9)

Scheduler host (reuse sanctioned background path), user-set scoping, exact dedup predicate, item-source reuse vs leaner query, toast-vs-bell, whether to retire the interactive producer, TTL/expiry reconciliation.
