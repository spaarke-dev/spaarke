## 6. BFF outbound

Terms. **OBO** = on-behalf-of: the BFF exchanges the caller's inbound bearer for a downstream token carrying the caller's identity. **App-only** = the BFF acts as itself. **UAMI** = the user-assigned managed identity bound to the App Service. **MI-FIC** = managed-identity federated identity credential: the UAMI's token is presented as a client assertion to prove the BFF's app registration, so no secret or certificate is needed. **Impersonation** = an app-only Dataverse call carrying `MSCRMCallerID = systemuserid`, so Dataverse evaluates row security as that user.

### 12a. Model 1 client sign-in — Teams tab, external SPA workforce plane, Office add-ins

What the code and live configuration show:

1. **Client tenancy today.** The Teams tab and the browser workforce plane sign in as the BFF's own registration `1e40baad…` against `/organizations` with no tenant pin or `domainHint` (`src/client/external-spa/src/auth/msal-config.ts:147-159`). That registration is `AzureADMultipleOrgs` — VERIFIED LIVE x04 A1 — so a home-tenant account *can* sign in once that tenant's admin consents (the multitenant premise that was [LIVE?] in x01 #8.1 is now settled). [ADDED by check: the sign-in itself is Entra behaviour, not code — per-tenant admin consent and the issued claims remain NEEDS LIVE TEST (item 6 and item 7 below; x03 F3, I7, A4).] The Office add-in signs in as the single-tenant `c1258e2d…` (`AzureADMyOrg`, x04 A6) against a **tenant-pinned** Spaarke authority baked at build (`AuthService.ts:80-98`; `deploy-office-addins.yml:67`); the production client `1958aec2…` is also `AzureADMyOrg` (x04 A7). 3. **NAA + popup fallback.** Teams: NAA primary, `acquireTokenPopup` brokered, `getAuthToken()` fallback (`msal-auth.ts:283-399`); never a redirect. 4. **Spaarke-tenant authority and the two token shapes.** For a U2 guest the Dataverse-hosted clients and the add-in pin the Spaarke tenant, so the expected token is `tid` = Spaarke, `acct=1`, `oid` = the guest object; the Teams/SPA plane leaves the choice to the IdP session, so the token may be minted by the home tenant (`tid` = home, `oid` = home). The BFF accepts or rejects a home-tenant issuer by library behaviour — not configured in code — NEEDS LIVE TEST (x01 #1; x03 A4, J1). Once the claims are known the server outcome is deterministic (§5.3): Spaarke-`tid` + systemuser → U1 path; Spaarke-`tid` without systemuser → `Guest` where Spaarke's tenant is listed (dev: it is, x04 §2) else `ForeignTenant`; home-`tid` + `acct=0` + listed → `Member` (email-bind/create a contact); home-`tid` unlisted → `ForeignTenant`. On L2-provisioned stamps the list can never contain Spaarke's tenant (`CustomerWorkforceTenantsRule.cs:22-23,100-105`), so the `Guest` outcome is unconfigurable there and the designed Model 1 contact-only path is "customer home tenant + `acct=0`" — i.e. a home-tenant token, which is exactly the shape whose BFF acceptance is unproven.
5. **Scope.** The dev app exposes `user_impersonation`, `access_as_user`, `access_as_external_user` and `SDAP.Access` (x04 A1); H3-created stamp apps expose only `user_impersonation` (`GraphAppRegistrationProvisioner.cs:523`); the Teams tab and Copilot request `access_as_user` (`.env.development:24`; `spaarke-bff-openapi.yaml:1308`). A stamp app therefore cannot serve the Teams tab or Copilot as built.
6. **Pre-authorization and consent.** `c1258e2d…` (dev add-in), `170c98e1…` (PCF client), the Teams client ids and Azure CLI are pre-authorized on the dev BFF app (x04 A1); `appRoleAssignmentRequired` is false everywhere (x04 §1). Per-tenant admin consent for a multitenant app and Teams org-catalog publication are NEEDS LIVE TEST (x03 F3, I7).
7. **Still unproven**: the real `tid`/`acct`/`idp`/`aud` of each surface's token (x03 A1–A6); default-scheme issuer acceptance for home-tenant and Model 2 tokens (J1); guest OBO and `systemuser.azureactivedirectoryobjectid` for guests (D3, E1); NAA/broker behaviour per host (F2, F3); the Teams audience in non-dev environments (C1); the Copilot vault registration and consent (A6).
