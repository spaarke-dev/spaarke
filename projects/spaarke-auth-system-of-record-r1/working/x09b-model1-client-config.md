### 1.3 Can one add-in package serve two customer stamps today? — No

Every value that selects a backend is a webpack build constant:

- `src/client/office-addins/webpack.config.js:23` `REQUIRED_ENV_VARS = ['ADDIN_CLIENT_ID','TENANT_ID','BFF_API_CLIENT_ID','BFF_API_BASE_URL']` (the build refuses without them); `:422-425` `DefinePlugin` bakes them as `process.env.*`; `:128,370-373` rewrites the manifest `resource` to `api://${BFF_API_CLIENT_ID}`.
- `outlook/taskpane/index.tsx:23-26` and `word/taskpane/index.tsx:19-22` build `CONFIG` from those constants (fallbacks hard-code the dev BFF `1e40baad…` and `https://spaarke-bff-dev…`).
- `shared/services/AuthService.ts:66-72` `AuthConfig = {clientId, tenantId?, bffApiClientId?, redirectUri?, fallbackRedirectUri?}` — no `authority`, no `apiBaseUrl`; `:79-87` derives `bffApiScope = api://${bffApiClientId}/user_impersonation` and resolves the authority from `tenantId`; `:89-91` constructs ONE `OfficeNaaStrategy` with that resolved config. In `@spaarke/auth`, `OfficeNaaStrategy.ts:415-416,446-447` create the MSAL client with a fixed `clientId`/`authority`; only the scope is per-acquire (`:219`). So switching customer under the same authority (Model 1) needs a new scope, not a new MSAL instance — consistent with the word-add-in reply.
- `outlook/taskpane/index.tsx:233-236` `apiClient.configure({ baseUrl: CONFIG.bffApiBaseUrl, bffApiClientId })`; `shared/services/ApiClient.ts:11-15` "the single `bffApiScope` configured at `initialize()` time… `getAccessToken()` ignores any scope argument".
- `shared/taskpane/App.tsx:342` and `:890` read `process.env.BFF_API_BASE_URL` directly (not via `apiClient`) — a second place the base URL is baked.

Result: one build ⇒ exactly one audience (`api://{BFF_API_CLIENT_ID}/user_impersonation`) and one base URL. A stamp BFF validates `AzureAd:Audience = api://{its own appId}` (H4b `AzureAd__ClientId ← from-h3-output:bff_app_client_id`, `manifest.yaml:646-647`), so a token minted for the dev/other audience is a 401 (g14 §1 "BFF validation").

### 1.5 Pre-authorization on each customer BFF app — handled, with two caveats

- Handled: H3 sets `api.preAuthorizedApplications` to exactly `EntraAppRegOptions.PreAuthorizedClientAppIds` on the enabled `user_impersonation` scope and re-runs are idempotent ("A second run with the same inputs sends no PATCH", `GraphAppRegistrationProvisioner.cs:90-94` branch header). Default list = `1958aec2…` only (Bicep above). Error if the app has no enabled `user_impersonation` scope (`:626-634`).
- Caveat 1: pre-authorization is **scope-bound** (`DelegatedPermissionIds = [user_impersonation id]`, `:656-664` branch). A client requesting any other scope (`access_as_user`) is not pre-authorized — see Q3.
- Caveat 2: the **dev** add-in `c1258e2d…` is pre-authorized only on the dev BFF, by hand (g14 §1 "by hand (runbook 004-entra-naa-registration.md)"; x04 A1). A dev build pointed at a stamp would prompt for consent (and would 401 anyway on audience).

### Plain-language summary (Q1)

The "one add-in for everyone" idea is an owner-approved design, not a built thing. What is built on master: the provisioning side pre-authorizes the production add-in app on every customer BFF, registers the customer's Dataverse origin as the SPA redirect, and lists `addins.spaarke.com` in every stamp's CORS. What is not built anywhere: the Spaarke directory endpoint (the service, its app registration, the group assignment step, and the registry column for the BFF app id), the add-in's runtime customer picker, and any production build or deploy job for the add-in. Today the add-in bakes one tenant, one add-in client, one BFF audience and one BFF URL at build time, in webpack and in two places in the pane code, so one package can reach exactly one backend; a second customer stamp would reject its tokens (wrong audience) and it could not even address it (wrong URL). The production site and the production add-in app exist live but are empty/unused, and the owner has decided not to deploy to production until the directory exists.

To add `access_as_user` to H3 you would change those three places (expose a list; reconcile each; carry both scope ids in `DelegatedPermissionIds`) plus the tests. It is a small diff, but it also makes every pre-authorization two-scope and leaves the platform with two names for the same permission forever. Re-running H3 on existing customer apps would be the normal idempotent reconcile — and today there are **no** existing customer apps (x04 §1), so no migration burden exists yet.

### 3.2 Does the BFF care which scope name is in `scp`? — No

- Token validation: `AddMicrosoftIdentityWebApi` with `AzureAd:ClientId`/`Audience` (`AuthorizationModule.cs:47-49`, per a09/g14); no `RequiredScope`/`RequireScope`/`VerifyUserHasAnyAcceptedScope` anywhere in `src/server/api/Sprk.Bff.Api` or `src/server/shared` (grep).
- Every `scp` read is a **presence** check or logging: `Api/Filters/KeylessProofAuthorizationFilter.cs:49-50,108` (a token WITH `scp` acts for a user and is refused on the app-only route); `src/server/shared/Spaarke.Core/Auth/CallerIdentity.cs:113,203-248` (delegated vs app-only by presence, "presence (not value)"); `Infrastructure/Logging/AuditEnrichmentMiddleware.cs:42-59`; `Infrastructure/DI/MiddlewarePipelineExtensions.cs:143-148` (log line). The former "scp contains `admin`" branch of the `SystemAdmin` policy was removed by UAC-r2 task 165 (`AuthorizationModule.cs:364-383`).
- Tests assume `scp = user_impersonation` (`tests/integration/auth/UnifiedAccessControl/IdentityBinding/IdentityBindingTestKit.cs:42`; `tests/unit/Spaarke.Core.Tests/Auth/CallerIdentityTests.cs:47,186,330`; `tests/integration/contract/Api/Platform/KeylessProofEndpointContractTests.cs:57`).
- `/api/config/client` publishes `api://{clientId}/user_impersonation` (`ConfigEndpoints.cs:134`); the directory contract's `scope` field would do the same.

### 3.4 Recommendation (simplest consistent option)

**Have every client request `user_impersonation`; do not add `access_as_user` to H3.**

- Zero BFF change (the BFF never inspects the scope value); zero H3 change; matches `/api/config`, the directory contract, the T257 correction and R3's proposal.
- Client cost is configuration: `VITE_TEAMS_MSAL_BFF_SCOPE` becomes `api://{resolved}/user_impersonation` (and, after the directory lands, is no longer a build value at all); the Copilot OpenAPI scope changes per T257.
- Two caveats, both dev-only and both live changes: (i) the dev BFF `1e40baad…` pre-authorizes the Teams first-party clients and the broker **on `access_as_user`** (teams-app-r1 DOC CLAIM, `r2-shared-entra-app-coordination.md:43-45`; x04 A1 lists the client ids but not the per-scope ids), so switching the **dev** Teams tab to `user_impersonation` may need those dev pre-authorizations extended to `user_impersonation` — or becomes moot once the dedicated client app replaces them; (ii) `access_as_user` can stay exposed on the dev app for the existing Copilot package until it is repointed.
- If the owner nevertheless wants `access_as_user` on stamps, the H3 change is the three sites in §3.1 and it must land **before** the first customer run (T186) to avoid a reconcile on live apps.

### Plain-language summary (Q3)

Customer BFF apps expose only `user_impersonation`; the Teams tab and the Copilot package ask for `access_as_user`, which simply does not exist on a customer app, so those clients could not get a token for a stamp as built. The BFF itself never looks at the scope name — it only checks that a scope claim exists to tell a user token from an app token — so nothing on the server prefers one name. The cheapest consistent fix is to have the Teams tab and Copilot ask for `user_impersonation` like every other client (a config change; the Copilot design already made that correction, and R3 has proposed the same), rather than teaching H3 to expose and pre-authorize a second scope. The only wrinkle is the dev tenant, where the Teams pre-authorizations were set up on `access_as_user` by hand.

## Q5 — How coordination notes travel between projects

Convention observed in `projects/customer-provisioning-orchestration-r1/notes/coordination/` (12 files, `YYYY-MM-DD-{to|from}-{project}[-N].md`; `-2`, `-3`, `-4` for further messages the same day):

- **The sender writes `to-<project>` in its own `notes/coordination/`.** All provisioning `to-` files are provisioning commits by `spaarke-dev` on the provisioning branch: `02e6036ad` (2026-10-07, first word-add-in message), `9ee442b3c` (`to-external-access-r3.md`), `08783f680`, `4d41cb026`/`a684795e2` (`to-word-add-in-r1-4.md`), `eecbfe820` (2026-10-09, `to-external-access-r3.md`). R3 likewise writes its outgoing notes in its own tree: `notes/t240-auth-coordination-response.md` (`0797490bf`, 2026-10-07) and `notes/coordination/2026-10-09-to-provisioning-t240d-review.md` (`b5d7bf2ca`); the word add-in writes `notes/coordination/2026-10-08-to-uac-r2-model1-guests.md` (`0b2aef2bd`).
- **The receiver writes the `from-<project>` file as a verbatim copy** after the owner relays it; the receiver's own commit carries it. Evidence: `2026-10-07-from-external-access-r3.md:1` begins `<!-- Verbatim copy of spaarke-SPA-external-access-platform-r3 notes/t240-auth-coordination-response.md (2026-10-07), relayed by the owner. Its relative links point into that project. -->` and is in provisioning commit `08783f680`; `2026-10-07-from-word-add-in-r1.md:3` "Relayed by the owner, verbatim" in provisioning commit `9ee442b3c`. The sender's git author is never on the receiver's `from-` file.
- **The transport is the owner, by hand** (copy/paste between sessions), sometimes via a GitHub issue: "Relayed by the owner" opens every provisioning `to-` note; "The answers go back through the owner" closes the word add-in's note; the UAC-r2 note header says "via the owner or a #1094 comment (ask the owner first)" and the 2026-10-07 UAC-r2 message references issues #1363/#1364. Provisioning's 2026-10-09 note asks R3 to "reply in your project notes and tell the owner".
- **Not every receiver keeps `from-` copies.** The word add-in absorbed provisioning's three 2026-10-07 messages into its numbered notes 113/114/115 (each opens with "Context: customer-provisioning-orchestration-r1 …" / "Finding (provisioning, 2026-10-08)"); R3 absorbed provisioning's messages into `design.md` §4.6 and §5 of its reply note. Provisioning has no `from-external-access-r3` copy of R3's 2026-10-09 review yet (only its own `to-` note), so that reply is at present visible only in the R3 tree.
- **Decisions that result are re-stated in each project's own decision record** (`decisions.md` §1 "Coordination notes | Hand-offs owed to/from other projects | `coordination/`"; R3 `design.md` §4.6 "Confirmed decisions"; add-in note 114 "Owner decisions").

### Plain-language summary (Q5)

There is no automated channel. A project writes its outgoing message as a dated `to-<other-project>` file in its own `notes/coordination/` folder and commits it; the owner copies the text into the other project's session; that project (the receiver) pastes it into its own tree as a `from-<sender>` file (or summarises it in its numbered notes) and commits that itself. Replies go back the same way. So the `from-…` files are written by the receiver, not the sender, and are verbatim copies; the sender's original stays in the sender's project. Anything decided is then copied into each side's own design/decision notes.
