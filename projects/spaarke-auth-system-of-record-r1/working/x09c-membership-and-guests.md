## Q1 — ADR-034 membership vs Dataverse's own access for a Dataverse system user on the SPA / Teams (`/api/v1/external/**`)

### Plain-language summary

When a licensed Spaarke user (a `systemuser`) opens the external SPA or the Teams tab, the BFF does **not** ask Dataverse "which records can this person see?". It computes an *approximation* from a fixed list of columns: records the person **owns**, records owned by a **team they are in**, records owned by **their own business unit**, plus records where their **linked contact** (or an organization that contact belongs to) is named in a reviewed "Assigned …" column. Every hit is given Read+Write+Create. Their linked contact's explicit external grants are added, then the Secure / Restricted / No-Access vetoes are applied.

That gives the **same answer as Dataverse** only in the "ordinary" cases — the person owns the record, or their team owns it, or it sits in their own BU and they hold a BU-depth Read role. It **differs** whenever Dataverse's answer depends on something the column list cannot see: **role depth** (a Basic/User-depth user still "matches" every record in their BU → over-grant), **parent/child or organization depth** (records in child or sibling BUs never match → under-grant), and **shares** (a POA share written by Manage Access "+ User", by the secure-child synchronizer, or by hand in the model-driven app is invisible to the SPA → under-grant; this includes shares on **secure** records). The SPA client has no code of its own for system users — the "handled by the SPA" recollection matches the *server-side* workforce branch in the BFF, not anything in `src/client/external-spa`. ADR-028 A5 was written to replace the approximation with Dataverse's own answer (an impersonated id-only query); the component that does that (`ImpersonatedRootSetSource`) is built, registered, cache-wired, dev-impersonation-capable and canary-gated — but **no code reads its answer**. The swap is UAC-r2 task 036, status `pending`, queued behind 136 and 099.

### 1.1 What `MembershipResolverService.ResolveAsync(systemUserId, entityType, accessConferringOnly: true)` computes — VERIFIED IN CODE

Pipeline (`src/server/api/Sprk.Bff.Api/Services/Ai/Membership/MembershipResolverService.cs:180-440`):

1. **Cache** — `tenant:{tid}:membership-resolved:{systemUserId}:{entityType}:{optionsHash}:v{n}`, 2-minute TTL, never cached when a sub-read faulted (`:1-23`, `:249-258`, `:412`).
2. **Discovery** — `IMembershipFieldDiscoveryService.DiscoverAsync(entityType)` returns one descriptor per Lookup column on the entity whose target is one of the six canonical identity tables `systemuser, contact, team, businessunit, account, sprk_organization` (`MembershipOptions.cs:250-257`), with the polymorphic Owner column emitted **twice** — `ownerid → SystemUser` and `ownerid → Team` (`MembershipFieldDiscoveryService.cs:108-111, 292-312, 556-567`). Audit columns (`createdby`, `modifiedby`, …) are globally excluded (`MembershipOptions.cs:39-46`).
3. **Access-conferring filter** (only because the caller passed `accessConferringOnly: true`; `:295-299`) — `FilterToAccessConferringRoles(entity, discovered, includePlatformOwnership: true)` (`:689-763`) keeps exactly:
   - the three **platform ownership columns by name**: `ownerid`, `owningteam`, `owningbusinessunit` (`:666-668`, admitted "structurally, ahead of the registry", `:722-737`); and
   - the **registry-listed** Contact- or Organization-typed columns for that entity (`:739-762`). The registry default (`MembershipOptions.cs:300-345`) is, for `sprk_matter` and `sprk_project`: `sprk_assignedattorney1/2`, `sprk_assignedparalegal1/2`, `sprk_assignedtoexternal`, `sprk_assignedtointernal` (Contact) and `sprk_assignedlawfirm1/2` (Organization); for `sprk_workassignment` the same plus `sprk_assignedlawfirmattorney1` and `sprk_assignedto` (Contact).
   - **Dropped**: every maker-authored `systemuser`/`team`/`businessunit`/`account` lookup (e.g. a `sprk_reviewer → systemuser`) and every unregistered contact/org column (`:738-745`, pinned by `ResolveAsync_AccessConferringOnly_MakerAuthoredSystemUserLookup_ConfersNothing`, `:759`).
4. **Identity normalization** — `IIdentityNormalizationService.ResolveAsync(systemUserId)` → `PersonIdentity` (`PersonIdentity.cs:71-92`): `SystemUserId`; `ContactId` = `systemuser.sprk_primarycontact`, else the contact bound to the user's Entra `oid` via `contact.sprk_externalobjectid` (`IdentityNormalizationService.cs:173-190, 339-392`); `TeamIds` = `teammembership` rows for the user (`:394-445`, fails **soft** to empty); `BusinessUnitId` = the user's **own** `systemuser.businessunitid` (`:271-288`); `AccountId` = linked contact's `parentcustomerid` when it is an account (`:450-484`); `OrganizationIds` = the contact's active `sprk_organization` memberships (`:493-537`). **No roles, no role depth, no BU hierarchy, no POA shares are read anywhere in this pipeline.**
5. **One FetchXml** against `entityType` (`BuildFetchXml`, `:1028-1200`): `<filter type='or'>` with one condition per (descriptor, identity value): `SystemUser` columns = `SystemUserId`; `Contact` = `ContactId` (skipped with a `member_skipped … no_systemuser_mapping` warning when the user has no linked contact, `:1115-1150`); `Team` = each `TeamId`; `BusinessUnit` = `BusinessUnitId`; `Account` = `AccountId`; `Organization` = each `OrganizationId` (`:1109-1177`). Ordered by primary id, paged with count/page + paging cookie (`:1056-1096`).
6. Result = de-duplicated ids + a `ByRole` map; `MembershipTermRights = Read | Write | Create` is stamped on every id by the caller, a constant "on purpose: membership confers no per-record level" (`AccessibleRecordSetService.cs:470-485`).

So, in plain words, for a `sprk_matter` the query is: *matter.ownerid = me OR matter.owningteam ∈ my teams OR matter.ownerid ∈ my teams OR matter.owningbusinessunit = my BU OR matter.sprk_assignedattorney1 = my contact OR … OR matter.sprk_assignedlawfirm1 ∈ my contact's organizations*. Nothing else.

### 1.3 When it gives the SAME answer as Dataverse, and when it differs

Dataverse's own answer for a user = (ownership ∪ team ownership ∪ BU/parent-child/org **role depth** ∪ POA shares ∪ hierarchy) × the user's privileges. The approximation reads ownership columns and a contact link only. **Same answer** (for a Spaarke staff user with the usual `Spaarke Basic User`-style role):

- S-A — the user **owns** the record (`ownerid = me`) and holds at least User-depth Read → both grant. VERIFIED IN CODE (`:1109-1112`) + Dataverse semantics (ASSUMPTION about the role, not read live).
- S-B — the record is **owned by a team the user is in** and that team (or the user) holds Read → both grant (`:1157-1160` Team leg of `ownerid`/`owningteam`).
- S-C — the record is owned by a colleague in the **user's own BU** and the user holds **BU-depth** Read → both grant (`:1163-1167`).
- S-D — the user is named on a registry "Assigned …" column through their linked contact → the SPA grants via Term 1; Dataverse grants too **only because** `AssignedAccessMaterializer` writes a POA share for a linked eligible user (`AssignedAccessMaterializer.cs:1448-1470`, a07 T48) — i.e. the same answer by two different mechanisms; on a Restricted record the materializer writes no share, so the model-driven app may deny while the SPA grants (unless the user is flagged external).

**Differs** — concrete scenarios (each VERIFIED IN CODE on the SPA side; the Dataverse side is standard platform behaviour, not re-tested live):

| # | Scenario | Dataverse (model-driven app) | SPA / Teams (ADR-034 approximation) | Direction |
|---|---|---|---|---|
| D-1 | Matter owned by a colleague in the user's **own BU**; the user holds only **User-depth** (Basic) Read | denied | **granted** — `owningbusinessunit = my BU` matches regardless of depth (`MembershipResolverService.cs:1163-1167`); the code itself names this: "a business-unit column match OVER-grants to users whose role depth does not actually reach the record" (`ImpersonatedRootSetSource.cs:31-34`) | over-grant |
| D-2 | Matter in a **child or sibling BU**; the user holds **Parent:Child** or **Organization**-depth Read | granted | **hidden** — `owningbusinessunit` is compared to the user's own BU id only; there is no BU-hierarchy walk and no role read (`IdentityNormalizationService.cs:284`; `:1163-1167`) | under-grant |
| D-3 | Record **shared** to the user (or to an access team they are in) — Manage Access "+ User" (`/share-user` writes a POA row and nothing in `sprk_externalrecordaccess`, `InternalShareEndpoints.cs:26-28, 525`), the Dataverse Share dialog, or the secure-child synchronizer | granted | **hidden** — no term reads `PrincipalObjectAccess`; "it silently MISSES records reachable only through a POA share" (`ImpersonatedRootSetSource.cs:33-34`; ADR-028 A5 `:278-283`) | under-grant |
| D-4 | A **secure** record: owned by the `Secure Record Owners` team in the Secure Record BU, nobody is placed in that unit (PROV D30, OWNER DECISION 2026-10-09), internal access is granted by explicit POA share | granted to the shared user | **hidden** unless the user is also on a registry "Assigned …" column (Term 1 via the contact) or holds a contact grant (Term 2) — the share itself is invisible (D-3) | under-grant on exactly the records that matter most |
| D-5 | Record owned by a team the user belongs to **whose roles do not reach it** (e.g. a BU default team with no Read role after the 2026-09-09 clean-up, UAC-r2 TASK-INDEX `:636`) | denied | **granted** — team membership alone matches `owningteam`; the code warns that "a business unit's DEFAULT team contains every user in the unit" (`MembershipResolverService.cs:839-841`) | over-grant |

Net: for the owner's own Spaarke staff account the SPA is "correct" today only to the extent that (a) the records they care about are owned by them, by their teams or inside their own BU **and** (b) they hold a role whose depth happens to equal "my BU". Anything granted by share or by deeper roles is missing; anything in their BU beyond their depth leaks. Whether the owner's dev account is in state (a)+(b) is NEEDS LIVE TEST (UAC-r2 F11 says the owner's dev guest holds `Spaarke Basic User` at Deep depth in the root BU — `UAC-r2/notes/session27-owner-decisions-and-research.md:63`, DOC CLAIM).

## Q2 — Tier-1 "role-to-module map"

### Plain-language summary

`sprk_approlemodulemap` is a tiny admin table: each row says "an Entra **app role** called X unlocks SPA **module** Y". The BFF reads the caller's `roles` claim from the workforce token and looks those names up in the active rows; the module codes it finds are the tabs the SPA may show. The table is maintained by hand (it sits in the Matter Management app's site map); nothing in the repo seeds it, and the only seeding on record is a note from task 072 that two rows (`FrontDoorUser → legal-front-door`, `FrontDoorUser → policy-library`) were created on dev with the MCP on 2026-08-10. The dev BFF app defines only the `Admin` app role, so **no workforce token can carry `FrontDoorUser`**; a workforce user therefore gets an empty entitlement list on dev. The SPA treats an empty list as "no gated tabs" (it does not fall back to the mock, because a 200 with `[]` is not an error) — the owner would see Quick Start plus the ungated Messages widget in the library and nothing else; only a thrown error (401/403/network) triggers the mock "Sam Rivera" tabs. For CIAM callers the blanket `assigned-work` entitlement is what the owner chose ("Option B", 2026-08-10) and the only thing implemented (the per-contact table from the same design note was never created), but it contradicts ADR-028 A3's "never infer Tier-1 from the plane" rule — the SoR carries it as M-1, a path-A exception candidate.

### 2.4 CIAM blanket — intended design or a problem?

- **Intended by the owner** (DOC CLAIM in code + notes): "Option B (owner, 2026-08-10) — resolved WITHOUT ever fabricating a Contact for an internal user … CIAM: BLANKET-entitled to the outside-counsel module set — there is no per-Contact external entitlement table. Record VISIBILITY is governed purely by Tier-2 grants" (`ModuleEntitlementResolver.cs:17-27`; `task-072-deviations.md:20-27`). The task-020 design proposed a per-contact `sprk_moduleentitlement` table (`module-entitlement-schema-decision.md:30-45`); it was **never created** (no entity folder in `SpaarkeMaster/Entities`, zero code references).
- **Contradicts the ADR as written**: ADR-028 A3 — "MUST NOT infer Tier-1 module entitlement from the fact of authentication, from the identity plane, or from Tier-2 record access" (`.claude/adr/ADR-028-spaarke-auth-architecture.md:124`). SoR §11 **M-1**: "Tier-1 inferred from the plane for CIAM (blanket `assigned-work`) … Open (path-A candidate)"; §12b R37: "either amend A3 to allow blanket Tier-1 for CIAM or require the map read".
- Practical risk today: low — the five CIAM widgets carry no `requiredEntitlement` at all (`widgetRegistry.ts:187-241`), so the blanket value is not even what gates them; the plane is. The real exposure is the same on both planes: Tier-1 is UX data; record visibility is Tier-2 (`ModuleEntitlementResolver.cs:29-31`). So: not a security defect, but an un-ratified deviation that the ADR amendment (§12b) must either sanction (path A/B) or close by adding a per-contact map.

## Q3 — Model 1 guest classification

### Plain-language summary

(a) **`sprk_isexternal` is set by nobody in code.** The column is a Yes/No on the user record, default No, visible on the System User form. Provisioning's user step (H11) invites guests and makes them Dataverse users but never touches the flag; the BFF reads it in 16 places and writes it in none; the only writer is an operator script that flags every `#EXT#` guest — the step G1 says is wrong under Model 1. "Set at user setup time" is therefore either the manual form field or the script; no automated setup path does it (the dev test guest actually reads **No**). ## Q4 — A licence-free customer employee (U3) in Model 1: what must happen for them to use the SPA / Teams?

### Plain-language summary

Today there are two shapes and only one of them is coded. **(A)** The employee signs in from their own company tenant: the SPA's workforce plane uses the multitenant `/organizations` authority, the token carries the customer's `tid` and `acct = 0`, the member test admits them, and a contact is created or email-bound. This is what the code was designed for — but the BFF is configured for Spaarke's single tenant and sets no issuer list, so whether it accepts a home-tenant token is unproven, and it contradicts the owner's (provisional) decision that Model 1 workforce sign-in uses Spaarke's tenant. **(B)** The employee is invited as a B2B guest in Spaarke's tenant (no Dataverse user) and signs in against Spaarke's authority: the token validates fine, but the member test returns `Guest` (dev) or `ForeignTenant` (stamp) and they are denied. Option B is the one consistent with the owner's decision (and with the add-in, provisioning D2 and the observed guest token); making it work needs a small, contained change to the member test (and its claims record) plus the matching binder rule — owned, per the owner's 2026-10-08 direction, by word-add-in-r1 task 126 after UAC-r2 signs off, with provisioning already supplying the tenant list the rule needs.

### 4.1 Option A — home-tenant token (multitenant BFF app, `/organizations`) → `Member`

- Client: the workforce plane in both hosts targets `https://login.microsoftonline.com/organizations` unless an `authority` override is passed; nothing passes one (`src/client/external-spa/src/auth/msal-config.ts:140-159`; `auth/standalone-plane.ts:13, 56`; `config.ts:100-115` "ONE multitenant app registration (reused `1e40baad-…`)"; no `authority` in `host/TeamsHostAdapter.ts` or `main.tsx`). - Server: the default scheme is `AddMicrosoftIdentityWebApi(configuration.GetSection("AzureAd"))` with `AzureAd:TenantId` = Spaarke's tenant on dev and the intake tenant on stamps; no `ValidIssuers`/`IssuerValidator` is set (`Infrastructure/DI/AuthorizationModule.cs:47-49, 99-167`; a05 `:143, 408`). Whether a token issued by the customer's tenant is accepted is **library behaviour, NEEDS LIVE TEST** (x03 J1; SoR §5.2). The `acct` optional claim must be on the BFF app (dev: yes, x04 `:26`; H3: yes per INCOMING-141 §5).
- Consistency with the owner's decision: **inconsistent.** R3 `design.md` §4.6 item 5 (OWNER DECISION 2026-10-07/08, marked **PROVISIONAL / R3 ON HOLD**): "Workforce authority = Spaarke's tenant (Model 1). R3's current `/organizations` multitenant shape is the **Model 2** path (deferred). Same direction in the add-in ("The add-in signs in to Spaarke's tenant (`TENANT_ID`) — verified working for a guest", `ADDIN/…/CLAUDE.md:285`) and provisioning D2 / G14 ("every Model 1 guest token carries Spaarke's `tid`", `PROV/notes/g14-shared-clients-auth-chain.md:59-60`).
