## 2. How it works (code-level flow)

### 2.1 Flow A — Per-record operation authorization on BFF routes (documents and typed records)

1. A route attaches `AddDocumentAuthorizationFilter("<operation>")`; the filter resolves the caller `oid` via `CallerResolution.ResolveObjectId` and the resource id from route values `id|documentId|containerId|driveId|itemId|resourceId` `[CODE src/server/api/Sprk.Bff.Api/Api/Filters/DocumentAuthorizationFilter.cs:54-73,124-137]`.
2. It builds `AuthorizationContext { UserId=oid, ResourceId, Operation, UserAccessToken = bearer-or-null }` and calls `AuthorizationService.AuthorizeAsync` `[CODE src/server/api/Sprk.Bff.Api/Api/Filters/DocumentAuthorizationFilter.cs:75-100]`.
3. `AuthorizationService` DENIES (`sdap.access.deny.no_caller_token`) when the token is blank — it never degrades to app-only evaluation `[CODE src/server/shared/Spaarke.Core/Auth/AuthorizationService.cs:54-72]`.
4. It fetches one `AccessSnapshot` through `GetCallerAccessAsync` (one of exactly two members touching `IAccessDataSource` — the sibling `GetCallerRecordAccessAsync` calls `_accessDataSource.GetRecordAccessAsync` for arbitrary entity sets and is the one T81's filters use) [CORRECTED by verifier: was "the only member touching `IAccessDataSource`" — the code comment at :75 says "exactly ONE place" but `GetCallerRecordAccessAsync` at :283-285 also calls the data source] `[CODE src/server/shared/Spaarke.Core/Auth/AuthorizationService.cs:76-80,198-226,256-286]`.
5. `IAccessDataSource` is `CachedAccessDataSource` wrapping `DataverseAccessDataSource` `[CODE src/server/api/Sprk.Bff.Api/Infrastructure/DI/SpaarkeCore.cs:107-115]`; the cache key is `{sp|obo}:{oid}:{documentId}` per token `tid`, TTL 60 s, and a `Faulted` snapshot is never stored `[CODE src/server/api/Sprk.Bff.Api/Infrastructure/Caching/CachedAccessDataSource.cs:89,112-113,151-153,170-192]`.
6. `DataverseAccessDataSource.GetUserAccessAsync` exchanges the caller's bearer for a Dataverse token via MSAL OBO (`AcquireTokenOnBehalfOf`, scope `{Dataverse:ServiceUrl}/.default`) using the ordered confidential-client provider `[CODE src/server/shared/Spaarke.Dataverse/DataverseAccessDataSource.cs:225-255,292-303]`, then sets that token on the shared `HttpClient.DefaultRequestHeaders` `[CODE …/DataverseAccessDataSource.cs:298-300]`.

## 8. Defects, risks and inconsistencies

1. **ADR-028 A5 is not implemented (doc/code divergence on a security boundary)** — severity **high**. The workforce systemuser accessible set is still the ADR-034 registry-membership approximation, which the ADR itself says "over-grants BU-matched records past role depth and misses POA-shared records" `[DOC-ONLY .claude/adr/ADR-028-spaarke-auth-architecture.md:278-283]`; `ImpersonatedRootSetSource` is registered and inert `[CODE ExternalAccessModule.cs:268-273]` `[CODE AccessibleRecordSetService.cs:1421-1429,1811-1816]`. Provisioning H11 creates the guest systemuser and roles but not the flag (grep P3/P4) `[CODE grep P3/P4]`; blank means internal everywhere `[CODE SystemUserIdentityResolver.cs:302-316]` `[CODE InternalShareEndpoints.cs:1308-1323]`.
