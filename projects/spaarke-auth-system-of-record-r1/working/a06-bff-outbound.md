## 4. Behavior by user type

### U1 — Spaarke staff (member in Spaarke tenant, licensed systemuser)

- Inbound BFF token has `tid` = Spaarke tenant = `TENANT_ID`; every OBO exchange (Flows C, F1–F4) runs against `login.microsoftonline.com/{TENANT_ID}` with the user's BFF token as `UserAssertion` [CODE GraphClientFactory.cs:96-99,286-293; OrderedCredentialClientProvider.cs:364-367]. - What fails: nothing by construction; a missing/malformed bearer on an OBO path throws `UnauthorizedAccessException` (throwing overload) or denies (non-throwing overload) [CODE TokenHelper.cs:13-56]. The actual claim contents of the OBO result (`upn`/`oid` preserved) are live behaviour [LIVE?].

- [ADDED gap-fill] **SPE documents (Flow M)**: on every id-keyed document route the staff member's token is exchanged only for the Dataverse rights check (F1/F3); the SPE read/write runs as the BFF, so NO container role is required to preview/download/open-link/upload-against-a-record [CODE FileAccessEndpoints.cs:23-32,189-197; OBOEndpoints.cs:180-181,323-330]. - [ADDED gap-fill] **ACS (Flow L)**: never OBO; the staff member is represented by an ACS identity keyed to their `systemuser.sprk_communicationuserid`, created and token-minted by the BFF's UAMI-backed identity client when they are `SenderParticipant` or a derived thread member [CODE AcsIdentityService.cs:22-23,52-99; MessagingChannelSender.cs:64-67; MembershipReconciler.cs:97-102].

## 8. Defects, risks and inconsistencies

1. **(medium) Inverted UAMI key precedence and no blank normalisation in three shared-lib MI branches.** `DataverseWebApiClient.cs:76-77`, `DataverseWebApiService.cs:108-109` and `DataverseAccessDataSource.cs:134-135` read `ManagedIdentity:ClientId ?? Graph:ManagedIdentity:ClientId`, the reverse of the canonical resolver (`ManagedIdentityCredentialFactory.cs:96-100`), and do not pin `TenantId`. Inert while both keys hold the same value (deploy scripts set both to `$UamiClientId` [CONFIG Configure-AppServiceSettings.generated.ps1:140,143]) but it is the FR-B4 conflation class the assertion provider's own comment flags as "not yet uniform" [CODE ManagedIdentityAssertionProvider.cs:72-80]. `DataverseAccessDataSource` is normally shielded because the BFF injects the singleton [CODE SpaarkeCore.cs:62-77 + ctor param :77]; `DataverseWebApiClient` is ALSO shielded — `AddSingleton<DataverseWebApiClient>()` satisfies its optional public-ctor `credential` parameter from the container, so selection is bypassed [CODE DataverseWebApiClient.cs:47,67-73; SpeAdminModule.cs:76]; only `DataverseWebApiService` is NOT shielded — its credential-taking ctor is `protected` (invisible to DI) and the GraphModule factory passes no credential [CODE DataverseWebApiService.cs:56-64,70-81; GraphModule.cs:131-132], so in the BFF it alone builds its own unpinned-tenant `DefaultAzureCredential`. [CORRECTED by verifier: was "`DataverseWebApiService` and `DataverseWebApiClient` are NOT (no credential injected) … so in the BFF they build their own unpinned-tenant credentials"] Net live exposure of this defect in the BFF: one class (`DataverseWebApiService`), which is also the impersonation (`MSCRMCallerID`) writer/reader — so Flow G runs on a credential that is NOT tenant-pinned and reads the legacy key first.
