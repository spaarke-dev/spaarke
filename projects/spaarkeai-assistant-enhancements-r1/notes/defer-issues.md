- **What it needs when picked up**: either (a) a narrow user-initiated memory-seed path (justify the BFF surface per §10), or (b) accept that the typed profile is the sole stated-profile channel and formally drop the MemoryItem-seed clause from FR-F3.

## D-042-02 — Profile-write authZ depends on `sprk_userprofile` row-security config (SECURITY)

- **Concrete failure scenario**: task 042 writes the profile client-side via a keyed upsert `PATCH sprk_userprofiles(sprk_systemuser=<id>)` in the host session. The questionnaire UI only ever supplies the **caller's own** Xrm `systemuserid`, so normal use is self-scoped. BUT a user with devtools could call the same-origin Web API directly with a **forged `sprk_systemuser` key**; if `sprk_userprofile`'s Dataverse security role permits creating/updating a row whose `sprk_systemuser` lookup points at **another** user, that user's server-side stated-profile read (task 030, keyed by `sprk_systemuser`) would then fold **attacker-authored text** into the victim's prompt (cross-user profile seeding). This is the mirror, on the WRITE side, of the app-only READ isolation ratified in 052 F1.
- **Mitigations present**: client sources the caller's own id; the client write runs under the **caller's** Dataverse privileges (row-level security applies, unlike the server app-only read); free-text is length/newline-hygiened at write time; and 052 F3/F4 proved profile text can never flip grounding/dispatch — the blast radius is tone/selection bias in the victim's own turn, not control-flow.
- **What it needs**: confirm/lock the `sprk_userprofile` security role so a user can only create/update a row keyed to **their own** `systemuserid` (or move the write behind a server endpoint that re-derives the caller key server-side — heavier, new BFF surface). This is a **Dataverse security-role configuration** task, not a client-code defect.
- **Trigger to revisit**: before production enablement of the questionnaire write; owner/security review of the `sprk_userprofile` role.
- ✅ **RESOLVED 2026-07-16**: owner confirmed `sprk_userprofile` is **user-scoped** — a user cannot create/update a row keyed to another user's `sprk_systemuser`, so the forge vector is closed at the Dataverse role level. No code change needed.

## U-UAT-01 — Compose-widget upload not "attached"/classified in the Assistant (owner UAT 2026-07-24)

- **Symptom (owner)**: In SpaarkeAi, open the **Compose widget tab** → **upload a file** there. That file is NOT shown as "attached" or "classified" in the **Assistant** (chat), so the Assistant can't interact with it. It needs to be attached + classified like a file uploaded directly in the chat composer.
- **Root cause (Explore sweep 2026-07-24)**: the chat's "attachment chip" store and the Compose widget's uploaded file are **two separate stores joined only server-side**. Attachment chips are owned by `useChatFileAttachment` (SprkChat) and fed **only** by `SprkChatUploadZone → addFiles` (composer `+`/drag-drop), mirrored in `useAttachments.attachmentChips`. The Compose browse/upload path (`Spaarke.Compose.Components/src/widgets/ComposeWorkspace.tsx` `handleBrowseFileSelected` → `registerActiveDocumentRef`) reaches the Assistant via the **`ComposeActionBridge`** (`registerActiveDocument`), NOT via `addFiles`/`handleAttachmentsChanged` — so **no chip is ever created** for a Compose-uploaded file (perceived as "not attached"). Classification for the Compose path rides a *different* trigger (`ConversationPane.registerComposeActiveDocument` → `POST /documents` → `eventBatch.fireForPromotedFile`), which only fires if `bridge.hasActiveDocumentHandler` is true and a session exists at upload time.
- **Scope**: **small wiring fix, not a larger gap.** Server upload (`POST /api/ai/chat/sessions/{id}/documents`), classification (Event path), and the cross-pane `ComposeActionBridge` already exist and are exercised by `ConversationPane.compose-browse-ingest-ceremony.test.tsx`. What's missing is the **last hop**: surface the Compose-uploaded `ChatSessionFile` as a **visible attachment chip** in the Assistant composer, and confirm the bridge handler/session is live at upload time so classification reliably fires.
- **Fix location (primary seam)**: `src/solutions/SpaarkeAi/src/components/conversation/ConversationPane.tsx` `registerComposeActiveDocument` (lines ~1201-1336) — after the `/documents` upload succeeds (already has `sessionFileId`, `fileName`), inject a synthetic attachment chip into the shared store. Needs an "inject external chip" entry point on `src/solutions/SpaarkeAi/src/components/conversation/useAttachments.ts` (currently `attachmentChips` is a read-only mirror fed only from SprkChat) **with dedupe** against the auto-promote caches (`activeDocUploadCacheRef` / `promotedFileIdsByNameRef`) so the file isn't double-promoted. Alt seam: expose an imperative "add external attachment" on `SprkChat` flowing through `useChatFileAttachment.addFiles` (single chip store; new SprkChat prop). Reuse the existing `ComposeActionBridge` channel — no new bus/context needed.
- **Client-only, no BFF change** (uses existing endpoints). Cross-cutting: `SpaarkeAi` (host-only — the fix landed entirely in `ConversationPane.tsx` + `summarizeRouting.ts`; NO shared-lib change after all).
