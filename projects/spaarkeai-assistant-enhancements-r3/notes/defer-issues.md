## D-1 — FR-02 visibleToAssistant toggle does not persist through the live-tab path (from task 011 re-point)

- **Discovered**: 2026-08-10 (task 011, owner-approved Option-A re-point).
- **Concrete failure**: A user toggles a layout tab's "visible to assistant" OFF; after reload the tab **re-appears** in the Assistant's workspace-state block. Cause: the awareness block is now fed from the live `StoredSession.Tabs` (`ISessionPersistenceService`), and `StoredWorkspaceTab` has **no `visibleToAssistant` field**, so `MapStoredTabsToWorkspaceTabs` defaults every live tab to `VisibleToAssistant = true`. Task 010 implemented the toggle against `WorkspaceTab.VisibleToAssistant` (correct at the block layer) but the flag is not carried on the live persistence path.
- **Fix required**: additive `visibleToAssistant` field on `StoredWorkspaceTab` + the `PATCH /sessions/{id}/tabs` DTO, and have the SpaarkeAi client send the per-tab flag on tab-persist. Then `MapStoredTabsToWorkspaceTabs` reads it instead of defaulting true. Cross-surface (BFF DTO + SpaarkeAi client) — bounded, additive.
- **Scope note**: FR-01 (Assistant SEES the tabs) IS delivered by the re-point. FR-02 (toggle-off persists hidden) is the partially-deferred half. Owner aware (AskUserQuestion 2026-08-10).
- **Severity**: Medium. Blast radius bounded to `{type,label}` identity (no content leaks post-trim).

## D-7 — Email per-item cards call the `IEmailDraftAi` facade via `/api/communications/draft`, not the task-023 chat-agent catalog tools directly (from task 025, CLAUDE.md §6.5 Path C)

- **ADR/spec in question**: task 025's own prompt/steps ("Reply/Reply All/Forward call the task-023 `draft_reply`/`draft_forward` tool… Summarize the thread calls `email.summarize_thread`").
- **Conflict**: `email.draft_reply`/`draft_forward`/`summarize_thread` are `sprk_availableincontexts = 100000001` (Chat only) — `EmailDraftToolHandler.Validate()`/`ExecuteAsync()` explicitly reject non-chat invocation ("chat-context-only… Playbook-context invocation is unsupported"). They are agent-loop tools the LLM calls mid-turn; there is no deterministic client-callable endpoint that invokes ONE named catalog tool and returns its raw structured JSON result. The tool's own description explicitly instructs the model NOT to restate the draft in its chat reply ("do not restate it in chat"), so even routing a card click through a hidden/deterministic chat turn would not reliably surface the raw `draft`/`text` field to the client for a card action (`landing: composer`/`chat`) to consume. This task's constraints also forbid touching BFF C#.
- **Resolution — Path C (pivot to comply)**: the four per-item cards call `createXrmEmailComposeHandlers(...).onDraftWithAi`, which POSTs to the PRE-EXISTING, unconditionally-registered `POST /api/communications/draft` endpoint (`CommunicationDraftEndpoints.cs`). That endpoint calls the SAME `IEmailDraftAi.DraftAsync(EmailDraftAiRequest{Intent,UserInstruction,CurrentBody,IsHtml,Subject})` facade `EmailDraftToolHandler.ExecuteComposeAsync`/`ExecuteSummarizeThreadAsync` call, with byte-identical `Intent`/`UserInstruction` construction (`'reply'` / `'custom'` + the same forwarding-note text / `'summarize'`). The card reads the source email's current subject/body via `fetchCommunicationPrefill` (the SAME Xrm-backed read `useEmailComposeActions.openComposer` already performs) instead of the tool's OBO Dataverse read — content is still fetched BY id at click time, never carried on the conduit (ADR-015 held).
- **Rationale**: reaches the IDENTICAL AI behavior (same facade, same Intent semantics, same prompt text) deterministically from a card click, reusing an EXISTING, already-shipped REST surface (§11 — zero new BFF endpoint, zero new component) rather than inventing a client-triggerable "invoke named catalog tool" mechanism (which would be new BFF surface, out of this task's scope, and arguably a second dispatch protocol alongside the Event/Click/Text ADR-039 paths).
- **Alternative considered (rejected)**: route the card click through a hidden/deterministic chat turn (mirroring the R2 "Summarize this email" chip pattern) and let the LLM invoke the catalog tool. Rejected because (1) the tool's own description tells the model NOT to restate the draft in chat, so the client has no reliable extraction point for `landing: composer` cards; (2) `sprk_availableincontexts=Chat` scoping (task 030's `OpenTabContextTypes` PreFilter) is not yet wired (task 030 is still 🔲), so the tool may not even be in the projected catalog for the turn; (3) it would non-deterministically depend on model tool-selection for a UI action the user explicitly clicked.
- **Impact**: the four email.draft_reply/draft_forward/summarize_thread catalog rows (task 023) are exercised end-to-end ONLY via the chat agent loop (e.g. a user typing "reply to this email"), not via these UI cards. If a future task wants the cards to literally invoke the named catalog tool (for telemetry/ledger parity with agent-invoked calls, or to consolidate on one AI entry point), it needs a NEW deterministic tool-invocation surface — that is new BFF scope, intentionally NOT built here.
- **Severity**: Low. User-observable behavior is correct (same AI output); the divergence is an internal-wiring/telemetry-provenance nuance, not a functional gap. Flagged for the next BFF-touching per-item-card task (e.g. 026 documents, or 040/050) to consider a shared deterministic tool-invoke seam if this pattern repeats.
