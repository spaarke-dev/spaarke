The Assistant ⇄ Workspace Interaction Contract

One definition of how the Assistant sees, answers about, and opens Workspace surfaces — so every widget behaves predictably and nothing ships without a matching Assistant capability.

Guiding principle. The Assistant gives the overview and answers directly by querying the source; the Workspace shows the detail. The Assistant is aware of tabs so it can answer, open, or direct — it does not read data out of a tab (Compose is the one interactive exception).
Why now — the evidence

Three UAT rounds surfaced the same shape of failure

The Assistant can see tabs (we fixed that), but it has no reliable, domain-shaped way to answer about them. It falls back to a generic Dataverse query it writes by hand — and gets it wrong.

“how many overdue tasks do I have”
Hand-wrote GETDATE() — unsupported by Dataverse — then asked the user to confirm today’s date.
no task tool · no “today”
“do you see the daily briefing tab?”
Answered “yes” but opened a second Daily Briefing tab — no de-dup, and the layout tab is invisible to the agent anyway.
duplicate · unaware
“show me the narrated summary”
Said “no notifications today” while the briefing showed 12 updates / 11 overdue — it had the tab’s name, not its data.
no data path

The pattern is consistent: awareness without capability parity. The fix is not "put more data in the prompt" — it is "give each surface a tool the Assistant can call."

Ground truth — how the Workspace works today

Widgets self-register, then mount as tabs through one event path

A widget is declared in a registry, and when something needs it on screen it fires a widget_load event on the PaneEventBus; WorkspacePane turns that into a tab via WorkspaceTabManager.addTab(...). Registration is spread across four sites:

Verdict

A good pattern with one gap to close — not a problem to undo. Decentralized self-registration keeps the code modular (no god-file; Compose registers separately to avoid a package cycle). The only risk it creates for us: a widget added at any site could ship without its Assistant contract. Fix — make the contract fields (context-type · parity tool · interaction pattern) required in the registration metadata, so the registry enforces parity wherever a widget is declared.

The data-access layer — behind the parity tools

Three lanes, all already built

A parity tool is the Assistant’s interface to a domain; behind each is a data mechanism. The design rule is one mechanism per data shape, no duplication. This is how RAG, the Dataverse toolset, FetchXML, and the domain services fit together.

LaneMechanism (exists today)Backs
1 · Structured recordsNative Dataverse-MCP-shaped toolset in the BFF — read_query (SQL→OData over OBO), search_data, describe. Not an external MCP server — native, security-scoped, citedtasks · matters · grids · calendar
2 · Unstructured / semanticRAG index (Azure AI Search vector) via IRagService / DocumentSearchHandler / KnowledgeRetrievalHandler + on-demand bodydocuments — summarize · "what does it say" · find-similar
3 · Composed servicesPurpose-built services that already encapsulate the query — BriefingService :128, membership resolverDaily Briefing · "records I'm on"
Key

The overdue-tasks failure is a lane-1 symptom. read_query is a general SQL-subset that rejects GETDATE()/COUNT/aggregates — it makes the model author the query, and it got the date wrong. A tasks parity tool encapsulates “overdue = dueDate < today” server-side, reusing the grid’s saved-query / FetchXML executed over OBO. RAG and FetchXML are complementary (semantic content vs structured records), not competing.

Parity = read + act. Each surface also gets its generative verbs: email → summarize · draft reply; document → summarize · draft response · draft memo. These map to the existing Actions/Bindings catalog (EmailDraftToolHandler, text/analysis handlers).

Definition of done

The acceptance test

One sentence defines success. When this works end-to-end — no query error, no asking for the date, no duplicate tab — the contract is real.

“how many overdue tasks do I have?”
Today
“I attempted to query… the system does not support the dynamic GETDATE() function… could you confirm today’s date?”
After the contract
“You have 6 overdue tasks. I’ve opened your Tasks tab showing them.” — tasks parity tool computes “overdue” server-side; date injected; existing Tasks tab focused, not duplicated.
