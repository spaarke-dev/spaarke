
==================== UC1 ====================
WHO DECIDES: mixed
MECHANISM: Internal plane: the BFF sends the caller's token by OBO and asks Dataverse RetrievePrincipalAccess what rights this systemuser has on this record, so Dataverse applies role depth, BU, team and share rules. SPA/Teams plane: the BFF runs an app-only FetchXml where owningbusinessunit = the caller's BU, owningteam is in the caller's teams, or ownerid = the caller, and gives a flat Read|Write|Create on every matching root.
GRANTS: INTERNAL: Dataverse's own security model, evaluated for the resolved systemuser on the specific record by RetrievePrincipalAccess (DataverseAccessDataSource.cs:705-757 for the document or record target; CallerRecordAccessProbe.cs:406-470). A matching BU or owning team gives access only as far as Dataverse says it does:
- a role privilege at BU depth or wider, or
- owner-team membership that carries the team's roles, or
- a POA share.
The BFF never compares BU or team itself. DataverseAccessDataSource fills TeamMemberships and Roles into the snapshot (:327-331), but OperationAccessRule reads only snapshot.AccessRights (Rules/OperationAccessRule.cs:49). OperationAccessPolicy then only says which right an operation needs.

SPA/TEAMS: a structural column match in MembershipResolverService. PlatformOwnershipColumns {ownerid, owningteam, owningbusinessunit} (MembershipResolverService.cs:595-596) are admitted without any registry entry when AccessConferringOnly=true on the systemuser plane (:255-258, :688-692). BuildFetchXml then binds:
- Team descriptors → each id in identity.TeamIds (:904-909)
- BusinessUnit → identity.BusinessUnitId (:911-916)
- SystemUser → the caller's systemuserid (:864-866)
These are exact-equality OR conditions. There is no BU hierarchy, no role depth and no privilege check. AccessibleRecordSetService.ComposeForSystemUserAsync walks every page (AccessibleRecordSetService.cs:997-1002) and credits each hit as a membership term (:1048-1051). Handlers then allow on CallerPrincipal.HasProjectAccess / GetEffectiveRights / GetMatterRights (e.g. ExternalProjectDataEndpoints.cs:273, :570-571).
LEVEL: INTERNAL: whatever RPA returns, mapped one-to-one by DataverseAccessRightsMapper (DataverseAccessRightsMapper.cs:61-71):
- Read, Write, Delete, Create, Append, AppendTo and Share are mapped.
- AssignAccess and any unknown right contribute nothing.
The operation's requirement comes from OperationAccessPolicy, for example read=Read, write=Write, download_file=Write, entity.associate_document=AppendTo, share=Share (OperationAccessPolicy.cs:139-248).

Degraded paths:
- Document path (GetUserAccessAsync): if RPA fails, it falls back to a read probe capped at Read (DataverseAccessDataSource.cs:685-687, :776-852).
- Record path (GetRecordAccessAsync): the same fallback, a probe capped at Read (:436-449).
- CallerRecordAccessProbe: no fallback; any failure gives None (CallerRecordAccessProbe.cs:446-452).

SPA/TEAMS: always the constant MembershipTermRights = Read|Write|Create (AccessibleRecordSetService.cs:288-289), displayed as "Collaborate". It never includes Delete, Share, Append or AppendTo, and it ignores the user's actual Dataverse privileges. It is unioned highest-wins with any sprk_externalrecordaccess grants held by the user's linked contact (:1059-1062).
IDENTITY: Every path starts from the `oid` claim. CallerResolution.ResolveObjectId (Infrastructure/Authentication/CallerResolution.cs:89-95) accepts the short `oid` claim or the long schema-URI form. It deliberately has no fallback to `sub`/NameIdentifier; a missing oid gives 401.

INTERNAL PLANE:
(1) Document routes use AuthorizationService, then CachedAccessDataSource, then DataverseAccessDataSource.GetUserAccessAsync. That method OBO-exchanges the caller's bearer token for a Dataverse token (DataverseAccessDataSource.cs:286-297). Still under that OBO token, it runs `systemusers?$filter=azureactivedirectoryobjectid eq '{oid}'` (:307, :577-615) to get the systemuserid.
(2) Record routes use GetCallerRecordAccessAsync, then GetRecordAccessAsync. This does the OBO exchange, then the same oid lookup with an explicit per-request token (:419-430).
(3) Filters for entity, delegation, todo, quickcreate and record routes use CallerRecordAccessProbe. It does the OBO exchange and then calls WhoAmI() (CallerRecordAccessProbe.cs:357). The systemuserid comes from the credential, so the oid is never passed around as data.
(4) Office entity search (master task 062) uses CallerSystemUserResolver. It looks up oid → systemuser.azureactivedirectoryobjectid app-only (Services/Ai/Context/CallerSystemUserResolver.cs:100-106), then runs an impersonated read with MSCRMCallerID set to that systemuserid (OfficeService.cs:1821-1839).

SPA/TEAMS PLANE:
- CallerPrincipalResolver.DeterminePlane (CallerPrincipalResolver.cs:293-313) picks Workforce unless `iss` contains ciamlogin.com or `tid` equals Ciam:TenantId.
- WorkforcePrincipalResolver (WorkforcePrincipalResolver.cs:99-151) calls MembershipEndpoints.ResolveSystemUserIdAsync. That is an app-only QueryExpression on systemuser.azureactivedirectoryobjectid that excludes disabled users (MembershipEndpoints.cs:398-449), cached per tenant for about 10 minutes. It returns the systemuserid.
- IdentityNormalizationService.ResolveAsync then reads two things app-only: systemuser.businessunitid, giving BusinessUnitId (IdentityNormalizationService.cs:199-224), and the teammembership rows, giving TeamIds (:665-693).
- The resulting PersonIdentity is cached for 10 minutes (:55, :174). MembershipResolverService binds these values into FetchXml.
DESIGNED-vs-LIVE: LIVE, internal plane: every BFF route with a per-record gate for a workforce systemuser asks Dataverse RPA under OBO. That covers DocumentAuthorizationFilter (write/delete/read/share on the document, file access, version, operations routes), FinanceAuthorizationFilter, EntityAccessFilter (Office save), TodoSourceAccessFilter (master task 064), QuickCreateSourceAccessFilter, RecordRouteAccessAuthorizationFilter, DelegationRuleFilter / InternalShareEndpoints, and the AI search / RAG / semantic-search scope=entity checks. Office entity search uses an impersonated read instead, which is still Dataverse-native. MDA forms that read Dataverse directly never touch the BFF. For UC1 on this plane the BFF holds no BU or team logic; Dataverse decides.

LIVE, SPA/Teams plane: the ADR-034 column-matching path decides. Access comes from owningbusinessunit or owningteam matching the caller, plus ownerid; platform ownership was restored structurally by task 043 C-1. The level is a fixed Read|Write|Create, followed by the veto pipeline.

DESIGNED / REGISTERED BUT INERT:
- ADR-028 A5, and the FR-20 swap (task 036) of ComposeForSystemUserAsync onto ImpersonatedRootSetSource. The source class exists and is registered, but nothing consumes it and no flag is read in production. Its own registration comment admits this (ExternalAccessModule.cs:195-196).
- The NFR-04 negative canary (task 034) exists as a test tripwire only.
Net effect: the BU over-grant and share-blind under-grant that A5 was written to remove are still live on the Teams plane.

UNCHANGED BY THE MERGE for UC1: the master-side decisions (Office search impersonation, TodoSourceAccessFilter, JobOwnershipFilter) all keep Dataverse as the decider. IDataverseUserClient (now in Infrastructure/Dataverse, registered unconditionally at SpaarkeCore.cs:94-95) is not on the UC1 authorization path; it serves our task-127 communications reads.

NOT SUPPORTED: UC1 for a CIAM caller. A CIAM contact cannot be a systemuser, has no BU or team, and gets grant-only access.

==================== UC2 ====================
WHO DECIDES: BFF
MECHANISM: Workforce JWT, then the ExternalCollaboration dual-scheme policy and the group CallerPrincipalAuthorizationFilter. The resolver picks the Workforce plane by issuer and finds no enabled systemuser for the oid, then maps the caller to a contact by contact.azureactivedirectoryobjectid, else by email claim with the no-hijack check. AccessibleRecordSetService.ComposeForContactAsync then builds an app-only (rootId -> AccessRights) map for project, matter and work assignment: sprk_externalrecordaccess grants (direct plus org-inherited) ∪ standing-grant membership ∪ org-expansion membership, with Secure pre-max suppression, then the deny-list veto, then the Restricted veto. Handlers gate on KEY PRESENCE for most reads and on rights flags for to-do lists and writes, and data and bytes are served app-only. Dataverse row security is never consulted, because a contact is not a security principal.
GRANTS: All reads are app-only against Dataverse and run inside ComposeForContactAsync (AccessibleRecordSetService.cs:1114-1322). Four sources can add a record; two vetoes can remove it.

Additive terms (combined highest-wins by bitwise OR in AccumulateTerm, :308-318):
- (T1) The contact's own active, unexpired sprk_externalrecordaccess grant rows: _sprk_contact_value = contact, statecode 0, sprk_expiresdate >= today. A null expiry confers nothing (ExternalParticipationService.cs:61-62, 108-109).
- (T1b) ORGANIZATION grant rows (contact empty) for every sprk_organization the contact is an ACTIVE member of in the sprk_contactorganization junction (:909-942, 1020-1060, 1096-1132). Both T1 and T1b come from GetGrantSetAsync, which is Redis-cached for 60 seconds (:189-227). They cover project, matter and work-assignment roots only (:1128-1132).
- (T2) Standing-grant membership. It applies ONLY if contact.sprk_standinggrant = true AND sprk_accesspermissiongrant is set. That field is FLS-secured, and the read fails closed to NotHeld (SubjectStandingGrantReader.cs:155-237). Records come from MembershipResolverService.ResolveByContactAsync: contact-typed lookups in the access-conferring registry only, with platform ownership excluded (MembershipResolverService.cs:384-539, 614-700). They are credited at the contact's baseline (AccessibleRecordSetService.cs:1158-1175, 1270-1277).
- (T3) Org expansion. For each active org whose own standing grant and baseline are set, records that reference that org through registry-listed org-typed lookups are credited at the org's baseline, one walk per distinct baseline (:1195-1249, 1283-1290).
- There is NO automatic contact-anchored membership without a standing grant (:1139-1141, 1161).

Secure (sprk_issecure) suppression, applied before the max:
- T2 and T3 are dropped outright on secure roots.
- T1/T1b contribute only DirectAccessLevel, so org-inherited rows contribute None (:237-259, 1262-1265).

Vetoes, applied after the max (:357-407, 1298-1301):
- The deny list (sprk_noaccessentry) for the contact and its active orgs (:596-672) removes keys.
- Restricted (sprk_accesspermission = 100000002) removes EVERY key for a contact principal, because the survivor map is empty (:1301). So a UC2 user can never reach a Restricted root.

Children and other modules:
- Children are reached only through an accessible root: documents, invoices and to-dos (ExternalAccessModule.cs:244-268).
- Service requests are visible only where sprk_requestedby = the caller's contactId (:299-308).
- Grid configuration is a static allow-list (:318-324).
LEVEL: Each record's rights are the OR of its terms. The mapping is ExternalAccessLevels.ToAccessRights (ExternalCallerContext.cs:207-213): ViewOnly = Read; Collaborate = Read|Create|Write; FullAccess = Read|Create|Write|Delete; null or out-of-range = None. The standing and org baselines use the same mapping (SubjectStandingGrantReader.cs:61).

How the endpoints enforce it:
- Most reads check KEY PRESENCE only, not Read: GET /projects, /projects/{id}, /documents, document content download, /versions, /events, /contacts, /organizations, and module /fetch and /record. They use HasProjectAccess (CallerPrincipalResolver.cs:161) or the id sets (ExternalModuleRegistry.cs:129-144).
- To-do lists require Read (ExternalProjectDataEndpoints.cs:399-401).
- POST to-dos, events and document upload require Create (:433-434, :797-798, :570-571).
- PATCH /todos/{id} requires Write (:903).
- No route consumes Delete on this plane.

So a record can sit in the set with AccessRights.None, and it is still readable wherever the check is presence-only.

==================== UC5 ====================
WHO DECIDES: BFF
MECHANISM: The BFF decides, working like a policy engine over rows it reads app-only from Dataverse. It unions the caller contact's own sprk_externalrecordaccess grants, its standing-grant membership and org expansion. On a sprk_issecure root it keeps only the DIRECT grant level: org-inherited grants, standing membership and org expansion are suppressed before the highest-wins max. It then applies two post-max vetoes, deny-list then Restricted, and stamps the (recordId → rights) map onto CallerPrincipal. The /api/v1/external handlers gate on that map and read or stream data app-only. Dataverse's Secure business unit, owner team and POA shares are never consulted for this principal.
GRANTS: Only one thing reaches a secure record: a DIRECT, personal sprk_externalrecordaccess row that meets all of these conditions:
- _sprk_contact_value = the caller's contact
- statecode 0 and not expired (filter at ExternalParticipationService.cs:61-62)
- targets the secure root through _sprk_project_value, _sprk_matter_value or _sprk_workassignment_value
- a row like this carries DirectAccessLevel = sprk_accesslevel (ExternalParticipationService.cs:871-907)

Things that do NOT reach a secure record:
- Organization-inherited grants, which have DirectAccessLevel = null (ExternalParticipationService.cs:917-941).
- The contact's standing-grant membership, filtered by .Where(!IsSecure) at AccessibleRecordSetService.cs:1270-1277.
- Organization expansion, filtered the same way at AccessibleRecordSetService.cs:1283-1290.
All three are suppressed before the max (AccessibleRecordSetService.cs:237-259, 1262-1265).

Documents, invoices, to-dos and events do not have their own grants or secure flag. They are reachable through their parent root's id (the module scope dimensions at ExternalAccessModule.cs:244-292, and the project-id routes in ExternalProjectDataEndpoints).

The grant row itself can only be minted through /api/v1/external-access/grant. The DelegationRuleFilter / CallerRecordAccessProbe there requires the GRANTOR to hold Write on the record, checked by OBO WhoAmI + RetrievePrincipalAccess (CallerRecordAccessProbe.cs:206-238). On a secure record that means a systemuser the Secure BU or a POA share admits. The contact itself can never manage access: a non-systemuser gets AccessRights.None at CallerRecordAccessProbe.cs:230-234.
LEVEL: The direct row's own level, mapped by ExternalAccessLevels.ToAccessRights (ExternalCallerContext.cs:207-213):
- ViewOnly = Read
- Collaborate = Read | Create | Write
- FullAccess = Read | Create | Write | Delete (no external route exercises Delete)
- A null level = None

Several direct rows on the same record are unioned highest-wins (ExternalParticipationService.cs:953-961, 1000-1011). A suppressed organization grant cannot outbid a lower direct grant: ViewOnly direct plus Collaborate via the organization yields Read.

Two vetoes run after the max and remove the key entirely:
1. The deny list (sprk_noaccessentry, keyed on the contact or its active organizations) (AccessibleRecordSetService.cs:375-378).
2. Restricted (sprk_accesspermission == 100000002). On this plane nothing survives it, so even a direct FullAccess grant is removed (AccessibleRecordSetService.cs:391-406, 1298-1301; ExternalParticipationService.cs:521).

How routes enforce the rights:
- Mutating routes gate on the specific right: Create for POST to-dos, events and documents (ExternalProjectDataEndpoints.cs:433-434, 570-571, 797-798), Write for PATCH /todos.
- To-do LIST routes gate on Read (ExternalProjectDataEndpoints.cs:399-401).
- The other project read routes gate only on presence in the map (HasProjectAccess). See the first caveat: a None-rights entry still passes those.
IDENTITY: Plane selection: the /api/v1/external group accepts both the Ciam and the default workforce JwtBearer schemes (AuthorizationModule.cs:351-359; ExternalAccessEndpoints.cs:54-57). CallerPrincipalResolver.DeterminePlane chooses Workforce whenever iss does not contain "ciamlogin.com" and tid does not equal Ciam:TenantId (CallerPrincipalResolver.cs:293-313). WorkforcePrincipalStrategy then calls WorkforcePrincipalResolver (CallerPrincipalResolver.cs:483-487).

==================== UC6 ====================
WHO DECIDES: BFF
MECHANISM: The BFF reads the contact's own active, unexpired sprk_externalrecordaccess rows plus the org-grant rows inherited through active sprk_contactorganization memberships (app-only, cached 60s). It folds them highest-wins into CallerPrincipal (recordId -> AccessRights) and checks each route by id-in-set, plus Create or Write for mutations. It never reads sprk_issecure or sprk_accesspermission, and never runs the Secure / Restricted / deny-list veto pipeline on this plane. So "secure" has no effect on a CIAM caller's access, only on where uploads are stored.
GRANTS: An active (statecode 0), unexpired (sprk_expiresdate >= today UTC; a null expiry now grants NOTHING) sprk_externalrecordaccess row. It can be either (a) keyed to the contact (_sprk_contact_value = contactId), or (b) an ORGANIZATION grant row (contact empty, _sprk_organization_value = an org the contact actively belongs to via sprk_contactorganization statecode 0) (ExternalParticipationService.cs:61-72, 108-109, 846-848, 1020-1060, 1096-1132). Each row targets exactly one root: sprk_project, sprk_matter or sprk_workassignment. Child records (documents, invoices, to-dos, events) are reachable only through an accessible root. The rows are written by POST /api/v1/external-access/grant (or /invite-and-grant) by an internal user. DelegationRuleFilter requires that user to hold Write on the target record, checked AS THE CALLER through OBO WhoAmI + RetrievePrincipalAccess (ExternalAccessEndpoints.cs:123-126, DelegationRuleFilter.cs:158-177, CallerRecordAccessProbe.cs:206-238). On a secure record, the internal user's Write normally comes from the explicit POA share that provisioning gives the creator (CollaborateRights + ShareAccess, ProvisionProjectEndpoint.cs:169, 726-730), because the Secure Record BU's owner team has no members. The grant endpoint does NOT check sprk_issecure on the root. It will write a per-contact grant OR an organization grant on a secure record without distinction (GrantExternalAccessEndpoint.cs:84-93, 596-620, 655-705).
LEVEL: sprk_accesslevel on the grant row maps through ExternalAccessLevels.ToAccessRights (ExternalCallerContext.cs:207-213): ViewOnly (100000000) = Read; Collaborate (100000001) = Read|Create|Write; FullAccess (100000002) = Read|Create|Write|Delete. Null or an unknown value = None. Across duplicate rows and direct plus org-inherited rows, the HIGHEST level wins (ExternalParticipationService.cs:953-976; CallerPrincipalResolver.cs:417-429 ORs duplicates). The CIAM strategy uses the EFFECTIVE `AccessLevel`, which includes org-inherited rows, and never the `DirectAccessLevel` (CallerPrincipalResolver.cs:386-388, 402-403). So on a secure record a contact receives the full org-inherited level. Enforcement is per route. Read routes on ExternalProjectDataEndpoints (GET project, documents, download, versions, events, contacts, organizations) gate only on set membership, HasProjectAccess (any level) (ExternalProjectDataEndpoints.cs:273, 290, 322, 694, 766, 823, 840). To-do list requires Read; to-do/event/document create requires Create; to-do PATCH requires Write (ExternalProjectDataEndpoints.cs:399-401, 433-440, 570-582, 797-804, 897-909). Module-host reads gate on the record id being in the principal's id sets (ExternalModuleDataEndpoints.cs:267-274; ExternalAccessModule.cs:224-292). All data then comes back APP-ONLY: ExternalDataService managed-identity token (ExternalDataService.cs:13, 1102), RecordService over the privileged ServiceClient (RecordServiceExtensions.cs:15), and SPE bytes via app-only SpeFileStore.DownloadFileAsync (ExternalProjectDataEndpoints.cs:344-349).
IDENTITY: Plane: the /api/v1/external group requires AuthPolicies.ExternalCollaboration, which accepts both the "Ciam" scheme and the workforce scheme. The group-level CallerPrincipalAuthorizationFilter calls ICallerPrincipalResolver (ExternalAccessEndpoints.cs:54-57, CallerPrincipalAuthorizationFilter.cs:32-48). CallerPrincipalResolver.DeterminePlane picks CiamContact when the validated token's `iss` contains "ciamlogin.com" OR its `tid` equals config Ciam:TenantId (CallerPrincipalResolver.cs:293-313). Claim-to-row mapping: CiamContactPrincipalStrategy reads `oid` (or the objectidentifier URI claim) plus preferred_username/upn/email (CallerPrincipalResolver.cs:345-350) and calls ExternalParticipationService.ResolveExternalContactAsync (ExternalParticipationService.cs:314-361). That method takes `oid` and does an app-only lookup of contact.sprk_externalobjectid (ResolveContactByOidAsync :366-398); a match is authoritative. Otherwise it falls back to a first-login match on emailaddress1 and binds the oid onto that contact only if the contact has no oid yet (:339-348). A contact already bound to a DIFFERENT oid is refused, so a shared email cannot hijack it (:350-360). With no oid and no email the result is 401 (:352-360). An unresolved contact gets 403 sdap.access.deny.contact_not_found (:366-373). The resolved row is a Dataverse `contact`. It is never a systemuser, so it is not a Dataverse security principal (SystemUserId = null at CallerPrincipalResolver.cs:394).
DESIGNED-vs-LIVE: LIVE path: token -> ExternalCollaboration policy -> CallerPrincipalAuthorizationFilter -> DeterminePlane=CiamContact -> CiamContactPrincipalStrategy -> ExternalParticipationService (oid-bound contact; app-only grant rows plus org-inherited grant rows; 60s tid-keyed cache) -> CallerPrincipal (recordId -> rights) -> per-route membership/Create/Write checks in ExternalProjectDataEndpoints and ExternalModuleDataEndpoints -> app-only Dataverse and SPE reads. This follows ADR-028 A1: broker-only, no OBO on the external path (ADR-028 lines 48-50, 123).

DESIGNED but NOT reaching this plane: the three task 037/039 vetoes (FR-21 Restricted, FR-22 Secure pre-max suppression, FR-23 deny list) are implemented and tested, but live only in AccessibleRecordSetService (ApplyVetoPipeline :357-407; GrantedRightsFor isSecure :237-256; ComposeForContactAsync :1256-1301). That service is reached only from WorkforcePrincipalStrategy. The CIAM strategy's own doc says it is the 'EXISTING external-SPA resolution, unchanged' (CallerPrincipalResolver.cs:316-321). The spec wording says FR-21/22 apply to 'all contact principals' / 'every principal kind' (spec.md:84-85), so the CIAM plane is a spec gap, not a deliberate exclusion that any code or ADR records.

REGISTERED-BUT-INERT and irrelevant to UC6: ImpersonatedRootSetSource / ADR-028 A5 (ExternalAccessModule.cs:181-198). It is registered, has no consumer, and applies to WorkforcePrincipalKind.SystemUser only (ADR-028 line 329: the CIAM/contact plane derivation is untouched).

Secure Record provisioning (ProvisionProjectEndpoint: Secure Record BU owner team plus creator POA share plus own SPE container) is live. For a CIAM contact, though, it only affects (a) who can issue the grant: the DelegationRuleFilter OBO Write check, which Dataverse decides natively for the GRANTER, and (b) which container an upload lands in. The CIAM contact's own access decision is made entirely by the BFF from grant rows. Dataverse never evaluates the contact.

Net: UC6 IS SUPPORTED, by explicit grant, with BFF-decided access at the grant row's level. The secure flag does NOT narrow CIAM access: org-inherited grants, Restricted records and deny-list entries are all unenforced on this plane.
