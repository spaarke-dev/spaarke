## S2 — `w14:paraId` carry-through in TipTap ✅ PASS (+ simplifies the design)

**Harness**: `scratchpad/s2-tiptap` — headless TipTap v3 (jsdom) + `@tiptap/extension-unique-id` **3.28.0, MIT** (verified: main `ueberdosis/tiptap` repo, not Pro; deps: `uuid` only). Pre-set paraIds on 3 paragraphs (simulating the server OOXML pre-parse), then split the middle paragraph.

| Check | Result |
|---|---|
| Untouched paragraphs keep their paraId through an edit elsewhere | ✅ Alpha `000001101` + Charlie `000001103` preserved |
| Split: does one half keep the original id, the other get a fresh one? | ✅ one half keeps `000001102`, the other gets a fresh id (UniqueID's built-in **dedup** re-mints the duplicate) |
| Split halves have distinct, non-empty ids | ✅ |

**Findings for the design:**
1. **No custom split/merge minting plugin needed** — `UniqueID.configure({ types: ['paragraph'], attributeName: 'paraId' })` handles it (dedups the copied id on split, re-mints one half). *Design simplification* — the hypothesized custom plugin drops out.
2. **`UniqueID` does NOT auto-assign ids to `setContent`-loaded nodes** (they stayed `null`). **Load-time paraIds must be set explicitly** from the server pre-parse (a transaction stamping `paraId` per paragraph) — which is exactly the plan. UniqueID's job is only to mint ids for NEW nodes (split/paste/typed).
3. **Minted ids are UUIDs**, not OOXML-shaped. Point `UniqueID.configure({ generateID })` at an **8-hex `< 0x80000000` generator** so new-paragraph ids are valid `w14:paraId`s directly (or translate server-side on save). Small, known.

## S4 — E1 baseline source (DECISION, not a runtime spike) ✅ DECIDED

**Question**: what does the delta apply onto — client-retained bytes, a server cache, or a re-fetch?

**Facts** (from the code analysis + S1): (a) the pristine load-time original is available client-side as `state.docxBytes` but is **lost on page refresh**; (b) after today's first lossy dirty save, the **current SPE version is already degraded** — so re-fetching "current" is NOT a valid baseline; the baseline must be the **load-time** version; (c) SPE versions files, so the load-time version is addressable by its `versionId`.

**Decision**: **Primary baseline = the load-time SPE version, fetched by `versionId`** (captured at Load) from SPE version history on Save — authoritative, survives refresh AND survives prior dirty saves, **zero new storage** (SPE already versions). **Fast-path**: when the client still holds `state.docxBytes` (same-session, no refresh), send it and skip the re-fetch. **Fallback** (if version-by-id fetch proves impractical): a size-capped Redis cache of the load-time original (ADR-009, ADR-015 Tier-3).

**Build-time confirmation** (small, not a blocker): extend `SpeFileStore` to fetch a specific driveItem **version's** content (`/versions/{id}/content` — a known Graph capability). Encode as a spec task.

## S5 — Track-changes apply path is slice-safe ✅ PASS (+ one R3 payload item)

Code inspection of the shipped R2 redline apply path (`usePendingRedline.ts`, `marks/InsertionMark.ts`, `marks/DeletionMark.ts`, `docxBridge.ts`).

- **Deletions are a ProseMirror MARK over a resolved `{from,to}` range** (`usePendingRedline.ts:461-465`, `setMark(DELETION,...)`), leaving original text nodes — and their bold/italic marks — physically in place. **No `tr.replaceWith`/`replaceRange`/text-replacement anywhere** in the module. `buildRejectBaselineJson` (`docxBridge.ts:190-192`) keeps all non-redline marks through accept/reject.
- **Verdict: slice-safe — no davefowler flatten bug.** Existing/surrounding user formatting is preserved.
- **The one R3 item (supports D4)**: the AI-drafted `new_text` is a plain **string** on the wire (`ComposeEditor.tsx:275`) rendered via `buildInsertionHtml` as escaped plain text (`usePendingRedline.ts:313-320`) — so an *inserted* AI replacement carries no inline formatting. To let AI replacements themselves carry bold/italic, enrich at the **payload + `buildInsertionHtml` boundary** (make `new_text` a formatting-bearing fragment/HTML), NOT the mark/range layer (already correct). This is a bounded, well-located R3 change.
