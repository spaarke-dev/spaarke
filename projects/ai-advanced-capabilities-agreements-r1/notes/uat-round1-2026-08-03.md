- **Message source**: `ReviewMemoEndpoints.ResolveBoundAnalysisIdAsync` (`src/server/api/Sprk.Bff.Api/Api/Ai/

## agent-C resolution — item #4 (Save error "A change could not be anchored…", 2026-08-03)

**Empirical-reproduction-FIRST (root §F.3):** two failing tests were written BEFORE any code change
(one client, one server), each confirmed RED, then made green by the fix.

### Root cause — TWO defects compound (a trigger + a blast-radius amplifier)

The reviewer's session had **advisory REVIEW comments placed but (likely) no committed text edits**
— a "review was attempted" save. The 422 the owner saw is the catch-all mapping in
`ComposeEndpoints.MapPatchException` (§ any `ComposePatchException` kind other than
Malformed/UnsupportedSchema → 422 "…could not be anchored…"). Two things had to line up:

1. **TRIGGER — comment anchors omit the robust `paraOffset` (hypothesis H1/H3, confirmed in code).**
   Text-edit ops carry the task-055 robust anchor `paraOffset` (paragraph-relative char offset), so
   the server realigns them across the **TipTap↔OOXML run-merge boundary** (TipTap merges same-format
   runs → its `runIndex` disagrees with OOXML's fine-grained run flatten). Advisory comments did **not**:
   `composeSessionCommentThreadsToAnchoredComments` (`ComposeCommentThread.types.ts`) built the comment
   `range` from only `{runIndex, offset}` and **dropped** the `paraOffset` that `resolveRunAnchor`
   already returns (`stepOperationInterceptor.ts:400`). So a comment on a multi-run paragraph resolved
   server-side by `(runIndex, offset)` only and refused with an anchor error — the SAME class of 422
   that `paraOffset` (prong 2) had already eliminated for text edits. NDA advisory comments anchor to
   long multi-sentence excerpts clamped to their start paragraph (UAT round-3 fix), so their anchors
   are exactly the fragile multi-run case.

2. **BLAST RADIUS — the best-effort recovery was comment-blind (task-055 prong 1, pre-existing).**
   When any comment fails to anchor, the whole `ComposeShadowPatchEngine.Apply` throws; `ComposeService`
   enters per-paragraph best-effort recovery (`ApplyBestEffortByParagraph`). But `appliedCount` counted
   **only ops**, never baked comments. For a comments-only review save (empty op-log), even comments
   that baked perfectly contributed 0 → `appliedCount == 0` → the guard `if (partial.AppliedCount == 0)
   throw;` **re-threw the refusal → 422**, discarding even the comments that DID anchor. This is exactly
   the "fails the WHOLE save" behavior the task FIX RULES call out — a non-destructive comment must
   degrade gracefully, not sink the save. (It also silently dropped a failed comment when a text edit
   succeeded — `unresolvedCount` stayed 0, so the reviewer never saw the loss.)

Not H2 (032 status-cycle) or H4 (unrelated master behavior): the reproduction is deterministic at the
save-apply seam, independent of the client save-status race.

### Fix (minimal; ADR-049 preserved — anchors stay purely numeric, no write-path text-search)

- **Client trigger** — `ComposeCommentThread.types.ts` `composeSessionCommentThreadsToAnchoredComments`:
  carry `paraOffset` onto **both** range endpoints (same spread pattern text ops use), so a comment
  anchor is as robust as a text-edit anchor. Purely additive; omitted-when-absent keeps the server's
  `(runIndex, offset)` fallback intact for older payloads.
- **Server blast radius** — `ComposeService.ApplyBestEffortByParagraph`: count baked comments toward
  the applied work and **surface un-anchorable comments** on `partialApply.unresolved`
  (`opType:"AdvisoryComment"`) — folded into `Total`/`AppliedCount`/`UnresolvedCount` so the existing
  `appliedCount == 0` guard and the client partial-apply banner both read correctly, with **no call-site
  change**. Result: a comment that can't anchor is **skip-with-report**, never a whole-save failure.
  **The honest-failure contract for TEXT is unchanged** — a failing text op still lands in `unresolved`
  exactly as before, and a batch with zero applied work (no op, no baked comment) still hard-fails 422.
  Op-only batches have no comments, so the accounting reduces to the prior values (existing seam tests
  #1/#2 unchanged).

## Resolution — ITEM #13 (workspace-tab persistence + resume) — 2026-08-04

Full design + evidence trail: `notes/uat4-execution-notes.md` "agent #13 (item #13)". Summary:

**What was broken (confirmed by cold-load analysis, not assumed):** the two SHIPPED tab-persistence
mechanisms both DECLINE the owner's exact surface. The unbound "home" surface (Daily Briefing →
direct-Compose door) has NO `entityContext` → `tabAnchorKeyForContext` returns null → the localStorage
anchor never writes; and a direct-Compose session is unbound → `chatSessionId` is null at tab-open time
→ the BFF `/tabs` PATCH is skipped and does not restore on return. Net: the Compose tab was genuinely
lost. This is a CLIENT state-persistence + resume gap (the server-side run already survives disconnect
per round-4 #10b, and completed findings are durably ledgered + re-materializable via FR-16).

**The fix (smallest honest version; §11 extend, don't invent; ADR-030 zero new event types; NO server
change):** a new `composeRunPersistence.ts` (pure, unit-tested) + wiring in `WorkspacePane.tsx` that
persists ONLY the home-surface Compose tab(s) — the one surface the shipped anchors miss — keyed on the
SAME `deriveComposeInstanceKey` document identity, to a single versioned localStorage entry
(`sprk_ai2_composeRunState`, following the existing `sprk_ai2_*` convention + the owner's "follow the
localStorage convention" clause), TTL-bounded (8h) + explicit-close-cleared:
- **PERSIST** on Compose-tab open (seed + captured session) and on run-start (the round-4
  `nda_review_background_run` "Continue working in background" signal stamps `run:{inFlight,dispatchedAt}`).
- **RESTORE** on cold-load (home surface, after the shipped restore settles): reopens each fresh persisted
  Compose tab via the EXACT `widget_load{compose}` door, threading `composeSessionId` so ComposeWorkspace
  resumes the session and FR-16 recall re-materializes COMPLETED findings on mount — for free.
- **RESUME** a still-young in-flight run: reuses the round-4 tab spinner + polls the EXISTING
  `GET /api/ai/chat/sessions/{id}/compose-outputs`; on findings-after-empty it dispatches the SAME
  `compose_advisory_comments` event the live path uses (so placement + the completion-toast rules run),
  guarded so it never double-places with the tab's own FR-16 mount-materialize.
- **AGENCY:** an explicit tab close drops the entry (not resurrected); navigation teardown retains it.

**Documented limitations (honest):**
1. **Non-dismissed navigate-away spinner.** Run-in-flight is captured from the round-4
   `nda_review_background_run` signal (fires when the user chose "Continue working in background"). If the
   user navigates away with the progress modal STILL up, the tab still restores + the document loads +
   completed findings materialize via FR-16 on mount/next-open, but WITHOUT the live spinner/poll for that
   one path. The realistic + round-4-demonstrated flow (dismiss → tab spinner → navigate away) IS covered.
2. **New browser tab / storage scope.** localStorage (chosen for reliability across the code-page iframe
   teardown + to follow the existing convention) is origin-shared, so a fresh browser tab within the TTL
   would also restore the Compose tab — a mild superset of the requirement, bounded by the 8h TTL +
   explicit-close. Multi-tab persistence is additive (the full set); the resume spinner is a single shared
   boolean across compose tabs (round-4 parity).
