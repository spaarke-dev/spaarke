## DI-02 — Un-flushed TipTap compose edits in the OUTGOING session could be lost on a History switch → **RESOLVED (flush-on-unmount, `ComposeWorkspace.tsx`)**

- **STATUS: RESOLVED 2026-08-06** — investigated + fixed. No GitHub issue needed (delivered).
- **Original escalation record (for history):**
- **Discovered**: 2026-08-06, task 035 (rich History restore) — escalation trigger evaluated, judged below the STOP bar.
- **Concrete failing behavior**: task 035 now **clears compose tabs on a genuine History switch** (required — preserving them would corrupt the reopened session's tab set and re-block restore). The compose **document is durable** (server-authoritative per ADR-049 + `composeRunPersistence` localStorage, explicit-close-only removal), so the document is never destroyed. BUT if the TipTap→server edit flush is **not** continuous/auto-on-unmount, a mid-edit draft in the *outgoing* session could lose keystrokes entered since the last flush when the user switches History before those edits flush.
- **Why below the STOP bar**: document durability is guaranteed; only un-flushed in-memory deltas since the last flush are at risk — and the same property pre-exists on any tab close (035 did not create the flush cadence, it added one more path that closes a compose tab).
- **Recommended fix / investigation**: confirm the TipTap edit-flush cadence (debounce interval / flush-on-blur / flush-on-unmount). If edits are NOT flushed on unmount, add an explicit flush before `clearAllTabs()` on the History-switch path (or make the compose editor flush-on-unmount). If flush is already continuous/on-blur, close this as a non-issue with a documenting comment.
- **GitHub issue**: PENDING.
- **Investigation finding (2026-08-06)**: the escalation's premise ("a debounce that hasn't fired yet") was optimistic — there is **no autosave/debounce/flush-on-blur at all** in `ComposeWorkspace.tsx`. `triggerSave` fires ONLY on explicit Ctrl+S, the toolbar Save button, or the cross-pane "Add to DMS" bridge chip (`useRegisterComposeSaveHandler`). Traced `WorkspaceTabManager.closeTab` and `clearAllTabs` (`src/solutions/SpaarkeAi/src/components/workspace/WorkspaceTabManager.ts:563,656`): **neither reads editor dirty state or gates on it** — every compose-tab-close path (manual X, exclusive-playbook reset, AND task 035's History switch) unmounted the compose widget with zero flush. So DI-02 was a **real, broader-than-scoped gap**: not "since the last debounce tick" but potentially the entire in-progress edit since the last explicit Save.
- **Fix**: added a flush-on-unmount to `ComposeWorkspace.tsx` (`src/client/shared/Spaarke.Compose.Components/src/widgets/ComposeWorkspace.tsx`, just after `handleDirtyChange`) — a `hasUnsavedWorkRef` mirrors "is there unsaved work" (dirty OR an un-persisted transient/create-on-save draft) on every render; an unmount effect's cleanup best-effort flushes through the SAME `triggerSave` path a manual Save uses when that ref is true. No new persistence/store/endpoint (§11) — reuses the existing save path end to end. Chosen at the ComposeWorkspace level (not WorkspacePane) because it is the single choke point every close path already funnels through, so manual tab-close and exclusive-playbook-reset are ALSO covered, not just the History-switch path task 035 added.
- **Non-obvious implementation detail (verified empirically, not just in theory)**: the flush effect MUST be `React.useLayoutEffect`, not `React.useEffect`. React detaches a forwardRef child's `ref.current` (`editorRef.current`, the `ComposeEditorHandle`) during the same synchronous commit pass as `useLayoutEffect` cleanups, but strictly BEFORE the later, separate passive-effect pass that runs `useEffect` cleanups. A `useEffect`-based first attempt measurably saw `editorRef.current === null` at cleanup time (`triggerSave`'s internal `if (!editorRef.current) return;` guard silently no-opped — the flush never fired); `useLayoutEffect` fixed it.
- **Known residual gap (documented, not fixed — narrower than the original concern)**: multiple compose tabs can be mounted simultaneously (kept-alive, hidden except the active one — R2 multi-Compose-tab). The fix is PER-INSTANCE (each `ComposeWorkspace` mount flushes itself independently on its own unmount), so it correctly covers a dirty BACKGROUND compose tab too — this is NOT the single-writer cross-pane bridge (which only reaches the active tab). No further gap identified.
- **Test**: `src/client/shared/Spaarke.Compose.Components/src/widgets/ComposeWorkspace.unmountFlush.test.tsx` — asserts (1) a dirty workspace flushes the captured op-log via `triggerSave` on `unmount()` with no explicit Save ever fired, (2) a clean (never-edited) workspace does NOT fire a spurious save on unmount. Both pass. Adjacent regression suites re-run clean: `WorkspacePane.compose-relaunch/compose-run-restore/compose-multi-tab/tab-restore-race.test.tsx` (20/20 passed).
- **Pre-existing, unrelated finding surfaced during verification**: `ComposeWorkspace.saveOpLogPreservation.test.tsx` and `ComposeWorkspace.bornInEditorSave.test.tsx` (+ `.search`/`.imports` variants) currently fail in this worktree on the UNMODIFIED file too (confirmed via `git stash`) — their `@spaarke/ui-components` jest mock is missing a `RichFilePreviewDialog` stub added by a later "Open Document" preview feature, so any promoted-doc fixture crashes with "Element type is invalid." Not caused by this fix; not in DI-02's scope; flagged for a future test-fixture-drift pass.
