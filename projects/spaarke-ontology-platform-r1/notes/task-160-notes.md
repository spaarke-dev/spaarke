## Owner decisions applied (2026-10-23)
1. **Composer**: an opt-in `composeOnly` prop on the shared EmailComposer (no fork; `hostOwnsChrome` unchanged). It hides Send, the From row (switcher and static text) and the External / Internal Only tags; the composer's own `send()` and `saveDraft()` reject with no network call and no host callback. The shared-component diff is its own commit (`a8d213e368`) for the email project and R3 to review.
2. **Link by recipient**: an ENABLED systemuser (`internalemailaddress` or `domainname`), INCLUDING one flagged `sprk_isexternal`, gets the app link; anyone else the portal link; mixed gets both, labelled. The owner chose this over treating flagged-external users as external. A contact and a systemuser sharing an address (`systemuser.sprk_primarycontact`) is settled by the rule: the enabled systemuser wins, so it is not a STOP. The read is the A9 licensed-user read (`IContactIdentityStore.FindEnabledSystemUsersByEmailAsync` + `ContactBindingDecision.DecideLicensedUserEmail`), app-only.
3. (a) The client commits the composer's ADDRESSES (`BudgetInquiryActionExecutor.Map` passes `to` unchanged). No id resolution added. (b) App link = `Dataverse:EnvironmentUrl` (must be absolute https) + `/main.aspx?etn={logical}&id={id}&pagetype=entityrecord`. (c) Footer: see the deviation below. (d) The matter's name and number are read at send time as the BFF (`IFieldMappingDataverseService.RetrieveRecordFieldsAsync`). (e) Only the matter core is supported (the commit route sets `MatterId` only for a matter); the token map also lists project / workassignment / invoice for the portal, but no label columns for them.

## Deviation from D-181's footer text (recorded per owner 2026-10-23)
D-181 said the footer reads "Budget inquiry: {core name} ({core number})". `EntityName` is ALSO written to `sprk_communication.sprk_regardingrecordname` (`CommunicationService.cs:2723-2724`), which must name the RECORD, so `EntityName` is "{core name} ({core number})" (name alone with no number, number alone with no name) with NO prefix. With the default template the footer reads "This message is filed with Spaarke regarding Acme v. Roe (MAT-000123). Ref: {token}". The subject already says it is a budget inquiry, so nothing else was needed. The label is cut to 99 characters + an ellipsis so it fits the 100-character column. When the matter cannot be read, `EntityName` is the inquiry's own subject (the service request's name), never a logical name and GUID.

## Decisions (directional)
- A recipient whose user read FAILS is treated as external (portal link) and logged at Warning (count only, no addresses). Not internal: the app URL is not offered to someone we could not classify.
- Mixed recipients with one link unavailable: the available line is still labelled.
- The prefill reads only for a plan with send-budget-inquiry on a matter core (must-not-fire otherwise); a fault gives no prefill and never fails the plan read.
- `onStateChange` writes only real changes, so mounting the composer over the starting values is not a "choice" (the discard check is unchanged).
- A body the user switches to rich text is committed as plain text (block ends become line breaks).

## Known limits
- **Cc / Bcc** are not part of the action (the executor has `to` only). The composer still shows them; when the user adds any, the step shows a warning that they are not sent. Hiding them would need another composer prop (not decided).
- send-reminder and send-email also render the composer (POML constraint). Their server send is unchanged; their `to` is now addresses from the composer (the executors accept addresses already). send-reminder's empty-To law-firm fallback is unreachable from the composer because `to` is required (it was already required).
- A side-pane pick of a contact with no usable email address adds nothing and the step now says so (fix round 1, F2).
- The prefill shows the address only (the composer's `initialTo` is addresses); the name is in the DTO for a later use.
