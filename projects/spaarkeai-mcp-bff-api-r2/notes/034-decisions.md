# Task 034 — spaarke_get_briefing and the Daily Briefing widget (FR-09, FR-16)

## D-034-render — which briefing call the tool makes

- **Decision:** the tool returns what `POST /api/ai/daily-briefing/render` returns (`DailyBriefingNarrateResponse`).
- **Why:** `/render` is the only briefing call the Console's `DailyBriefingApp` makes (`useBriefingRender` -> `fetchBriefingLive`).
  `/summarize` is not called by it, and `/narrate` takes a payload a tool cannot supply. So the Console and Copilot show the same briefing
  for the same user and windows.
- **How:** the route's rules moved into one private `RenderCoreAsync` in `DailyBriefingEndpoints.cs`. The route handler maps its answer to the
  same `IResult` as before (REST bytes unchanged: the existing route tests pass untouched). A new public
  `DailyBriefingEndpoints.RenderForCallerAsync(HttpContext?, RenderDailyBriefingRequest?, ct)` runs the same core for the tool and reads the three
  services from `HttpContext.RequestServices`, so `Api/Mcp/**` names no `Services.Ai` type (ADR-013; same precedent as `ListPlaybooksForCallerAsync`).
- **Not cached:** the briefing is regenerated per call, as the Console's Refresh does.

## Decisions

- **No FR-14 start/status.** The render is one synchronous composite call, not a playbook run: there is no run record to start and poll. The
  tool enforces `McpLongRunning.Budget - 3 s` (27 s) with a linked cancellation token and answers `briefing.timeout` (504, fixed text: "Ask again, or open it in the Spaarke Console.") instead of hanging. Whether real briefings exceed 27 s is unmeasured: measure at dev deploys 039/043 (deferred, D-034-1).
- **Argument check.** `dueWithinDays` (1-31, default 5) and `recencyHours` (1-744, default 168), both optional; the schema is closed. An absent window is the
  Console's default, not the collector's 120 h (see "Verifier fixes", F4). The route clamps; the tool refuses
  an out-of-range or mistyped value with `briefing.invalid_parameter` (400), because a model that asks for 40 days should be told, not silently
  given 31. The message names the fix and never echoes the value.
- **Reason codes.** `DATAVERSE_USER_CONTEXT_REQUIRED` (no caller 401; a caller with no Spaarke user 403, as the route), `briefing.unavailable`
  (503: feature off, binding unconfigured, circuit open), `briefing.failed` (500), `briefing.timeout` (504), `briefing.invalid_parameter` (400).
  The route's own 503 detail for an unconfigured binding (`ex.Message`) is never copied into a result.
- **Model-visible text (ADR-015).** Counts line, then the TL;DR summary and key takeaways, each value through `McpText.SingleLine`, clipped to at
  most 1,000 characters. Per-channel detail (record names, descriptions) is only in `structuredContent`, for the widget.
- **Size bound (NFR-02).** At the route's worst case (50 rows in each of 4+ channels) the body is over 64 KiB. `BriefingSizeBound` keeps the
  structured briefing under 56 KiB: it blanks the bullets' descriptions first, then keeps the first N bullets of every section (N halving), so no
  section disappears; the text says how many highlights were left out, and `structuredContent.omittedHighlights` carries the count (only then; the widget shows a warning bar). A briefing
  that fits is returned untouched (REST parity holds for an untrimmed briefing only; a trimmed one is never the route's body).
- **`ReadOnly = true` although the route writes.** Each render writes a capability-ledger entry (when
  there is something to narrate) and may write de-duplicated proactive suggestion cards (FR-15) that appear in the Console. The Console does the same on
  load, so the tool is annotated read-only and idempotent. Known limit K1: a client that treats `readOnlyHint` as "no side effect at all" is wrong about the
  ledger entry and the cards (an approval prompt for a "write" tool would not be shown for this one).

## Widget decisions

- **First read = the opening result.** The host delivers the tool result that opened the widget (`toolResult` on the shared host connection). The
  widget's first `renderBriefing` takes it (single use, up to 45 s wait) instead of calling the tool again, so opening the briefing costs one
  generation. A second read (Refresh) calls the tool. If no result arrives, the widget asks for the briefing itself.
- **Default windows (was known limit K2; fixed, F4).** The opening result is generated by the model's call, which usually has no arguments. It now gets the
  Console's defaults (5 days, 168 hours), the same windows the widget sends on its own reads (Refresh), so the first view and a refreshed view agree. What
  is still not applied is the user's SAVED preferences (D-034-2).
- **Bundle: 1.13 MB** (target 1 MB, ceiling 3 MB; `check-bundle-size.mjs` warns, passes). Kept down by build-time shims
  (`src/shims/*`), not by changing the Console component:
  - `@spaarke/auth` -> a shim whose `authenticatedFetch` always rejects (no fetch, no MSAL in a sandboxed page);
  - `@spaarke/ui-components` (barrel) -> deep-path re-exports of what the briefing package uses, plus stand-ins for `SendEmailDialog` and
    `RichFilePreviewDialog` that draw nothing (the component opens them only from actions a widget hides; the composer carries lexical; 1.56 MB -> 1.16 MB);
  - `@spaarke/ui-components/services` (barrel, which pulls marked, DOMPurify, Application Insights, chat) -> five deep-path re-exports.
  - Types come from the package's deep paths, not its barrel (the barrel registers the Console's workspace widget).
- **Hidden, not stubbed:** with an injected `BriefingDataService` the component hides inline To Do, dismiss, email, document preview, the
  Preferences menu and record links (task 010). The widget supplies `renderBriefing` only and `navigation.openUrl` (mapped to the host's open-link).
- **Zero network/Xrm:** `App.test.tsx` mounts the real component, mocks `@spaarke/auth` and `getXrm`, defines a counting `window.Xrm`, and asserts none is
  touched on open, on Refresh and with the actions hidden.
- **Theme:** `hostTheme.ts` is now in `src/client/widgets/shared/mcp/` (exported from the barrel) for the r2 widgets; the Decisions widget keeps its
  own identical copy (r1 file, not touched; D-034-3).
- **Not StrictMode** in `main.tsx`: an effect running twice would trigger a second generation.

## Verifier fixes (two review passes)

- **F4, FR-09 parity: an absent window is the Console's default.** The Console always sends windows (the user's saved Daily Digest preferences, else 5 days and
  168 hours: `DEFAULT_DAILY_DIGEST_PREFERENCES`, `timeWindowToHours('7d')`). The tool, called with no arguments, used to pass none, so the route gave it the
  collector's 120 h. `GetBriefingTool.TryReadArguments` now defaults an absent `dueWithinDays` to 5 and an absent `recencyHours` to 168 (`DefaultDueWithinDays`,
  `DefaultRecencyHours`). The collector's own default (120 h) is NOT changed: the email and scheduled paths use it. The tool description and the schema text say
  168. Tests: windows forwarded for none / one / both arguments; descriptor text.
  - **Saved preferences are not applied (D-034-2).** Searched `src/server` for a service that reads `sprk_userpreference` (the Daily Digest type, 100000002) as the
    caller: none exists. The only server mentions are a comment in `DailyBriefingCollector`, an entity-name list in `OwnedChildWrite`, and
    `PlaybookRunContext.UserPreferences`, which nothing populates. The Console reads the row from the browser with `Xrm.WebApi`. Reading it here would be new
    surface (CLAUDE.md section 11), so it was not added; the `disabledChannels` filter is client-side in `DailyBriefingApp` and so is not applied by the tool either.
    A user who has saved narrower or wider windows, or disabled channels, sees a different briefing in Copilot than in the Console. **The owner may narrow FR-09 to
    "default preferences"** or accept the draft issue in notes/defer-issues.md (D-034-2).
- **F1, a trimmed briefing says so.** `BriefingSizeBound.Fit` trims descriptions first (nothing is left out) and then trailing highlights. When highlights are left
  out the result adds `structuredContent.omittedHighlights` (a count) and the widget shows one Fluent warning bar: "N highlights were left out; open the Spaarke
  Console for all of them." (a briefing trimmed only of descriptions, or not trimmed, has no such property and no bar; the bar follows each read, so Refresh clears
  or sets it). **REST parity (`structuredContent` equals the route's body) is promised for an untrimmed briefing only.** Tests: tool (worst case; description-only
  trim; untrimmed parity; `Structured`) and widget (opening result, no notice, Refresh both ways, the count's reader).
- **F1, a cancelled caller lookup is not a failure.** `ResolveSystemUserIdAsync` caught every exception, so a cancelled systemuser lookup (an aborted request, or the
  tool's 27 s budget running out during it) was logged as an error and answered 500 `briefing.failed`. It now rethrows `OperationCanceledException` when the
  caller's token is cancelled, so the tool answers `briefing.timeout` and the REST route stops logging an aborted request as an error. Every non-cancelled outcome
  (401, 403, the 500 for a failed lookup) is unchanged, and the existing route tests pass untouched. A new test pins that a non-cancel lookup fault is still the
  route's 500 and the tool's `briefing.failed`.
- **F2, CI path filters.** The widget's build shims re-export deep paths of `Spaarke.UI.Components`, so `src/client/shared/Spaarke.UI.Components/src/**` is now in
  `publish-bff-artifact.yml`'s pull_request paths and in the `mcp_conformance` filter of `ci-tier1-blocking.yml` (the narrower `EmailComposer/**` line stays).
  Both files parse as YAML; Actions itself was not run.
- **F2, test clock.** The timeout test no longer asserts on `DateTimeOffset.UtcNow` elapsed time; a hang would stall it to the runner's timeout, which is the failure.
- **Small fixes.** The timeout text is "Ask again, or open it in the Spaarke Console." (the render stops with the budget; it does not keep running). The comment on
  `ReadOnly = true` now says what the call writes (above). `widgetSurface.test.ts`'s `BUILT_FORBIDDEN` also forbids `.fetch(` (a method call), with must-fire controls;
  the built page passes (no `.fetch(` in it).

### Known limits that remain (owner questions)

- **K3, rate limit.** The tool runs under the `mcp` policy (60 calls per caller per minute); the REST `/render` runs under `ai-batch` (20 per user per minute). Each tool
  call is a full AI render, so a model that loops can render 3 times as often as the REST route allows. Owner's call: give the tool its own tighter limit, or accept.
- **K4, oid in route logs.** The shared route methods log the caller's `oid` (`{AadOid}` in the lookup lines) on the MCP path as on REST. The tool's own telemetry line
  carries none. ADR-015 permits GUID ids; the strict reading of NFR-05 is the existing project-wide owner question (tasks 008, 024).
- **K1, readOnlyHint** (above): the tool is annotated read-only although each call writes a ledger entry and may write suggestion cards.
- **FR-14 is unmeasured.** Whether real briefings exceed the 27 s budget is not known; measure at the dev deploys (D-034-1, #3226).
- **Saved preferences** (D-034-2, above).
