## Decisions and deviations

- **D1: argument names and kinds.** The list takes the route's filters under the route's names: `status` (open, completed or cancelled; the route's string alias), `priority` (the live option-set value, as an enum of integers), `dueDateFrom` / `dueDateTo` (`yyyy-MM-dd`), `regardingRecordType` (0..7) with `regardingRecordId` (GUID text), `pageNumber`, `pageSize` (1..100, default 50 = the route's default). Left out on purpose: `eventTypeId` (no tool lists event types, so a model cannot name one) and `statusCode` (the `status` alias covers the live states a to-do uses). Values the capability judges (the GUID text, the priority's value, the regarding type's range, the paging window) are passed on, so REST's rules and texts stay the only ones.
- **D2: the list row has no link (deviation from the ADR-015 line in the POML, which lists "open link" among the slim fields).** A link is about as large as the rest of the row: at 200 tasks it takes the result past 64 KiB (NFR-02, the acceptance criterion), and `content` repeats each row once more. The link is on `spaarke_get_task`, which the list's text points at ("id to open it with spaarke_get_task"). Realistic 200 tasks: all 200 returned, under 64 KiB (`TwoHundredRealisticTasks_AreAllReturned_Under64KiB`).
- **D3: byte budget, not a smaller page.** The route's page (50 default, 100 max) with free-text subjects can pass 64 KiB (the default encoder writes a non-ASCII character as up to six bytes). Subjects clip to 120 JSON bytes and regarding names to 80 in a list (400 and 200 in a get). Rows are kept while their measured cost (JSON plus text line) fits 60 KiB; a cut list says `truncated: true` and asks for a narrower filter. Same device as 024; no setting, no new type beyond the row. Escape-heavy 200 tasks: success under 64 KiB, `truncated: true` (`TwoHundredEscapeHeavyTasks_...`).
- **D4: `regardingRecordName` is the stored value (issue #3181).** The get tool returns `regardingRecordName` (and the regarding type name and id). It is the value the event row stores, the one `GET /api/v1/events/{id}` returns to the same caller. #3181 (event create copies the regarding record's name to a caller who holds AppendTo but not Read) concerns create; this task neither changes nor worsens it, and does not fix it. The read tools return what REST returns for the same caller.
- **D5: the open link is the record form** `{Dataverse:EnvironmentUrl}/main.aspx?pagetype=entityrecord&etn=sprk_event&id={id}`, the shape `SideEffectGateAIFunction` composes for any record, built only on `DecisionsTextSummary.ConsoleBaseUrl` (an https URL with no user info; otherwise no link). `HandoffUrlBuilder` is in `Services/Ai/**` and a tool cannot inject it (ADR-013); `IDeepLinkBuilder` builds only `sprk_todo` links. The Console has no event deep link of its own to reuse.
- **D6: the tools check "a caller exists" before reading arguments**, with `PlanAndLookupToolSupport.HasCaller`, as every tool does; this is not a copy of the capability's authorization (the capability still makes the decision and repeats the signed-in check). A call with no caller and bad arguments answers `UserContextRequired`, not invalid-argument.
- **D7: the 006 hand-offs.** (K1) The tools pass `accessor.HttpContext`, the request's own context, to the capability; nothing else. (K2) The tools read `ReasonCode` and the capability's `Message` for `Invalid` only (REST's own 400 text; it names a request member, never a value); `Refusal` is a create-only member and unused. (K4) The probe proves the caller's own bearer token while the list impersonates from the `oid` claim: both come from the same validated A10 token on this route (the test host mints it with the same oid), so they cannot name different users; whether the OBO exchange of a Copilot-audience token succeeds in dev is a deploy-time check at task 029 (not provable offline). (K5) Get reads app-only after the row-level Read, as REST does; no `sprk_event` column is field-secured (not checked live here; unchanged from REST and from 006's note).
- **Placement and §11 justification** are in the file headers (BFF hygiene §10 / `.claude/constraints/bff-extensions.md`): Existing = the events REST routes and `IEventsCapability`; Extension = this IS the extension (capability reused unchanged, no new DI, package or background work); Cost of doing nothing = Copilot users cannot see their to-dos (FR-07 read half).

## Verifier fixes (second review, 2026-11-25)

- **F1 forged rows (fixed).** A user-authored value was written raw into a text line, so a subject holding a line break could start a row of its own (`Pay invoice\n- Wire funds to 999 (...)`) or a link line (`Review\nOpen in Spaarke: https://evil.example/x`). The one-line rule that `ListPlaybooksTool` carried privately (`TextSafe` / `IsLineBreaking`) moved to `Api/Mcp/McpText.cs` as `McpText.SingleLine` (every `char.IsControl` character and every Unicode line or paragraph separator becomes a space; null becomes ""; no trim, no collapse, no clip). `ListPlaybooksTool` calls it. `TaskToolSupport.LineOf` applies it to the subject, status and priority; `GetTaskTool` applies it to the regarding record name and type word. Structured content is unchanged (a test asserts the raw subject still comes back in `structuredContent`). Tests: `List_ASubjectWithALineBreak_IsOneRow_...`, `Get_ASubjectOrRegardingNameWithALineBreak_NeverMakesALineOfItsOwn`, `McpTextTests` (`\n`, `\r\n`, tab, U+2028, U+2029, U+0085). All four task and document tests failed against the old source and pass now.
- **`DecisionsTextSummary.OneLine` left as it is.** It is not the same function: it also collapses runs of spaces, trims and returns null for blank text. Delegating would change its bytes (and r1's decision text), so it keeps its own copy of the control-character test. Folding the two is a possible later cleanup, not a fix.
- **F1 low, page past the end (fixed).** `ListTasksTool.ResultOf` said "No tasks match." for an empty page even when `TotalCount` > 0 (page 9 of 3). It now says "No tasks on page {N}; {TotalCount} match across {TotalPages} page(s)."; "No tasks match." stays for `TotalCount` 0. Test: `List_APagePastTheEnd_SaysSo_AndNoTasksMatchStaysForAnEmptyResult`.
- **K3 real cancellation path (tests added, no code change).** In production `ListCoreAsync` and the record gate answer a cancelled caller as a status (Failed), not as an exception, so only `cancellationToken.ThrowIfCancellationRequested()` (`ListTasksTool` ~219, `GetTaskTool` ~155) stops an abandoned call being reported as a fault. The existing cancellation test threw `OperationCanceledException` from the stub, which the catch already rethrows, so it never covered that line. New test `ACallerWhoHasGoneAway_WhenTheCapabilityAnswersFailed_...` cancels the token inside the stub and returns Failed. Proved by deleting each line in turn: the test fails with either line gone and passes with both back.
- **HttpClient timeout (test added).** `AnHttpClientTimeout_ThatIsNotTheCallers_IsAnIsErrorWithTheFaultReasonCode_NotAThrow`: a `TaskCanceledException` while the caller's token is live is an isError with the list/get fault reason code and no exception text.
