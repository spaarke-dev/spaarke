## 2. Three reported symptoms, triaged

### Symptom A — "the collision names the wrong file"

Operator expected the collision to name `Examiner report draft.docx`; it named `Untitled Document.docx`.

**CONFIRMED (code):** `OfficeService.cs:640` passes the **requested** `fileName` into
`ResolveNameCollisionAsync(upload, containerId, fileName, contentStream, ...)`. The refusal therefore names
**the file being uploaded**, and a collision means an item of *that same name* already exists in the container.

**So the message is almost certainly accurate**, and it is evidence of something else: there is an
**orphaned `Untitled Document.docx`** already in PAT-191111's container. **HYPOTHESIS:** it was created by the
operator's earlier (2026-09-17) UAT save, which also did not associate — i.e. Symptom C happened first, and
Symptom A is its downstream consequence.

⚠️ Do NOT "fix" the message. Confirm the orphan exists first (§4.1). If no `Untitled Document.docx` exists in
that container, this flips to a genuine defect and the whole diagnosis changes.

### Symptom B — "it did not save as a version of the existing document"

**Expected behaviour, not a defect — given the document matching decision (A + C, B supporting).**

The Word file is a **copy** of a pre-stamp document. `Examiner report draft.docx` was modified 2026-09-04,
before task 014's custom-XML stamp shipped, so the copy carries **no stamp** (FR-02 path A unavailable), and a
local copy has no SPE URL (FR-01 path unavailable). With neither identity signal, the pane correctly treats it
as a NEW document. Recognising "this is a copy of that document" from content alone is exactly what the
owner's decision **declined** to do automatically — path C (the save-time prompt) is the mechanism, and
**"Save as new version" in that very banner is the intended remedy.**

**OPEN QUESTION for the operator:** was "Save as new version" clicked, and what happened? If it was clicked and
still produced a new unassociated row rather than a version, that IS a defect and supersedes this triage.

### Symptom C — "saved to SPE but not associated to the matter" ← **the primary defect**

`_sprk_matter_value = NULL` on the saved row while the file exists in SPE.

**CONFIRMED (code)** — `OfficeDocumentPersistence.cs:256-267`:

```csharp
if (request.TargetEntity != null)
{
    if (!DocumentAssociationMap.TryApply(
            updateRequest, request.TargetEntity.EntityType, request.TargetEntity.EntityId))
    {
        _logger.LogWarning(
            "Target entity type {EntityType} has no sprk_document lookup — document will be "
            + "created UNASSOCIATED. Known gaps: account, contact, sprk_todo (no column exists).",
            request.TargetEntity.EntityType);
    }
}
```

Two facts follow:

1. Association runs **only when `request.TargetEntity != null`**. A save with no target creates an
   unassociated row **silently** — no warning is logged on that branch at all.
2. `sprk_matter` is **not** in the known-gaps list, so a save that *does* carry a matter target should populate
   the lookup and would log a warning if it could not.

**HYPOTHESIS (most likely):** the pane did not send `TargetEntity` on that save — the association never had a
chance server-side. Note the screenshots support this reading: the first shows **no Related-to selection**
("No suggested Matter matches"), and PAT-191111 appears selected only in the *second* screenshot, after the
collision banner.

**COMPETING HYPOTHESIS:** `TargetEntity` was sent and `DocumentAssociationMap.TryApply` returned false for
`sprk_matter`. §4.2 separates these in one log query — the warning fires only in the second case.

⚠️ **Do not assume NULL `_sprk_matter_value` means "unassociated".** Task 026 (`notes/026-slot-scope-decision.md`)
records that `sprk_document` carries **16 association-shaped lookups** — 4 direct slots plus 12 `sprk_related*`
— and `unified-access-control-r2` task 095 adds a two-slot model. Check the other direct slots before
concluding (§4.3). The matter form showing "1 associated document" is corroborating but not conclusive, since
that grid may read a different relationship.

## 3. Why this matters more than it looks

If Symptom C is real, **every pane save that omits a target silently produces an orphan**: bytes in SPE, a
`sprk_document` row nobody can find from the record, and a name that then **blocks the next legitimate save**
of the same file (Symptom A). One missing association turns into a recurring collision.

## 4. Diagnostics that settle this — run these FIRST, in this order

### 4.1 Does the orphan exist? (settles Symptom A)

Read-only Dataverse query for rows named `Untitled Document.docx`, newest first, showing the association slots:

```
GET {org}/api/data/v9.2/sprk_documents
  ?$select=sprk_documentid,sprk_filename,sprk_name,createdon,sprk_graphdriveid,sprk_graphitemid,_sprk_matter_value
  &$filter=sprk_filename eq 'Untitled Document.docx'
  &$orderby=createdon desc
```

- Rows returned → the collision message was correct; Symptom A is a consequence of Symptom C.
- Zero rows → the collision named a file that does not exist as a document row. Re-open Symptom A as a real
  defect and check the SPE container directly.

### 4.2 Was `TargetEntity` sent? (settles Symptom C)

App Insights component **`spe-insights-dev-67e2xz`** (rg `spe-infrastructure-westus2`) — the BFF's component
(`cloud_RoleName = spaarke-bff-dev`):

```kusto
traces
| where timestamp > ago(1d)
| where message has "created UNASSOCIATED" or message has "no sprk_document lookup"
| project timestamp, message
| order by timestamp desc
```

- Warning present → `TargetEntity` WAS sent and the map failed for `sprk_matter`. Fix `DocumentAssociationMap`.
- Warning absent → `TargetEntity` was **null**; the defect is client-side in the save payload. Then check
  `useSaveFlow.ts` / `buildSaveContext()` for whether the selected Related-to record reaches `targetEntity`,
  and whether the collision-retry path ("Keep both" / "Save as new version") **drops** it on the retry — a
  retry that loses the target would explain a selected matter producing an unassociated row.
