# Task 042 — live UAT findings, 2026-09-18 (Word, deployed build v1.0.9)

> **Status: DIAGNOSED 2026-09-18.** Root cause established from five independent directions (Dataverse rows,
> App Insights request+trace log, client code, server code, and the AI profile written onto the victim row).
> Filed as **ISS-006** / [#1005](https://github.com/spaarke-dev/spaarke/issues/1005).
>
> ⚠️ **This note previously carried a triage that was WRONG on its central point** — it called Symptom B
> "expected behaviour, not a defect" and named "Save as new version" the sanctioned remedy. That remedy is
> exactly what caused the damage. §6 records what was wrong and why, because the mistake is reusable.

---

## 1. The defect, in one paragraph

A Word save whose filename collides is refused with `OFFICE_020`, and the pane offers **"Save as new version"**.
That button versions the open document onto **whichever `sprk_document` already owns the colliding file name in
the container** — which, because Word's default name is `Untitled Document.docx` and containers are
business-unit scoped, is routinely **an unrelated document belonging to someone else**. The pane never names
the document it is about to overwrite, and the version path **silently discards the user's selected Related-to
record**. On 2026-09-18 this wrote a patent Examiner's Report into an unrelated orphan row, profiled it, and
indexed it for RAG under that row — while the matter the user had selected received nothing.

## 3. The mechanism, end to end (every step code-verified)

1. **The name.** `WordAdapter.getSubject()` returns `properties.title || 'Untitled Document'` — Word's *Title
   metadata property*, which is normally blank. So a Word document with no Title uploads as
   `Untitled Document.docx`. (`notes/020-filename-defaults-document-name.md`; `notes/025-…` M11.)
2. **The namespace.** Containers are **business-unit scoped** (`RecordContainerResolver.cs:54-55`), and the
   container root is flat. That makes `Untitled Document.docx` **one shared slot for an entire business unit**.
3. **The refusal.** The create upload states `ConflictBehavior.Fail`, so SPE refuses before any bytes move and
   the server returns `OFFICE_020`. **This part is correct and worked exactly as task 025 designed it** —
   "Nothing was uploaded or changed" was true.
4. **The refusal names a document.** The 409 carries `existingDocumentId` = *"the `sprk_document` that already
   holds `fileName` in the target drive"* (`errorMessages.ts:34-36`). Resolved **by file name**, with no
   relation whatsoever to the record the user selected.
5. **The pane offers to version it.** `SaveFlow.tsx:1253` shows "Save as new version" whenever that id is
   present; `handleSaveAsVersionInstead` (`:871-877`) resubmits with
   `saveTarget: { mode: 'version', existingDocumentId }`.
6. **The association is dropped.** `useSaveFlow.ts:937-941` — `const sentEntity = versionTarget ? null : selectedEntity`.
   A version save **never** sends `targetEntity`. PAT-191111 was discarded client-side, before the request left
   the browser.

Step 6 is deliberate and, for its intended case, correct: task 023 D-4/D-5 reasoned that re-associating an
already-filed document would be inert and would add an authorization check that could refuse a legitimate
version save. **The bug is not step 6. It is step 4 feeding step 5** — a filename match being treated as
document identity.

## 4. Consequences

- **Cross-matter content exposure.** The orphan row is still *named* "Untitled Document", but its
  `sprk_filesummary` now reads *"a formal response letter … regarding the Examiner's Report … Canadian Patent
  Application No. 3,116,549 … Borden Ladner Gervais LLP"*, and `sprk_filekeywords` lists the parties. The
  content is also in the `spaarke-files-index` RAG index under that row. Anyone with access to the orphan can
  now read, search and AI-query a document they were never granted.
- **Silent misfiling.** The user selected a matter, clicked the button the pane offered, and got "saved" — with
  the matter empty. Nothing in the UI indicates the association was dropped.
- **BU-wide reach.** One orphan named `Untitled Document.docx` arms this for **every user saving an unnamed
  Word document to any non-secure record in the business unit**.

  `_sprk_matter_value` alone over-counted by 11 rows that are associated via another direct slot — exactly the
  trap §4.3 of the old note warned about.
- **These orphans are long-standing, NOT introduced by this project**: earliest `2026-01-13`, distribution
  `2026-01: 167 · 02: 4 · 03: 30 · 04: 6 · 05: 4 · 07: 14 · 08: 23 · 09: 8`. Record-less saves are allowed by
  design (`notes/025-…` M4), so an unassociated row is not itself the defect.
- **Association is NOT broken.** The row created at `04:21:54` the same morning — `Invoice PAT-942665.docx` —
  has its matter lookup correctly set. Same code path, same day, 11 minutes earlier. This **disproves** the
  competing hypothesis that `DocumentAssociationMap.TryApply` fails for `sprk_matter`.
- **The 423 Locked** at `16:29:49`, between two 409s, is observed and unexplained. Low priority; recorded so it
  is not lost.
- **App Insights retention is ~2 hours in this component.** All 17,303 rows over the nominal 7-day window sit
  between 15:00 and 17:00 UTC on 2026-09-18. Telemetry for the 04:32 save **does not exist and cannot be
  recovered** — do not re-run that query expecting an answer.

## 6. What the earlier triage got wrong

| Old claim | Verdict |
|---|---|
| "Symptom A — the collision message is almost certainly accurate." | ✅ **Right.** The orphan exists and owned the name. |
| "Symptom B — expected behaviour, not a defect … **'Save as new version' is the intended remedy**." | ❌ **Wrong, and it was the important one.** That remedy is the defect. The note reasoned correctly that *content-based* matching was declined by the owner, then assumed the collision prompt was therefore safe — without checking what the prompt's own button targets. |
| "Symptom C — leading hypothesis: the pane sent no `TargetEntity` on that save." | ⚠️ **Right mechanism, wrong save.** The target was dropped, but by the *version* path on the 16:30 save, not by a missing selection on a create. The 04:32 orphan is a separate, earlier event. |
| "Competing hypothesis: `TryApply` returned false for `sprk_matter`." | ❌ **Disproven** by the 04:21:54 row. |
| "§4.2 App Insights will separate these." | ❌ **Unanswerable.** No telemetry survives for 04:32. The question was settled by Dataverse row-creation times instead. |

**The reusable lesson**: the old §5 said *"Do not add content-based auto-matching for Symptom B — that is the
owner decision, and 'Save as new version' is the sanctioned path."* Citing a correct owner decision to close a
question is not the same as verifying the thing you are recommending instead. The sanctioned path had never
been traced to the line that picks its target.

## 7. Suggested fix (for the owner — not implemented here)

The minimum honest fix is **two changes that must land together**:

1. **Name the document before offering to version it.** The 409 already resolves a document id; the pane must
   show *which* document ("Save as a new version of **{name}** — filed to **{matter}**") so a user can see it is
   not theirs. A filename match is a *suggestion*, never an identity.
2. **Do not offer the version retry when the colliding document's association contradicts the user's
   selection** — or, at minimum, carry the selected `targetEntity` through and refuse server-side rather than
   dropping it silently. Today the pane discards the user's explicit choice with no indication.

Worth considering alongside, but **owner-scoped** (it is note 025's open question 8, still unresolved):
`Untitled Document.docx` as the default upload name is the multiplier that makes this reachable at all.

⚠️ **Do NOT "fix" this by making the version save re-associate.** That would silently re-file someone else's
document onto the current user's matter — a worse outcome than the one being fixed, and it would cross the
authorization boundary task 023 D-4/D-5 deliberately avoided.
