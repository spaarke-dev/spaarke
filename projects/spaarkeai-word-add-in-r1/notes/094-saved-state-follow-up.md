## 1. What shipped

| Area | Change |
|---|---|
| **Name lock** | Once a document is in Spaarke — the pane opened on a resolved identity (pre-save) OR this pane session already saved it (post-save) — the Document Name field renders **read-only** (`renderDocumentDetails('locked', …)`), showing the Spaarke name (the resolved identity's `documentName`/`fileName` for a version save; the typed name for a create) with a hint ("This document's name is set in Spaarke. | **"Save as new document" unlock** | One handler (`handleSaveAsNewInstead`) serves both the pre-save locked box and the post-save locked box: pre-save it flips the save-mode choice to `'new'` (the form switches to the plain create path with `RelatedToPicker` + the editable name field); post-save it also clears the saved-state bundle. Suppressed in the locked box when the ERROR banner is already offering the identical action (`error?.offerSaveAsNew`) — otherwise a refused version save showed the SAME button twice. |
| **Button wording** | The save button reads **"Save"** whenever it is enabled, everywhere in the pane — including when the pane opens on a document already in Spaarke. "Saved" (gray, disabled) and "Save as new document" are unchanged. | **Own-write suppression (AC3)** | `WordAdapter._suppressDocumentChangeEvents` is set `true` for the duration of `writeDocumentStamp`'s custom-XML-part write (task 089) and checked by the wrapped change handler before calling `onChange`. Belt-and-suspenders: a custom XML part write touches no paragraph, so it is not expected to fire a paragraph event at all (same class of inference as task 089 §2's "Word persists an addAsync part the same way its own data-store parts are wired" — not directly observed, reasoned from the API surface), but nothing in the documentation GUARANTEES that, so the flag makes it true by construction either way. Pinned by `WordAdapter.documentChangeDetection.test.ts`'s "a change event fired mid-writeDocumentStamp is suppressed" test, which simulates the worst case (the mocked `addAsync` fires a change event synchronously, mid-call). |
| **Re-enable rule** | `SaveFlow.hasUnsavedChanges = savedDocument !== null && canSaveNewVersion && (!canDetectDocumentChanges \|\| contentChangedSinceSave \|\| profileRegenerated)`. With detection supported: "Saved" (gray) until a content-change event sets `contentChangedSinceSave`, or a Generate Profile sets `profileRegenerated` (088 behaviour, kept). **Without** detection: the `!canDetectDocumentChanges` term is unconditionally `true`, so the button is an enabled "Save" immediately after saving — the owner's binding "never block a save" rule. The removed 088 name-edit trigger (`savedNameChanged`) has no replacement; the name box can't be edited from the saved state at all now. |
| **Lifted saved state (App.tsx)** | `SaveFlow` is optionally controlled: new props `savedState?: SavedDocumentPaneState` / `onSavedStateChange?: React.Dispatch<React.SetStateAction<SavedDocumentPaneState>>`. Omitted → `SaveFlow` keeps its own `useState` (every existing caller/test unaffected). `App.tsx` holds `const [saveFlowState, setSaveFlowState] = useState<SavedDocumentPaneState>(DEFAULT_SAVED_DOCUMENT_PANE_STATE)` and passes both through `SaveView` → `SaveFlow`, so the bundle (`savedDocument`, `profileRegenerated`, `profileRefreshSignal`, `contentChangedSinceSave`) survives a Save-tab remount (switching to To Do/Find and back) because `App` itself never unmounts on a tab switch — only the tab's own view does. |
| **Content-change subscription lives in `SaveView`** | New `shared/taskpane/services/documentChangeDetectionService.ts` (`subscribeToDocumentChanges`) bridges the adapter's async `registerDocumentChangeHandler` to a synchronous subscribe/unsubscribe pair for `useEffect`. `SaveView` registers it unconditionally (capability-gated internally) for the Save tab's own lifetime and calls `onSavedStateChange` to flip `contentChangedSinceSave` to `true`. Unmounting the Save tab (switching away) removes the handler (AC3's "handlers are removed on unmount") — edits made while the tab is unmounted are simply not observed; the AC only requires the SAVED STATE (not live edit-tracking) to survive the switch. |
| **Two-button "Open" on collision** | `openRecordLauncher.openDesktopUrl(url)` — a synthetic `<a href="ms-word:…">.click()`, always reports `{opened: true}` (nothing can detect a failed launch). New `HostCapabilities.canOpenDesktopWord` (both adapters: `true` only on `Office.PlatformType.PC`/`Mac` — **platform, not host**: the collision's "Open in Word" opens the OTHER document, always a Word file, reachable from an Outlook-hosted pane too). **Placement (CLAUDE.md §11 — component justification):** no new BFF route, service or DI registration; `open-links`'s `desktopUrl` field already existed and was simply unused by the client until now. One new client service (`documentChangeDetectionService.ts`) — justified because the async-registration-to-sync-unsubscribe bridge is a distinct responsibility from both the adapter (Office.js mechanics) and `SaveView` (React lifecycle wiring), and is independently unit-tested at the WordAdapter level already; a third thin layer avoids duplicating the cancel-race handling in both `SaveView` and any future caller.

## 2. Verified: the Word content-change event API (escalation trigger — did NOT fire)

The POML's escalation trigger: *"No Word content-change event exists in a GA requirement set that Word desktop 2501+ and Word on the web support."*

Verified on Microsoft Learn, 2026-10-04 (WebSearch + WebFetch, not inferred from memory):

- **API**: `Word.Document.onParagraphAdded`, `Word.Document.onParagraphChanged`, `Word.Document.onParagraphDeleted` — `https://learn.microsoft.com/en-us/office/dev/add-ins/word/word-add-ins-events` (GA table, not the "preview" table further down the same page) and `https://learn.microsoft.com/en-us/javascript/api/word/word.document`.
- **Requirement set**: **WordApi 1.6** — `https://learn.microsoft.com/en-us/javascript/api/requirement-sets/word/word-api-1-6-requirement-set`. The page's own description: "WordApi 1.6 mainly added enhanced support for management of styles and tracked changes" (these three events are listed in its API table).
- **Platform availability (GA, not preview)**: Office on the web — supported; Windows (Microsoft 365 subscription + volume-licensed/LTSC) — version **2308** (build 16731.20234); Mac — version **16.76**; iPad — version **16.76**. All of these predate the POML's "desktop 2501+" floor by roughly a year and a half (build 2308 = August 2023); the requirement set has been GA since then, not newly added.
- **Coauthoring**: all three events fire for both local (`event.source === 'Local'`) and remote (`'Remote'`) edits — not used by this task, noted for completeness.
- **`track()`**: NOT required for these three (the `.track()` requirement in the events article applies only to content-control and comment events).

**Conclusion**: the escalation trigger's premise is false — a GA requirement set exists, is old enough to already be on every supported platform, and the API shape matches exactly what the POML's background section guessed (`onParagraphChanged` / `onParagraphAdded` / `onParagraphDeleted`). No escalation needed; proceeded directly to implementation.

**Sources**: `https://learn.microsoft.com/en-us/office/dev/add-ins/word/word-add-ins-events`, `https://learn.microsoft.com/en-us/javascript/api/requirement-sets/word/word-api-1-6-requirement-set`, `https://learn.microsoft.com/en-us/javascript/api/word/word.document`.

## 4. Deviations from the POML (directional mode)

- **Duplicate "Save as new document" suppression** — not named in the POML. The locked name box's own unlock button and the error banner's `offerSaveAsNew` button are the SAME action reached two ways; when both would render at once (a refused version save of an already-locked document), the locked box suppresses its copy (`!error?.offerSaveAsNew`) rather than showing two identically-labelled buttons. Judged necessary, not optional — the alternative is confusing duplicate UI, not a design choice with two reasonable answers.
- **Removal mechanics for `registerDocumentChangeHandler`'s unsubscribe** — the POML/background didn't specify HOW to remove the handler; Microsoft Learn's sample uses `Word.run(eventContext.context, async (context) => { eventContext.remove(); await context.sync(); })`, but **Word.run has no context-accepting overload** in the installed `@types/office-js` (confirmed by `tsc`; Excel/Visio DO have one, Word doesn't). Used `handler.remove()` followed by `context.sync()` directly on the `RequestContext` instead — same two steps (queue the removal, then sync it), without going back through `Word.run`.
- **Locked name's displayed value for a version save** — uses the resolved identity's `documentName`/`fileName` (the record's actual Spaarke name), not the local `documentName` field state (which the user can no longer edit in this mode, but which started from an FR-06 default derived from `itemName` and could in principle differ from the stored record name, e.g. if the file was renamed locally after being downloaded). Noted as a known best-effort: if `documentIdentity` is somehow stale or absent, falls back to the locally-held name.
