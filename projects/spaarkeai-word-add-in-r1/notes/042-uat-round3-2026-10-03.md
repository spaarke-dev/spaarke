## 2. UAT-9 diagnosed: Quick Save collided with the document's OWN earlier save

Every ribbon Quick Save (`HasTargetEntity=False` in the BFF's "Save request received" trace) in the window:

| Time (UTC) | File name sent | Result | Collided with |
|---|---|---|---|
| 10-02 23:49 | The Newfound Importance of Knowledge Management.docx | **409 `OFFICE_020`** | `2bcfc5d2-…`, created **10-02 21:17 by this user's own pane save** of the same document (filed to `PAT-176903`) |
| 10-03 16:55 | same | **409 `OFFICE_020`** | `2bcfc5d2-…` again |
| 10-03 17:02 | Untitled Document.docx | **409 `OFFICE_020`** | `c2acd288-…`, an Aug-13 orphan of the same default name |
| 10-03 17:03 | Invoice 00012 from Word Add in 10-3-2026.docx | **succeeded** — document `1eea00c5-…` created and profiled | — |

**Chain, every step evidenced:**
1. The pane saved the document on 10-02. The server stamps the identity into the **stored** copy (task 014). The
   document **open in Word is never stamped**: the client only reads stamps (`WordAdapter.readDocumentStamp`); no
   code writes one.
2. The next save from the same open document cannot recognise it. The ribbon sends no identity at all; the pane
   recognises it only within the session that saved it (task 077).
3. It is therefore a create, under the same file name, into the same business-unit container → Graph refuses the
   name (`conflictBehavior=fail`) → 409 `OFFICE_020`.
4. The ribbon catches every error in one `catch` (`word/commands/index.ts:158`) and shows the fixed text "Failed to
   save. Open Spaarke to try manually." The server's message, code and correlation id are logged to a hidden console
   only.

The pane saves at 16:46, 16:48 and 16:50 hit the same collision. The pane offered Keep both only because the owning
document was not filed to the record chosen in the pane, and Keep both produced
`The Newfound Importance of Knowledge Management Version 2.docx`. That is the "Name Already Exists" screenshot
(UAT-5).

**Owner decisions, 2026-10-03** (asked in session):
- After a save, **write the identity mark into the open document**, accepting that Word then sees the document as
  changed. Pane saves, Quick Saves and a copy reopened from disk then recognise it.
- Quick Save, when the name belongs to a **different** document: **keep both automatically** and say which name
  was used.
- **Share is removed from the ribbon** and, in a follow-up message the same day, **replaced by "Open Spaarke"**,
  which opens the app. The owner asked: *"which app? how do we resolve that?"* — see §3a.
- The Save tab **keeps the form** after a save (confirmation bar; Open Document; a gray "Saved" button that becomes
  "Save version" when the name or profile changes).

**Correction to round 2.** `042-uat-round2-2026-09-30.md:75` says Quick Save calls resolve-identity first. It does
not; that code (`index.ts:171-177`) is the Share command's. Quick Save sends no identity.

## 3. UAT-10: what Share did (now removed)

`shareDocument` (`word/commands/index.ts:194-227`) resolved the document's identity, and if it was not in Spaarke,
opened the pane with **no message**. Otherwise it called `POST /api/documents/{id}/share-link` (Share right
required), which creates a **view-only, organization-only, expiring** link. It then tried to copy the link to the
clipboard, **ignored a failure**, and **always** said "Share link copied to clipboard." The link was never shown.
The pane's Copy Link and Send Email remain.

## 3a. "Open Spaarke": which app, and how the add-in names it

**What exists (dev, read live 2026-10-03, `appmodules` + `sitemaps`):**

| App | Unique name | What it is |
|---|---|---|
| **Matter Management** | `sprk_MatterManagement` | The user app. Its first page ("Work → Workspace") is the **Console** (`$webresource:sprk_spaarkeai`); then Matters, Projects, Invoices, To Do List (`sprk_smarttodo`), Email Review, AI Search, Documents, Email, Reports, Contacts and an Admin area |
| Spaarke Platform | `sprk_SpaarkePlatform` | Records plus "Console Settings" (policies, signals, decision records…) |
| Spaarke AI Setup | `sprk_SpaarkeAISetup` | Admin set-up |

**Recommended resolution (task 089; the owner may override before it runs):**
- "Open Spaarke" opens **Matter Management at its Workspace (the Console)**:
  `{ORG_URL}/main.aspx?appname=sprk_MatterManagement&pagetype=webresource&webresourceName=sprk_spaarkeai`.
- The app is named by its **unique name** (`appname=`), not its GUID. The unique name travels with the solution,
  so it is the same in every environment. The app id is a GUID and is the wrong key to configure.
- It is a **build setting next to `ORG_URL`** (`SPAARKE_APP_NAME`, default `sprk_MatterManagement`), injected by
  `deploy-office-addins.yml` the same way. Per-customer builds already exist (D-13), so a customer whose app has
  another name changes one setting and no code.
- The same `appname` goes on **every record link the add-in opens** (`openRecordLauncher.buildOpenRecordUrl`, used
  by View Document, Open Document, the To Do link, Find and Send Email's record link). Today those URLs carry no app,
  so a record opens in **the user's default app**, which may not be Spaarke's. That is the other half of UAT-1
  ("open the Spaarke app Document").
- If the setting is absent, the button is not shown (the same rule as `ORG_URL` today), never a guess.

## 4. Two server defects found while diagnosing (task 093)

### 4.1 The save's job row never reaches a terminal state

Every successful save since **10-02 20:49** (5 of 5) left its `sprk_processingjob` row at
`sprk_status = 1 (In Progress)`, stage `FileUploaded`, progress 70. Three earlier saves the same day (12:22, 12:25,
13:27) ended `Completed / Complete / 100`. The request itself logged `recorded: Completed, Complete, 100%` (the save's
own view in `sprk_result`, which the pane reads, so **the pane is unaffected**). About 1–3 s later
`UploadFinalizationWorker` rewrites the pipeline columns to Running/70 and then hands profiling to
`AppOnlyDocumentAnalysis` (`QueueNextStageAsync`). Nothing closes the row afterwards. Why the midday rows did
close is part of the task.

### 4.2 Request telemetry is cut short by `using var activity = Activity.Current`

`UploadSessionManager.UploadSmallAsync` (`Infrastructure/Graph/UploadSessionManager.cs:122`) **disposes the
request's own Activity** when the method returns. The request is then exported early: `resultCode 0`,
`success = false`, a truncated duration (1.4 s of a 3 s request), and the upload's tags
(`operation=UploadSmall`, `filePath`) on the request record. Both "status 0" saves today (16:48, 17:03) **succeeded**.
The same line appears at **20 sites** in `Infrastructure/Graph` (`DriveItemOperations.cs` ×15,
`ContainerOperations.cs` ×4, `UploadSessionManager.cs` ×1), so every Graph-touching route's success rate in
App Insights is unreliable.
