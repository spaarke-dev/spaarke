## The measurement — determined empirically, as the constraint required

The constraint was *"determine empirically which specs CAN run headless… do not assume either way."* The
`.env.example` keys (`CLIENT_SECRET`, `TEST_USER_PASSWORD`, `TENANT_ID`) *look* like proof a live tenant is
required, and stopping there would have been the easy wrong answer. The code says otherwise:

- the specs default to **`https://localhost:3000/taskpane.html`**, not a tenant URL;
- there are **24 route-interception calls** across the spec and its page object, so the BFF is **mocked**;
- `WordTaskPanePage.mockWordEnvironment()` injects `window.Office`/`window.Word` via `addInitScript`, so
  **Office.js is mocked too**;
- the build's four required env values (`ADDIN_CLIENT_ID`, `TENANT_ID`, `BFF_API_CLIENT_ID`,
  `BFF_API_BASE_URL`) are **plain text in `deploy-office-addins.yml:66-69`** — public client IDs and a URL, not
  secrets. **CI can supply them.**

So I ran it, rather than reasoning about it:

1. `npm install` at the repo root (8 devDeps — Playwright is declared there, and was **not installed**).
2. `npx playwright install chromium`.
3. Built the add-in with those four env values → `dist/word/taskpane.html`.
4. Served `dist/` on `127.0.0.1:3000` (HTTP 200 confirmed).
5. `npx playwright test --project=chromium tests/e2e/specs/word-addins/save-flow.spec.ts` with
   `ADDIN_TASKPANE_URL` overridden.

**Result: every test failed** with `page.waitForFunction: Timeout 15000ms exceeded`.

A timeout alone does not say *why*, so I probed the page directly. The taskpane **boots** and then stalls:

```json
{ "title": "Spaarke for Word", "bodyLen": 66, "rootChildren": 1,
  "fuiFocus": false, "anyFui": 0, "testids": [], "text": "Loading..." }
PAGE ERRORS: none
[Spaarke] Starting initialization...
[Spaarke] Stage 1: Waiting for Office.js...
Warning: Office.js is loaded outside of Office client
[Spaarke] Office.js ready: {host: null, platform: null, addin: null}
[Spaarke] Stage 2: Initializing auth service...        <-- stops here
```

No page errors. It reaches auth init and never returns, so the app never renders and no `data-testid` ever
appears.

## The two blockers — both in the harness, not in the specs' intent

**1. The real `office.js` is never intercepted.** The spec *does* call `mockWordEnvironment()` in `beforeEach`
**before** navigating, so the mock is applied correctly. But a grep for `appsforoffice` / `office.js` across
the spec and the page object returns **zero** hits: nothing blocks the CDN script the taskpane HTML loads. The
real Office.js supersedes the injected mock and reports `host: null`, so host detection never resolves.

**2. Auth cannot complete headless.** With no Office SSO context and no signed-in user, the MSAL-backed auth
service the bootstrap awaits at Stage 2 never settles.

There is also a **third, smaller defect** worth recording because it would bite whoever fixes the first two:
the readiness probe is `waitForFunction(() => document.querySelector('[data-fui-focus-visible]') !== null)`.
Fluent v9 sets `data-fui-focus-visible` on **keyboard focus**, not on mount — so even a fully rendered pane
might never satisfy it. The probe should wait for a `data-testid` the pane actually renders.

## Why this is escalated rather than fixed (the trigger)

> *"If running the e2e specs in CI requires standing up infrastructure this project does not own (a hosted
> add-in, a test tenant), STOP and escalate with the cost — do not build a parallel harness inside this task."*

**Being precise about which half fired matters.** It is *not* the infrastructure half: no test tenant and no
hosted add-in are needed, because the specs mock both the API and Office.js, and the build config is public.

It is the **parallel-harness** half. Making these run means:

| Work | Est. |
|---|---|
| Route-block `appsforoffice.microsoft.com/lib/*/hosted/office.js` and serve a stub, in the shared page objects | ~half a day |
| Complete the Office mock so host detection resolves (`host`, `platform`, `requirements.isSetSupported`) | ~half a day |
| Provide a test seam for the auth service so bootstrap can proceed without MSAL — **a production change**, not a test change | ~1 day + design review |
| Replace the `data-fui-focus-visible` readiness probe with a real signal | ~1 hour |
| Add the CI job: build add-in with the 4 env values, serve `dist/`, run 3 specs on chromium only | ~2 hours |

The third row is the reason this is not a tidy-up. Giving the add-in an auth seam so tests can bypass MSAL is
a **production-code change to an auth path**, which is CLAUDE.md §6 escalation territory in its own right and
should not be smuggled in under a CI-wiring task.

**🔔 Decision needed**: fund that as its own task, or accept these 109 tests as live-host-manual and let
task 042's UAT be the place they earn their keep.
