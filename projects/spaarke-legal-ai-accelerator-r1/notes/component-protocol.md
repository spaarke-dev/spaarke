# Spaarke legal accelerators — component protocol (v0.1 draft)

**Status:** v0.2 draft for owner review, 2026-11-02. v0.2 changes:
- A playbook *set* replaces the single master playbook.
- Plugin K must hold no review procedure, because Word may load it (not yet tested).
- Playbook locations split into personal and governed.
- §4.5 approved. Built from the NDA MVP tenant tests (`notes/mvp-nda/results.md`) and the researcher notes of 2026-10-29 → 11-02.
**Evidence marks:** ✅ verified in our tenant · 📄 documented by Microsoft · ❓ assumed or unknown (each has a test in §8).

This protocol answers, for every primitive we use: **what it is for, why, how it is built, who manages it, and how it is distributed.** It also sets the rules that keep primitives from overlapping.

---

## 1. Principles

1. **Components, not solutions.** Each Spaarke plugin is a functional component that stacks with Microsoft's Legal plugin and third-party plugins. We do not rebuild what an installed component already does.
2. **One job per primitive.**
   - *Positions* live only in playbooks.
   - *Procedures* live only in skills.
   - *Defaults* live only in the profile.
   - *Distribution* is the plugin's job.
   - Nothing is written twice.
3. **One procedure per task per app.** For any task (e.g. "review an NDA") in any app (Word, Cowork), exactly one skill owns it. Where Microsoft already owns it, we supply content (a playbook), not a competing skill.
4. **One source, many outputs.**
   - Every playbook, topic and skill is authored once in `src/accelerators/`.
   - The build generates every distributed form: the Word playbook (.docx), the Cowork playbook, and the plugin zips.
   - Distributed copies are never edited by hand.
5. **Code only where it runs.**
   - Skills that need scripts are Cowork-only (✅ Word never loads our package; 📄 Office-app skills have no Python).
   - Everything else is instruction-only so it can run wherever skills are supported.

## 3. Plugin structure: complementary, never duplicated

Two Spaarke plugins per practice, each with a disjoint set of skills:

| Plugin | Contains | Turn on in | Notes |
|---|---|---|---|
| **K — "Spaarke <Practice> Knowledge"** | P5 instruction-only skills only. No scripts. | Every app that loads skills (Cowork today; PowerPoint and Excel 📄; Word when Microsoft adds Custom skills ❓) | Its skills **hand off** to engines when present: "If `<engine>` is available (Cowork), pass it the edit plan; otherwise report findings only." |
| **E — "Spaarke <Practice> Engines"** | P6 engine skills: a thin SKILL.md plus scripts | Cowork only | Engines are called **by** knowledge skills or by name. They contain no positions and no review logic. |

This is the "skills-only plugin plus code-only plugin" idea in a form the platform supports. A plugin can't carry bare code: code ships inside a skill folder. So the code plugin holds *engine skills* whose only job is to run scripts.

**Rule for K: assume it loads everywhere.**
- We have not tested a correctly built, instruction-only plugin in Word (T-P7). Harvey's presence in Word is circumstantial evidence that Word may load it.
- So K must be safe in Word. It holds **no skill that Microsoft Legal already provides in any app**. Above all, it holds no "review this agreement against a playbook" procedure, because in Word that is Microsoft Legal plus our Word playbook.
- With that rule, K causes no overlap whatever T-P7 shows:
  - **Playbooks vs K:** a Word playbook import creates *topics with rules* (positions), not skills, and K skills contain no positions (rule 4.3). Nothing is duplicated.
  - **Microsoft Legal vs K:** K holds no procedure Microsoft has. Nothing competes.

**Mapping today's NDA build onto it (until T-P7 and the T-P1 inventory):**
- **E (Cowork):** `nda-review`, the review procedure plus scripts, as today. It is Cowork's packaged-output review, which Microsoft doesn't do (§4.5).
- **K (everywhere):** only instruction-only skills that no Microsoft Legal skill provides. Candidates, to confirm against T-P1:
  - `accelerator-setup` (profile and onboarding, without the probe);
  - "which Spaarke playbook applies to this agreement" (routing across the playbook set);
  - "explain our position on topic X" (reads the playbook and cites the Topic ID).
- **Revisit after T-P7:** if Word does load K, we can decide deliberately whether any Word-side skill adds something beyond Microsoft Legal plus our playbook.

**Not decided yet:**
- ❓ Cross-plugin skill hand-off in Cowork is untested (T-P3). It is only needed if a K skill hands work to an E skill.

## 4. Non-overlap rules

1. **Microsoft first.** Before building a skill, list what Microsoft Legal (Word and Cowork) and the installed third parties already do (inventory, T-P1).
   - If Microsoft does the task, Spaarke supplies **content only**: a playbook or guidelines.
   - A Spaarke skill must add something Microsoft doesn't. Example: `nda-review` adds the packaged three-file set, script checks, the page-1 summary, topic IDs and the profile.
2. **In Word, review = Microsoft Legal + Spaarke Word playbook.** We do **not** ship a competing review skill for Word. This withdraws the `nda-review-inline` Word edition proposed earlier on 2026-11-02; it would create the three-way overlap of playbook, Word skill and Cowork skill.
3. **Positions never in skills.** A skill may reference the playbook and topic IDs; it never states a position. A position found in a skill is a defect, and the build gate should catch it (T-P5).
4. **Routing descriptions.** Every skill description says what it is for and names the owner of neighbouring tasks: "Do NOT use for MSAs (use review-contract)". This is already gated (`description-routing`).
5. **NDA overlap in Cowork, resolved (owner, 2026-11-02):**
   - `nda-review` (ours) and Microsoft's `review-contract` + playbook both review NDAs.
   - NDAs route to ours *because* of the packaged, checked output.
   - A customer who doesn't want that package uses Microsoft's skill with our playbook and switches our Cowork plugin off.
6. **Playbooks complement, never overlap.**
   - Each playbook covers one agreement type.
   - A shared position lives once in `core/positions/` and is compiled in (§2 P2).
   - A routing skill or the user picks the playbook. Two playbooks never both apply to one agreement.

## 5. How orchestration actually works

- **Copilot chooses the skill**, not us. It matches the user's request against the descriptions of the enabled skills (✅ "Review this NDA" picked `nda-review`; an MSA went to `review-contract`, T-09). Users can force a choice with the `/` menu or a skill chip (✅ Cowork; ✗ Word for our package).
- **Toggles are per user and per app** (✅ ours was on in Cowork and off in Word). An admin can deploy plugins to people or groups (📄) but cannot force per-app toggles (❓).
- **Protocol:**
  - Toggles are set once per role, not per task. Onboarding gives a recommended set per role; e.g. NDA attorney: Legal for Cowork on, Spaarke Knowledge on, Spaarke Engines on in Cowork.
  - Users should not need to switch plugins while working.
  - Overlap is prevented at design time (§4), not by asking users to toggle.
- ❓ How Copilot ranks two enabled skills that both match is undocumented; coexistence tests are T-P2.

## 6. Playbooks: lifecycle, locking and drift

**Where they live: two kinds, two places.**

| Kind | Location | Editable by attorney? | Read by |
|---|---|---|---|
| **Governed** (Spaarke baseline, firm-approved) | A SharePoint library, e.g. `Legal Playbooks/<practice>/`. Attorneys have **Read** only. | No | Word: Attach from Cloud › import (❓ T-P10). Cowork: the profile points to the library path (❓ T-P10). |
| **Personal** (an attorney's own) | The attorney's OneDrive: `Documents/Cowork/Playbooks/<practice>/`, today's MVP location (✅) | Yes, it's theirs | Word and Cowork, as today |

- **Today:** the MVP keeps everything in the user's OneDrive. That works, but it can't be locked, because the owner of a OneDrive file can always edit it.
- **Governed versions** therefore move to a shared library.
- **Fallback if T-P10 fails:** if Cowork can't read from a SharePoint library, setup copies the governed playbook into OneDrive with its version line, and the skill warns when the copy is older than the library version.
- The master Markdown stays in the repo or the customer's source. Both locations above hold outputs.
- **Cowork:** the skill reads the playbook named in the profile, or the attached file; it parses it fresh every run (✅). It never edits the playbook.

**Locking the Spaarke versions:**
1. **Primary: SharePoint permissions.** The library is read-only for attorneys and editable by the playbook owner. Simple and reliable.
2. **Optional: Word Restrict Editing** (no changes allowed) on the .docx. ❓ Confirm the Legal plugin still imports a protected file (T-P6).
3. **Avoid: sensitivity labels with encryption.** Unless the label grants Copilot extract rights, an encrypted file can't be read by Copilot. Test before using (T-P6).
4. **Locking can't cover P4.** Once imported and saved, Microsoft's playbook is the user's own editable copy.
   - Mitigation: every topic carries `Topic ID:` and the playbook carries a version line, so drift can be detected.
   - The guidelines say "Status / version".
   - Onboarding says: re-import when Spaarke publishes a new version.

**Drift rule:**
- The master is the only source. Word and Cowork copies are outputs.
- Changes an attorney wants go back to the playbook owner, who edits the master and republishes.
- ❓ Whether Microsoft's saved playbooks can be shared or centrally replaced is untested (T-P4).

**Does Microsoft's playbook "replace" our skill?** No: they cover different things.
- Microsoft's playbook object holds *topics with rules*: positions, in Microsoft's format.
- Microsoft's review skill holds the *procedure* in Word.
- Our Cowork skill holds a different procedure (the packaged, checked set) that reads the *same positions*.
- One set of positions, two procedures in two apps, no duplicated content.

## 7. Connectors (MCP): v2

- **What it would add:** live matter data from Spaarke Dataverse, documents in SharePoint Embedded, and a route into Word for *tools* (📄 custom federated connector, admin-created, Entra SSO).
- **Why v2:**
  - The NDA accelerator needs no matter data.
  - A connector is new BFF surface: CLAUDE.md §10 hygiene, an auth and security review, ADR-028.
  - It should follow the Word skills question, not precede it.
- **Reuse first:** the tenant already has "Spaarke AI" and "Spaarke Dataverse MCP" agents (✅ Chat › Added). The v2 connector should extend those, not start new.
