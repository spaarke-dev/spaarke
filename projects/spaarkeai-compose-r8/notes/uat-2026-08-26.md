## 5. Root causes and fixes

### D-1 — the link warning was an UNTOUCHED-BLOCK invariant breach (FIXED)

**This was the most serious of the six**, and it is not the defect the banner described.

**Root cause.** The link was an **internal cross-reference** — `<w:hyperlink w:anchor="Section2">`, i.e.
"see Section 4.2", the shape every legal document is full of. Task 024 nulled it in the CONTENT MODEL
(`internal-link-flattened`) reasoning that *"bookmark targets are not model data"*, and justified the
asymmetry in its own comment: *"the read walk still renders it as a live #anchor href — **read-path
only**."* **That premise was false.** `ComposeEditor` does `setContent(projection.html)`, so the read
walk's HTML *is* the editable document. The editor therefore held `href="#Section2"` while the model held
`null`.

**Why that is far worse than a dropped link.** `formattingUnchanged` compares the editor's per-character
href against the loaded model's. `"#Section2"` vs `null` can **never** match, so a paragraph containing a
cross-reference fell to the **rebuild** tier; its canonical key then diverged from the base, the merge
planned `Render` instead of `Clone`, and the paragraph was **re-authored on every save even when the user
never touched it** — taking any footnote ref / inline `w:sdt` / text box sharing that paragraph with it.

> That is a breach of **"untouched blocks are preserved"** — one of the two paired ADR-049 invariants that
> *"no amendment may trade one for the other"* — not a §3 edited-block loss. On save the orphaned
> `"#Section2"` then failed `Uri.TryCreate(..., Absolute)` in the renderer, which is the only part the
> user ever saw: *"A link's target could not be preserved."*

**The corpus could never have caught it.** All 24 fixtures contain **exactly one** `<w:hyperlink>` and
**zero** `w:anchor`. The "100% untouched-block preservation" figure had never once seen a cross-reference.
This is the second time a headline preservation number has rested on a corpus that lacked the construct.

**Not new in R8.** `projects/spaarkeai-compose-r7/notes/uat-issues.md:80` already records
`internal-link-flattened, link-target-not-preserved` from R7 UAT. It was reported, and carried forward.

**Fix.**
1. `ComposeDocxProjectionBuilder` — carry the anchor instead of nulling it. *This is the half that
   restores the clone path*, and therefore the invariant.
2. `ComposeDocumentRenderer.ResolveHyperlinkRelationships` — handle `#anchor` before `Uri.TryCreate`,
   authoring `w:anchor` and clearing the sentinel id. ADR-049 I-2-clean: a bookmark name is a
   self-contained scalar available verbatim at capture time, so it must be **carried, not re-derived**.
   It cannot dangle — the bookmark survives by clone or by `CarryUnmodeledConstructs` (task 041).
3. `internal-link-flattened` retired: no producer, so its client copy + label went in the same change
   (Direction B — a taxonomy advertising an unemittable code is the same over-claim as an under-reporting
   doc).

**Deliberately NOT done: no `("hyperlink", …)` row in `ReportableConstructs`.** The investigation proposed
one, on the premise that hyperlinks are lost on an edited block. After fixes 1+2 they are **kept**, so that
entry would mint a FALSE warning — precisely the anti-pattern tasks 046/048 *removed* entries for. The
parity harness is a two-direction forcing function; the measurement decided this, not the argument.

**Pinned by measurement, and proven non-vacuous.** New parity family `hyperlinkInternal`. Run against the
**unfixed** code it fails with:

```
hyperlinkInternal    untouched: 1/1 kept · edited: 0/1 kept · codes: (none)
```

`codes: (none)` — a **silent** loss, the same signature that exposed the inline `w:sdt`. Fixed: `1/1 · 1/1
· (none)`. The `expectedCode: null` arm now holds the §3 "hyperlinks are carried" claim in **both**
directions permanently.

**Doc honesty.** `COMPOSE-WRITE-RESIDUAL-LOSS.md` §3 claimed *"Comments, tracked changes, hyperlinks |
Carried on the content model itself"* — affirmatively the opposite of the truth, the over-claim §5 names
as the worst failure. Rewritten, with the correction called out rather than quietly applied. §2 gained a
row for `w:docLocation` / `w:tgtFrame` / `w:tooltip` / `w:history`, which **are** dropped silently on any
re-authored hyperlink — and §2's "nothing is silent" opener was amended rather than left standing, because
an unlisted silent loss is exactly what §5 exists to prevent.

**Still open (smaller):** `ComposeFormatToolbar` calls `setLink({ href })` straight from a `window.prompt`
with no scheme validation, so a user typing `example.com` manufactures the same warning. Worth fixing.

### D-6 — `view-url` 403: the filter read the wrong claim (FIXED)

**Root cause.** `DocumentAuthorizationFilter` read `ClaimTypes.NameIdentifier` and handed the result to
`IAccessDataSource`, which resolves a Dataverse `systemuser` via
`azureactivedirectoryobjectid eq '{id}'` — a column holding the Entra **`oid`**. With inbound claim-type
mapping left on (the default; never disabled anywhere in this codebase), .NET routes the token's **`sub`**
to `NameIdentifier` and `oid` to the long-form schema claim. Entra's `sub` is *pairwise* and non-GUID, so
it can never match a `systemuser`. A zero match is indistinguishable from "no rights" — it collapses to
`AccessRights.None` → `insufficient_rights` → **403 for every caller on every route the filter gates.**

**Why it looked impossible.** The tester had just opened, edited and saved that same document in Compose.
But Compose carries **no per-document filter at all** (`MapGroup("/api/compose").RequireAuthorization()`
only) and keys on the **SPE drive-item id**, not the Dataverse GUID. Compose never asks the question
`view-url` asks. "It worked in Compose" was never evidence of Dataverse Read.

**Two independent confirmations.**
1. *Wire fingerprint.* `code: undefined` + `message: 'Access denied'` matches only
   `ProblemDetailsHelper.Forbidden(reasonCode)`, which defaults the detail to that literal and emits
   `reasonCode`, never `code`. Every handler-thrown problem on this route carries `code`. So the 403 came
   from the filter, before any Dataverse row read or Graph call.
2. *The 403-not-401 tell.* The filter answers **401** when the claim is empty. A 403 proves the claim
   resolved to something non-empty — and under mapping-on that something is `sub`. The observed status
   code alone distinguishes the two hypotheses.

**Why 11,931 passing tests could not catch it.** The auth fixtures issue `oid` and
`ClaimTypes.NameIdentifier` as **the same constant**. In tests the two claims are interchangeable; in
production they never are. *A regression test MUST give them DIVERGENT values or it rebuilds the blind
spot instead of covering it.*

**Timing.** Commit `f076b1e38` (2026-08-24, two days before this UAT) attached
`AddDocumentAuthorizationFilter("read")` to `view-url`; its own message notes the route previously *"had
no per-document authorization of its own."* Before that commit this route could not 403.

**Fix.** New chokepoint `Infrastructure/Authentication/CallerResolution.cs` — deliberate sibling of
task 059's `TenantResolution`, same structural guarantee (takes a `ClaimsPrincipal`, so it *cannot* read
an identity from a header, route value or body). Resolves `oid` → long-form `oid` → `NameIdentifier` tail.

**Scope was larger than the filed defect** — the same lesson task 059 taught. Enumeration found
**11 broken sites in two classes**, not the one reported:

| Class | Shape | Sites |
|---|---|---|
| 1 — standalone | `FindFirst(NameIdentifier)` alone | `DocumentAuthorizationFilter` · `FinanceAuthorizationFilter` · `BulkDownloadAuthorizationFilter` · `WorkspaceLayoutAuthorizationFilter` · `ChatDocumentEndpoints` (in-handler authz) · `DataverseDocumentsEndpoints` (audit only — see below) |
| 2 — **backwards order** | `NameIdentifier ?? oid` | `IdempotencyFilter` · `PlaybookAuthorizationFilter` · `RegistrationAuthorizationFilter` · `SpeAdminAuthorizationFilter` · `UploadEndpoints` |

Class 2 is the subtler one and was **not** in the original finding: because `sub` is always present, the
`?? oid` tail is **dead code**. Two of those sites even end `?? FindFirst("sub")` — the author knew about
`sub` but ordered it last while `NameIdentifier` was already carrying it. `PlaybookAuthorizationFilter`
then runs `Guid.TryParse` on the result, which a `sub` can never satisfy.

`DataverseDocumentsEndpoints` is classed separately and honestly: its id reaches **telemetry only**, not
authorization. Fixing it is audit correctness (audit rows now correlate with the Dataverse user), not a
403 fix — it is not evidence for the security claim.

**Deliberately NOT changed:** `OfficeAuthFilter` / `OfficeRateLimitFilter` / `ResourceAccessHandler` read
`NameIdentifier` too, but only *after* checking both `oid` forms — correct already.

> 🔔 **OWNER SIGN-OFF REQUIRED BEFORE DEPLOY (auth change, CLAUDE.md §6).** This restores the *intended*
> check rather than loosening anything — the routes are denying **everyone** today, so the change is
> strictly from "nobody" to "those with Dataverse Read". But note the caveat `f076b1e38` recorded: a
> caller with container access but **no Read on the `sprk_document` row** succeeded before 2026-08-24 and
> will now correctly get 403. If UAT still 403s after this ships, that is the real permission gap, not
> this bug.

**Separate defect found, not fixed here:** `QueryReadAccessByProbeAsync` converts a Dataverse **404** into
a 403 — a deleted or wrong-entity id reports "no permission" instead of "not found". Worth its own ticket.

### D-4 / D-5 — the annotation path still anchors by TEXT SEARCH (root-caused)

**Confirmed: this is the same bug class Track C fixed for the edit path, never applied to the annotation
path.** Two independent halves of the anchor contract are missing for `agreement-review`:

1. **Return side.** `agreement-review.action.json`'s `flaggedSections[]` items require
   `sectionRef, quotedText, riskLevel, flaggedClause, assessment, standardRef` with
   `additionalProperties: false` — and **no anchor field of any kind**. Under Structured Outputs the model
   is *structurally incapable* of returning a paraId. Compare `compose-revise-document.schema.json`, whose
   `comments[]` require `target_para_id`.
2. **Supply side.** The dispatch sends `{fileIds, subDomain, reviewDepth}` — a **file** operand. The
   server's `HasStructuredOperand` scans for `selectionText/changesText/documentText`, matches none, and
   takes the file path, so the model never sees paraId-annotated text. It quotes from the RAG/Document-
   Intelligence extraction while placement searches the **editor's** blocks — two different extractions.

Placement therefore falls to `resolveAdvisoryAnchorSpan` → `resolveTargetSpans(...,'strict')`, i.e. the
very text-search module task 052 demoted on the edit path and deliberately left alive for annotations. It
fails deterministically for cross-paragraph quotes (a NUL sentinel between blocks means a needle can
*never* span a paragraph — and NDA clause quotes routinely do) and for recurring text (`ambiguous`, never
guessed). Task 055's paraId leg exists but is **dead code**: its own JSDoc says no caller supplies a
paraId.

**D-4's batch failure is a DIFFERENT defect** — do not conflate them. `findCommentAnchorRange` looks for a
`commentAnchor` **mark** by id; the thread survived in React state while its mark was destroyed with the
text it was attached to (the redline-accept path deletes struck ranges). That is an *anchor-lifetime*
failure, not a placement failure. They share only the symptom vocabulary.

**D-5 compounds it with a dishonesty bug.** The drop reason *is* computed — `anchor-mark-missing` /
`non-paragraph-anchor` / `cross-paragraph-span` — and then **discarded**, all three collapsing into
*"because its anchored text changed"*, which is only true for the first. That is why this UAT is not
self-diagnosing. Worse, the model-path save drops the same comments with **no banner at all**.

**Fix (designed, not yet applied)** — four layers, mirroring Track C:
1. **Dataverse mirror** (data, via `Deploy-ActionMirrors.ps1`): add `target_para_id` to
   `agreement-review`'s `flaggedSections[]` + `required`, prompt instructions, and the input schema.
2. **Supply**: pass paraId-annotated `documentText` at the four `useAgreementReviewGate` dispatch sites.
3. **Thread the anchor** through `ComposeAdvisoryCommentItem` → bridge → `placeAdvisoryComments`.
   One line at `ComposeWorkspace.tsx` activates the whole existing task-055 refusal path.
4. **Honesty + lifetime**: surface the three drop reasons as three distinct codes; warn on model-path
   thread loss; decide whether an accepted redline re-anchors or visibly orphans its comment.

**Design question for the owner (layer 4):** when a user accepts an AI redline over a flagged clause, the
comment's anchor text is deleted. Should the comment (a) re-anchor to the accepted replacement span, or
(b) show as "anchor lost" in the gutter? (b) is honest and cheap; (a) is what a reviewer probably expects.
This is a product decision, not a code one.
