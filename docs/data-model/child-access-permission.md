# Child Access Permission — `sprk_accesspermission` on To Do, Event, Communication and Document

> **Last Reviewed**: 2026-10-20
> **Reviewed By**: unified-access-control-r2 task 173 (owner rounds 81 and 84, GitHub #1423); task 189 (D7 T7a, GitHub #2126: a document's own narrowing)
> **Status**: Current (BFF and scripts in source; live rollout is the main session's gate)
> **Solution**: `SpaarkeCore` (the column ships with each table: rootcomponentbehavior 0)

## The rule

| Record | `sprk_accesspermission` holds | Who writes it | On the form |
|---|---|---|---|
| **Has a parent** (any non-null filing lookup) | The MOST RESTRICTIVE own value of the records at the TOP of its filing: Restricted (100000002) over Limited (100000001) over Standard (100000000). A null, or a top whose table has no such column, counts as Standard | The BFF only: the shared stamp path at create (`CoreAncestorResolver`), and `SecureChildReconciliationJob` every 2 minutes for everything else | Locked, with the info notification "Access permission is inherited from {parent}" |
| **No parent** | The value its user set | The user | Editable |
| **A Document with a parent** (task 189) | The STRICTER of its own narrowing and the value above: max(own, inherited). Its own narrowing is never widened; the inherited part follows its parents both ways | The same two BFF writers, from its record `sprk_accessinheritance` ([below](#documents-their-own-narrowing-task-189)) | Locked on a filed document today; T5 lets its pill be set to Restricted |

- **Display only — except on a document (D7).** Under D7 a document's own Restricted hides it from partners (task 188's read predicate, D7 T7, reads the stored value), so the BFF keeps a document's own narrowing (task 189, below). On To Do, Event and Communication, no access decision reads a child table's `sprk_accesspermission`. A child's access comes from its parent root (`sprk_project`, `sprk_matter`, `sprk_workassignment`): `ExternalParticipationService.GetRootRecordFlagsAsync` and the secure-root path read the ROOT flags (owner Q6, 2026-09-30). A parentless child's own value is recorded only — owner, 2026-10-08: "This is fine (BUT in future we might need to revisit)".
- **The top of a filing.** Walk the record's filing lookups up to records that have no filing parent of their own: a root (project, matter, work assignment), or a parentless child (a document under nothing, an unfiled invoice, a thread with no regarding). A To Do under a document under a Restricted matter is Restricted; a To Do under a parentless document whose own value is Restricted is Restricted.
- **Un-filing keeps the last value.** A record whose last parent is removed keeps the value it had, which becomes editable (round 81).
- **Undecidable filings are left alone.** A parent that cannot be read, does not exist, a filing deeper than 6 levels, or one that loops without reaching a record that has no parent: nothing is written and a warning is logged (`[INHERITED-ACCESS-PERMISSION]` at create, `[CHILD-ACCESS-PERMISSION]` in the job). The create never fails because of it.
- **Work assignments and projects** filed under a parent follow a FLOOR for `sprk_accesspermission` AND `sprk_issecure` (owner rounds 84 and 87): never looser than their parents, stricter by hand allowed (own values stay when the parent loosens) — enforcement through the filing walk (task 174), the stored values through `SecureRootInheritance.FollowParentsAsync` and `sprk_accessinheritance` (task 175; [access-inheritance.md](access-inheritance.md); write-path invariant I-17). On their main forms the same library is a floor lock (a looser pick is put back), not a read-only lock.

## Which lookups are "filing" lookups

The ONE map is `SecureChildLineage` (BFF, `Services/Access/SecureChildLineage.cs`), minus one link that is the record itself (`ParentLineage.NotFiling`): a document's `sprk_currentversionid` names its own file version. The form library carries the same map literally; `ParentLineageTests.FormLibraryParentLookups_MatchTheServerMap` fails the build when they differ.

| Table | Filing lookups (column → parent table) |
|---|---|
| `sprk_todo` | `sprk_regarding{agreement, analysis, budget, communication, document, event, invoice, matter, project, reportcard, workassignment}` |
| `sprk_event` | `sprk_regarding{agreement, analysis, budget, communication, event, invoice, matter, project, reportcard, workassignment}` |
| `sprk_communication` | `sprk_communicationthread`; `sprk_regarding{analysis, budget, event, invoice, matter, project, reportcard, workassignment}` |
| `sprk_document` | `sprk_matter`, `sprk_relatedmatter`, `sprk_project`, `sprk_relatedproject`, `sprk_invoice`, `sprk_relatedinvoice`, `sprk_workassignment`, `sprk_relatedworkassignment`, `sprk_relatedagreement`, `sprk_relatedcommunication`, `sprk_relatedevent`, `sprk_relatedtodo`, `sprk_canonicaldocument`, `sprk_parentdocument` |

**Not filing** (they never lock the field, and never give it a value): a contact, an organization or an account (parties), a service request (its own root, never looked through), an email activity, a document's own current version.

## Where it is written, and how fast

| Path | Mechanism | When the value is right |
|---|---|---|
| Every BFF create through `CoreAncestorResolver.StampAsync` / `DeriveForHostAsync` (Office To Do, workspace To Do builder, AI task action, communication service, AI email draft, event create) and the inbound association update | Inline, in the same payload | At create |
| Every other create or re-file: documents (all paths), client `Xrm.WebApi` and model-driven forms, imports, flows, BFF re-file routes (`PATCH /api/v1/child-records`, event and communication filing, `PUT /api/v1/documents/{id}`) | `SecureChildReconciliationJob` → `ChildAccessPermissionReconciler`: rows changed since its watermark and everything filed under them | Within one 2-minute run |
| A parent's value changes (a matter turns Restricted) | The same pass walks DOWN from every changed row (at most 6 levels) | Within one run |
| A hand edit of a parented child | The same pass (the row changed) | Reverted within one run. A document (task 189): an edit stricter than what its parents give it is kept as its own; one back to that value removes its own narrowing; one below it is put back |
| Rows nobody changed (created before task 173; drift after a restart) | The same pass's capped sweep window (`SecureChild:Reconciliation:MaxAccessPermissionRowsPerRun`, default 1000) until the instance has covered every row once | Within ceil(rows / cap) runs of a start |

Report: the job's `ResultJson.accessPermission` (`changed`, `parentless`, `undetermined`, `deferred`, `writeCapReached`, `changes[]`, `sweep`; task 189: `recordsWritten`, `ownKept`, `changedConcurrently`, `raisedOnly`). A listing fault or a failed write makes the run unsuccessful; an undecidable row is reported and carried.

**Write cap.** At most `SecureChild:Reconciliation:MaxAccessPermissionWritesPerRun` writes per run (default 500). A run that reaches it stops writing and keeps its window (the watermark and the sweep cursor stay), so the next run lists the same rows and writes the next ones; only differing rows are written, so a matter with thousands of children converges over several runs. The pass runs after the secure pass has saved its own cursor and watermark.

## Documents: their own narrowing (task 189)

D7 rule 2: a document's own Restricted hides it from partners. A document may therefore be stricter than its parents, and the BFF must never reset that to the parents' value. It holds **max(own narrowing, inherited)**:

- **Own vs inherited** is recorded in `sprk_document.sprk_accessinheritance` (task 175's v1 JSON: the parents, the value they last gave it as `floorPermission`, and `ownPermission`). The rule is task 175's classification, ONE copy (`AccessInheritance.OwnPermissionOf`), applied by `InheritedAccessPermission.DecideDocument` for both writers (`ChildAccessPermissionReconciler` and `CoreAncestorResolver.RefreshInheritedAccessPermissionAsync`, the child-records create and re-file):
  - a stored value equal to max(own, last inherited) is unchanged: the own narrowing stands and the inherited part follows the LIVE parents, both ways;
  - any other stored value was set outside these writers (a user's edit, a BFF writer's narrowing). Stricter than the last inherited value OR the live one → its own. At or below both → put back to the live inherited value, and the own narrowing is removed. So a user's Limited set after a Restricted matter widened to Standard stays Limited. Task 189's fix round added the live comparison; compared with the last inherited value alone, that Limited was put back to Standard (the "K1 variant", a defect);
  - no record (rows written before task 189): stricter than the current inherited value → its own; otherwise inherited. Sound because task 173 kept every parented row equal to its parents before.
- **The inherited part follows the parents both ways**, and a re-file follows the new parents (task 173's contract), for every row without an own narrowing. A document with its own Restricted stays Restricted when its matter widens.
- **A parentless document** keeps its own value, never written (round 81). A Limited or Restricted value on it is RECORDED as its own (`{parents: [], floorPermission: Standard, ownPermission: …}`), so a later filing keeps it. An un-filed document's last value is likewise recorded as its own.
- **Who may remove it:** any user with Write, by an edit to or below the inherited value (D3). A Full Access gate belongs to Manage Access (T3/T5).
- **A BFF writer that narrows** (the Office fallback, T8) writes `AccessInheritance.OwnNarrowing(Restricted)` in the same payload as the stored Restricted. Under a Restricted matter a narrowing equal to the inherited value is otherwise read as inherited and follows a widening.
- **One update** carries the value and the record. The job re-reads both just before writing; a row that changed since its listing is not written (`changedConcurrently`) and is decided again next run.
- **Fail closed, never below the parents** (fix round C, K1+K2): a stored value that is not a known level writes nothing (`undetermined`, carried). When a document's own narrowing cannot be known (an unreadable record: not JSON, another version, or a level inside it that is not known; or an environment whose documents lack the record column), its value is only RAISED to what its parents give, never lowered, and its record is left as it is (`InheritedAccessPermission.DecideDocumentRaiseOnly`; the run counts it in `raisedOnly` and `changed`). An unreadable record is also reported `undetermined` and carried; a missing column lists `sprk_document` in `tablesWithoutColumn`, and the column is then neither read nor written. Run `scripts/Set-DocumentAccessPermissionSchema.ps1 -Apply` before deploying a BFF with task 189: a raise kept while the column is missing (the parents widened again) is recorded as the document's own on the first run after the script and is never widened again. `SPAARKE-CUSTOMER-DEPLOYMENT-GUIDE.md` §7.4 says how to find such documents and widen them by hand.
- **Every parented document gets a record** (fix round C, F1), the Standard majority too: each row without one is written once (the sweep reaches the legacy rows), then not again while nothing changes. Without it, a user's narrowing made in the window its parent tightens to the same level read as inherited and followed the parent's later widening. Each write changes the document's `modifiedon` once (one audit entry; see the task 189 notes §8.9 for what reacts to it).
- **Not field-secured** (D1): the inherited part is always recomputed from the parents and never read from the record, so an edit of the record can only remove the user's own narrowing or add one — never take the document below its parents.
- **Only the approved writers write it.** `ChildAccessPermissionReconciler`'s `DecideDocumentAsync` and `CoreAncestorResolver.RefreshDocumentAccessPermissionAsync` write a document's value; every other writer of `sprk_accesspermission` is listed with the reason it never reaches a document. The shared stamp path (`CoreAncestorResolver.StampAsync`, `DeriveForHostAsync`, `ApplyInheritedAccessPermissionAsync`, `ResolveInheritedAccessPermissionAsync`) is **fenced**: it gives a document no value, whoever calls it, because its helper returns none for a table that records its own narrowing. Enforced by `tests/Spaarke.ArchTests/DocumentAccessPermissionWriterGuardTests.cs` (write sites; its ratchet baseline is empty) and, for the fence, `InheritedAccessPermissionStampTests`. The scan cannot see a key held in a local variable, or a payload a caller hands in (accepted limit). For the app-only generic writers that take such a payload, a run-time refusal closes it (below).
- **App-only generic writers refuse both columns on a document** (fix round C, K5): the Update Record playbook node (`UpdateRecordActionCore`) and a playbook's output mapping (`DataverseUpdateHandler`), whatever identity their run writes as (#2257 fix round 1), and the action seam acting for no person refuse a payload naming `sprk_accesspermission` or `sprk_accessinheritance` on `sprk_document` (`sdap.access.document_access_server_only`, nothing written; `InheritedAccessPermission.RefuseAppOnlyWrite`), as `ChildRecordEndpoints.RootServerOwnedColumns` does for a work assignment. A model or a configuration builds their payload, and a value or record it wrote could lower a user's Restricted. Unchanged: the same columns on a to-do, event or communication, and a user's own write (the form, the user-OBO chat tools and the action seam's apply of a proposal its impersonated user confirmed). Pinned by `DocumentAccessPermissionAppOnlyWriterTests`. ## The form

`sprk_accesspermission_inherited` (`src/client/webresources/js/sprk_accesspermission_inherited.js`), OnLoad `Spaarke.AccessPermissionInherited.onLoad`, registered by `scripts/Set-InheritedAccessPermissionFormLock.ps1` on every Main and Quick Create form of the four tables that shows the column (the TrackingFieldTrio pill on the To Do and Event main forms; a plain control the script adds to the Communication "Message main form" and the "Document main form" — no TrackingFieldTrio on Communication, owner round 81). The library writes nothing: it disables the controls it found enabled, stops the column being submitted, and puts back a change a bound PCF makes, while the record has a parent.
