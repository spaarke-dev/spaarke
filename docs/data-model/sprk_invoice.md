### Field security on the amounts and the firm (EB-D-200, task 166)

Seven columns are **field-secured, readable by everyone, settable only by the server** (owner decision EB-D-200, with the access reviewer's option D): the billed total `sprk_totalamount`, the five derived totals `sprk_feestotal`, `sprk_expensestotal`, `sprk_lineadjustmentstotal`, `sprk_invoiceadjustmentstotal` and `sprk_approvedtotal`, and the firm lookup `sprk_vendororg` (to `sprk_organization`). Record-level Write for users is unchanged (D-77); what a user can no longer do is set one of these seven values.

- **Writes.** Only "Spaarke BFF-Managed Field Writers" (the BFF application users) hold read, create and update. Every BFF writer is typed and app-only: `InvoiceTotalsService.RecalculateAsync` (the five derived totals), `InvoiceSubmissionPersister` (the billed total and the firm, in the invoice's create), `InvoiceAssignFirmService` (the firm, in Set firm's renumber transaction) and `InvoiceCorrectionService` (the billed total, in a header correction). Any other profile that can create or update one of the seven is a FAIL in the script, the platform System Administrator profile excepted.
- **Reads.** "Spaarke BFF-Managed Field Readers" (on every business unit's default team) holds read only, so every user still sees the columns on the forms and the Web API. The billed total is read-only on the main and quick-create forms (the total comes from the submission, FR-17, FR-20).
- **Generic writers are refused too.** The BFF application user is a Writers member, so field security alone does not stop the BFF's own generic writers (an AI output mapping, an Update Record node, Repair, a field-mapping rule). The six amount columns are therefore in `InheritedAccessPermission.AccessColumns["sprk_invoice"]` (app-only generic writes refuse them, with the reason "it decides no access; it is an invoice amount, and only typed writers derive it") and in `RecordTableRules` `MappingProtectedColumns` for `sprk_invoice`. The firm is in `AccessColumns` already. Pinned by `AccessTableAppOnlyWriterTests` and `RecordTableRulesTests`; every writer of the seven columns is pinned app-only and typed by `InvoiceMoneyColumnsAppOnlyWriteGuardTests`; the script and the SpaarkeMaster source are pinned to each other by `InvoiceMoneyFieldSecurityAgreementTests`.
- **Derived Threshold.** `sprk_totalamount` and `sprk_approvedtotal` are also base columns of the derived Threshold (`FinanceBaseValues.DerivedBaseColumns`). The evaluator is the BFF application user, a Writers member, so it still reads them; they are the reviewed exception in `DerivedBaseColumnSecurityExceptions` (a listed column must be secured, every other derived column unsecured).
- **Companions.** The money `_base` companions cannot be secured on their own; whether the platform masks them once the parent is secured is unverified (task 166 notes, F2). They are system-calculated and not user-writable.

### Totals calculation (FR-07, I-1, D-42; task 016)

The five totals and every Adjustment line's `sprk_amount` are written only by `InvoiceTotalsService.RecalculateAsync(invoiceId)` (`Services/Finance/InvoiceTotalsService.cs`), which applies `InvoiceTotalsCalculator` (`Services/Finance/InvoiceTotalsCalculator.cs`). No API takes a total from a caller. Definitions:

- fees total = sum of `sprk_amount` of Fee lines; expenses total = the same for Expense lines (both as billed);
- a Fee or Expense line's adjustment = `sprk_amount - sprk_approvedamount` when its status is Reduced, `sprk_amount` when Disallowed, 0 otherwise; line-adjustments total = the sum;
- a Percent Adjustment line = `value% x max(0, fees total - sum of the Fee lines' adjustments)` (clamped at zero, D-129 (2)), expenses never in the base, every percent line on the same base (they do not compound); a Fixed Adjustment line = its value; invoice-adjustments total = the sum of the Adjustment-line amounts;
- approved total = `sprk_totalamount` (billed) - line-adjustments total - invoice-adjustments total.

**Rounding.** `decimal` arithmetic; each computed adjustment and each total is rounded to 2 decimals with `MidpointRounding.AwayFromZero` (half a cent rounds up, not to even). USD only in R1; no currency conversion.

**Refusals (FR-32), stable codes, nothing written.** `invoice-totals.approved-total-negative` (adjustments exceed the billed total; applies only when the billed total is zero or more; a credit memo, with a negative billed total, has no extra limit, D-129 (1)); and, fail-closed, `invoice-totals.line-cost-type-unknown` (a line with no Fee / Expense / Adjustment cost type), `invoice-totals.line-approved-amount-invalid` (Reduced line with no approved amount, or one outside 0 .. billed amount; for a credit, outside the billed credit .. 0, D-129 (3)), `invoice-totals.adjustment-invalid` (Adjustment line with no method / value, a negative value, or a percent above 100), `invoice-totals.billed-total-missing` (`sprk_totalamount` empty). The earlier refusals `invoice-totals.line-amount-negative` (D-121) and `invoice-totals.total-below-storable-minimum` (a total below the old column minimum of 0) are gone: no total is below the storable minimum any more (D-127). A Fee or Expense line may be a credit: it keeps its negative `sprk_amount` and is summed as a signed value; a Disallowed credit is summed signed too, so disallowing a credit raises the approved total and needs no offsetting charge (D-128); a Reduced credit accepts part of the credit: the approved amount lies between the billed credit and 0, so -100 reduced to -40 raises the payable by 60; accepting more credit than billed (-150) or flipping the sign (+10) is refused (D-129 (3)).

**Percent adjustments on a negative fee base (D-129 (2)).** The fee base of a percent Adjustment line is clamped at zero: `value% x max(0, fees total - sum of the Fee lines' adjustments)`. On a net-negative base a percent adjustment adjusts nothing (10% of -700 is 0, the invoice stays -700); on a positive base it is unchanged. A fixed adjustment is not affected. Disallowing a credit takes it out of the base like any disallowed fee line. An Adjustment line's own `sprk_linestatus` is never read; only Fee and Expense lines are decided.

Each is built, not sent, by `IInvoiceLifecycleService.BuildSupersedeRequest` / `BuildSupersedeUndoRequest` as an `UpdateRequest` conditional on the row version the caller read (`IfRowVersionMatches`), for the caller's transaction; `TransitionAsync` refuses both. The request is returned, not sent, so the 049 processor can put it in one `ExecuteTransactionAsync` with the lines. Creating directly in Rejected (statecode 1) is the shape to verify on the first live run (task 079); if Dataverse refuses it, the builder changes to Create In Review plus a state change in the same transaction.

In Review (pending), Rejected, Returned to Firm and Cancelled are not counted. The matter / project rollup, the Signal evaluator's Threshold sums and the FinancialCalculation tool all use this set. A new invoice is created without a status value and takes the `statuscode` default, In Review.
